Comparative proposition

The claim being compared across conferences

The shared pressure is movement and contention; mechanisms and quality targets remain heterogeneous.

Venue roles

What each conference contributes

Venue Current role Evidence references
ISCA Systems and architecture cases expose expert traffic, collectives, KV (key-value: the stored notes a language model keeps about earlier words) locality, PIM (processing in memory: logic placed inside the memory chip) scheduling, and deployed memory context. 10
DAC Memory and accelerator (a chip or block built to do one kind of work fast) cases expose CXL (Compute Express Link: a standard link that lets chips share memory), near-memory, PIM, buffering, and movement-aware execution mechanisms. 4
ICCAD Physical-integration cases connect bandwidth (how many bytes a link can move per second) and placement to 3D thermal and package constraints. 1

What is actually comparable

What can fairly be compared

The comparison should be made at the mechanism and constraint level first. A fair comparison holds six things fixed: the workload or design set, the hardware or simulator assumptions, the baseline, the metric, the test budget, and what counts as a failure.

Required matched fields

What must match before results can be compared

Field Why it matters
Workload / design population Determines whether the mechanism addresses the same pressure.
Hardware / process / tool version Separates a mechanism from a platform advantage.
Baseline and budget Prevents unequal search, retries, tuning, or evaluator effort.
Metric and end-to-end boundary Prevents proxy improvement from being reported as system benefit.
Failure model and limits Defines what counts as valid, safe, feasible, or transferable.

Next matched comparison

The next fair comparison to run

Match workload, recall/accuracy, resident set, capacity, bandwidth, topology, migration cost, and tail latency (the wait for one result).

Current conclusion boundary
