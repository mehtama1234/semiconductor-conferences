The bigger theme this belongs to

  • Architecture and accelerators

Hardware and software jointly determine the executed work

A hardware design exposes operations, storage, connections, and ways to control execution. Software chooses how the application uses those resources.

A hardware feature produces little benefit if software cannot express or schedule useful work for it. A software optimization can likewise fail when the hardware lacks the storage, precision, or control it assumes.

Co-design means changing these choices together. The research question is whether the combined arrangement improves a stated application objective while preserving required behavior. The combined result alone does not show how much benefit came from each change.

Start with the boundary between the two

An instruction set describes operations software can request. A memory layout determines where values are stored and how the program addresses them.

A compiler translates a program into operations and a schedule. Runtime software makes decisions while the program executes, such as assigning work or selecting a representation.

Changing one of these boundaries changes both opportunity and responsibility. A new operation may reduce instruction count while requiring specialized hardware and compiler support.

A new memory format can reduce transfers while requiring conversion and a new execution routine. Those supporting costs belong in the system result.

Buffering shows why lifetime matters

A buffer is storage reserved for values needed during execution. The required capacity depends on when each value arrives and when its last use occurs. Values that are no longer needed can release space even if other parts of the computation are unfinished.

Matrix multiplication is often divided into smaller blocks, called tiles, so that inputs can be reused in limited nearby memory. Choosing tile dimensions affects input reuse, partial-output storage, and the number of times small execution routines must start.

A larger reuse opportunity can therefore come with more control or switching work.

Asymmetric tile buffering: mechanism and evidence boundary

The ATB preprint chooses input and output buffer dimensions independently and models both reuse and execution-switching costs. Sections 3–5 explain why storage lifetime and execution overhead must be considered together. ATB, sections 3–5

Asymmetric Tile Buffering: buffer shape changes which data can be reused before it changes how fast arithmetic runs

What tiled matrix multiplication needs to store

Matrix multiplication combines blocks of an input matrix with blocks of another matrix and accumulates partial output blocks. A tiled implementation loads a block into a local buffer, reuses it across several operations, and writes an output block when its required contributions are complete.

The buffer must hold data until the last operation that uses it; capacity is determined by both tile dimensions and data lifetime.

Input and output storage have different lifetimes. An input tile can be reused across multiple output tiles, while an output tile may need to remain local while partial sums from several input tiles accumulate.

Making the input and output tile shapes identical is convenient, but it couples two storage decisions that serve different reuse patterns.

What asymmetric buffering changes

Asymmetric tile buffering decouples input-tile dimensions from output-tile dimensions. This lets the implementation choose more input reuse or more output accumulation according to the matrix shape, precision and local capacity.

The useful objective is not simply a larger tile. It is the amount of arithmetic performed per value loaded or stored, subject to buffer capacity and the schedule that moves between tiles.

Arithmetic intensity is the ratio of arithmetic operations to data movement. Increasing reuse can raise arithmetic intensity, but a larger or differently shaped tile can also increase partial-output storage, reduce the number of compatible execution slots, or require more frequent kernel changes.

ATB's performance model explicitly includes kernel-switching cost, so the best buffer shape is a tradeoff between reuse and control overhead.

What the preprint evidence supports

The preprint describes mixed-precision BFP16-BF16 GEMM (general matrix multiplication: multiplying two grids of numbers) on an AMD XDNA2 AI Engine and compares MLIR-AIE, symmetric buffering and ATB configurations. The captured values include 4.8 TFLOPS for an MLIR-AIE endpoint, 17.3 TFLOPS for a symmetric configuration, 24.3 TFLOPS for an ATB configuration and a 24.6 TFLOPS size-sweep peak.

The preprint also prints a 4.54× speedup headline.

KL-MoE: pruning experts changes both the stored model and the routing choices that reach it

What a mixture-of-experts layer does

A mixture-of-experts layer contains several expert networks and a router. For each token, the router scores experts and selects one or more of them.

The selected experts process the token, and their outputs are combined. This lets a model have a large total parameter set while using only part of it for each token, but deployment still pays to store the experts and to move tokens to the selected computation.

Pruning removes some experts or reduces their representation. The model then has fewer possible functions and the router must send tokens to the remaining experts.

A pruning method is successful only if the retained experts cover the behaviors needed by the workload and the routing changes do not create load imbalance or a quality loss.

What KL divergence is comparing

Kullback–Leibler divergence compares two probability distributions. For distributions (P) and (Q), (D_{KL}(P|Q)=\sum_i P(i)\log(P(i)/Q(i))) when the terms are defined.

It is directional: comparing (P) to (Q) is not generally the same as comparing (Q) to (P). In this context, a KL-based selection can compare the output or routing behavior of experts and identify representatives whose distributions are similar under the selected data.

Similarity under one calibration set does not prove functional equivalence for every token. Two experts can behave similarly on common inputs and differ on rare inputs, long-context states or a task not represented in the calibration data.

The selection distribution, temperature, zero-probability handling, layer location and aggregation therefore need to be specified.

What hierarchical clustering and Linear Restore change

Hierarchical clustering first groups experts into a structure of related candidates instead of comparing every expert as one flat set. Representative selection then keeps a smaller set intended to cover the groups.

The claimed benefit depends on the clustering features and on whether group similarity predicts the downstream task behavior.

The record also names a lightweight Linear Restore mapping for pruned MoE layers. A restore mapping can transform or remap the retained experts' outputs to compensate for the removed experts, but it adds parameters, computation and a new learned approximation.

It does not recreate information that was never represented in the retained experts. The storage and latency of the mapping must be counted with the pruned model.

What the reported measurements require

The official description reports 12.89%, 7.24% and 6.14% average gains over O-Prune, MoE-I2 and HC-SMoE, plus 1.31× inference (running a trained AI model to get answers) speedup. The captured record does not identify what the percentage gains measure, the accuracy metric, pruning ratios, model list or storage/latency operating points.

These values cannot be read as accuracy gains, compression gains or speedups without the missing definitions.

Measure quality before and after pruning, expert count, retained parameters, router load distribution, token drop or reroute rate, restore cost, memory, latency, throughput and energy. Test common and rare tokens, long contexts, different batch sizes and all listed models.

Compare at equal quality, equal retained storage and equal hardware conditions where possible; otherwise keep each comparison dimension explicit.

What the record establishes and where it stops

The official description establishes a hierarchical MoE-pruning proposal using KL-divergence-based representative selection and a Linear Restore mapping. It reports source-level percentage and inference-speedup claims but does not define their metrics, model set, pruning ratio, hardware or exact page/table support in the captured record.

The KL-MoE record is evidence of a named pruning direction, not an independently validated general MoE deployment result. The detailed explanation above separates expert storage from routed compute, KL similarity from universal functional equivalence, restore computation from free recovery, and reported ratios from undefined metric boundaries.

GenDSE: CPU design-space exploration is a sequence of constrained choices followed by expensive evaluation

What design-space exploration is evaluating

A CPU (the general-purpose processor that runs ordinary programs) design space is a set of possible configurations. A configuration can specify choices such as pipeline structure, cache parameters, issue width, branch resources, execution units or other microarchitectural features.

A simulator estimates how a configuration behaves on a workload. The goal is not merely to generate a valid configuration; it is to find configurations with a useful tradeoff among performance, area, power, cost or another stated objective.

Simulation is expensive because each candidate must be constructed, checked and run on one or more workloads. The space is combinatorial: choosing one value can affect which later choices are valid and how valuable they are.

A search method therefore needs to preserve constraints and account for interactions between decisions.

What the sequential formulation changes

Representing exploration as a Markov decision process means constructing a configuration through a sequence of actions. A state records the choices made so far; an action adds or changes a design decision; a terminal state is a complete configuration that can be simulated.

The Markov assumption requires that the information retained in the state is sufficient for deciding the next action and evaluating the eventual configuration.

This formulation makes credit assignment explicit. A final score is produced after the complete configuration is simulated, but the method must learn which earlier choices contributed to that result.

If the state omits a dependency or constraint, the generator can favor invalid or misleading partial configurations.

What a GFlowNet-style generator and sketching are for

A GFlowNet is a generative policy trained to sample terminal objects according to a reward-related distribution rather than only returning one highest-scoring path. For design exploration, this can preserve multiple promising configurations and provide diversity across a Pareto-relevant region.

The reward definition still controls what “promising” means; a reward that overweights simulated performance can ignore area, power, validity or robustness.

Progressive Sketching is named as the data-efficiency component, but the captured record does not define the sketch, what information it removes, or whether it changes simulation fidelity or only the learning representation. Any sketch must be checked for information loss: reducing the number of simulations is useful only if the selected designs remain competitive under the full evaluation.

What the 90% claim needs attached to it

The official description reports 90% average simulation-cost reduction and solution quality, but does not give CPU configuration dimensions, absolute simulation budgets or numerical quality comparisons. A percentage reduction needs a defined baseline (the existing method a new result is compared against) count or time, workload set, simulator fidelity, invalid-candidate handling and stopping criterion.

“Solution quality” needs the objective, constraints, Pareto (Pareto front: the designs that no other design beats on every cost at once) measure and comparison point.

Evaluate GenDSE and the surrogate-guided baseline with the same initial design set, simulation budget, validity checks, workloads, random-seed protocol and stopping rule. Report best-so-far quality against simulation count, not only final quality after unequal budgets.

Show whether the method finds diverse valid designs and whether its selected candidates remain strong when re-evaluated with the full simulator or a higher-fidelity model.

What the record establishes and where it stops

The official description establishes a sequential-decision CPU design-space exploration proposal using MDP construction, GFlowNet-based configuration generation and Progressive Sketching for data efficiency. It reports a qualitative solution-quality claim and 90% average simulation-cost reduction but does not provide the dimensions, budgets or numerical quality evidence needed to interpret them.

The GenDSE record is evidence of a named exploration method, not an independently validated CPU-search result. The detailed explanation above separates valid configuration generation, reward shaping, diversity, simulation cost and final design quality.

HYPER-CIM: a predictive design flow must connect circuit choices to architecture behavior and fabrication evidence

What a digital CIM design contains

Compute-in-memory places some computation near the storage array so data does not travel through a separate memory-to-compute path for every operation. A digital CIM (compute in memory: arithmetic done inside the memory array) design still has a macro-level organization, interfaces, control, buffering, data movement and an architecture that uses one or more macros.

Choices such as precision, storage, channel count, pipeline depth and accumulation length affect different levels of that system.

Optimizing only one level can produce an attractive local result that cannot be used efficiently at the next level. A circuit choice can change cycle time, area, power or data format; an architecture choice can change how often the macro is activated, how much data is buffered and how much communication occurs.

A useful design flow must pass the relevant conditions between levels.

What the hierarchical predictive flow is doing

HYPER-CIM is described as a hierarchical exploration flow using a digital 28-nm CIM template, a multi-head circuit-optimization surrogate (a fast model that stands in for a slow simulation), Pareto search and silicon verification. A surrogate predicts one or more circuit metrics from design choices instead of simulating or implementing every candidate in full detail.

“Multi-head” indicates multiple predicted objectives or outputs, but the captured record does not define the heads, training data, model error or uncertainty handling.

The hierarchy can reduce search cost by using cheaper predictions at an early level and passing selected candidates to more detailed evaluation. This is useful only if the surrogate preserves the ordering of candidates well enough for the final objective.

A low average prediction error can still choose the wrong Pareto candidates if errors are concentrated near a constraint or tradeoff boundary.

What Pareto search means here

Two designs are compared across objectives such as energy efficiency and area efficiency. A design is Pareto-dominated if another design is at least as good on every objective and better on one.

The Pareto set contains non-dominated tradeoffs; it is not one universally best design. The flow must state the objectives, constraints, normalization, precision, workload and whether the set comes from predictions, detailed simulation, layout or fabricated measurements.

Silicon verification can show that selected fabricated macros operate under measured conditions and can reveal mismatch between the template, surrogate and physical implementation. The official description establishes a hierarchical digital-CIM exploration flow with a 28-nm template, circuit surrogate, Pareto search and some silicon-verification claim. The captured assessment records no recovered full paper and explicitly separates predicted configurations, training points and reported macros.

Full prior-design conditions, accuracy/workload conditions and fabricated-design reproducibility remain open.

The HYPER-CIM record is evidence of a predictive co-design flow, not independent validation of the entire predicted design space. Cassandra: self-speculative decoding reduces target-model work only when proposed reasoning tokens are accepted usefully

What speculative decoding changes

Autoregressive decoding generates one token at a time. For each next token, the model reads the current sequence and produces a probability distribution.

A self-speculative system uses a cheaper version or path of the model to draft several tokens, then uses a more accurate target path to verify them. Accepted draft tokens avoid repeating the full target computation; rejected tokens still cost draft work and verification work.

The useful unit is not draft tokens produced. It is accepted output produced per unit of complete decoding work, while preserving the defined output-quality rule.

Acceptance depends on the draft path, prompt, model state, draft length, verification policy and sampling/decoding rule. A high token count under one memory budget does not by itself establish lower response latency or equal reasoning quality.

What Cassandra changes in the edge execution path

The captured record describes a training-free pipeline with fine-grained data selection, pruning, mantissa truncation, salient-weight and KV-cache selection, and a lightweight hardware encoder-decoder for format conversion. These choices target different costs.

Data selection and pruning reduce what is computed or stored; mantissa truncation changes numerical representation; KV-cache selection changes which prior-token state remains available; format conversion determines whether the reduced representation can be consumed efficiently by the hardware.

Training-free means the method does not require an additional training phase for the reported use, not that it has no calibration, selection, conversion or runtime cost. A pruned or truncated draft can be faster but propose worse tokens.

A smaller KV (key-value: the stored notes a language model keeps about earlier words) cache can reduce memory traffic while removing context information. A format converter can make representations executable while adding hardware area, latency and energy.

Why reasoning LLMs need a stronger quality boundary

Reasoning tasks can depend on intermediate steps, not only on the final token distribution at one position. A decoder can accept many locally plausible tokens and still change a later reasoning path, answer, tool call or stopping point.

Evaluation should therefore report exact-match or task success where applicable, output length, refusal/error behavior, acceptance rate by draft length, target-verification work, time to first token and time per generated token.

The card reports up to 2.41× speedup over BF16 and 1.81× more tokens than Eagle-3 at the same memory budget on Llama 3 8B with an NVIDIA GeForce RTX 4090. “Up to” identifies a best condition.

The evidence does not specify prompt distribution, batch distribution, acceptance conditions, quality metric, complete latency boundary, format-conversion cost, hardware area or power, so the ratios cannot be generalized to edge devices or all reasoning workloads.

What a co-design evaluation must report

Compare BF16 decoding, Eagle-3 and the other named baselines with identical models, prompts, output-quality rule, batch, sequence length and stopping condition. Report draft and target compute, accepted-token rate, rejected-token work, KV-cache bytes, conversion traffic, memory occupancy, throughput, tail latency, energy and quality.

Measure the encoder-decoder module separately and as part of complete decoding.

The hardware claim also needs a supported-format definition and an area/frequency/power boundary. A commercial RTX 4090 result is evidence for that software/hardware setup, not evidence of a fabricated edge accelerator (a chip or block built to do one kind of work fast) or an NPU (neural processing unit: a chip built to run AI models) implementation.

The abstract's page-level evidence supports the mechanism and headline conditions, but exact tables and method details require the full paper.

What the record establishes and where it stops

The primary preprint abstract establishes a training-free self-speculative decoding proposal for reasoning LLMs (large language model: an AI model that reads and writes text) combining reduced data/weight/KV representations with lightweight format conversion. It reports bounded Llama 3 8B/RTX 4090 speed and memory-budget claims.

It does not establish exact acceptance/quality behavior, complete conversion cost, hardware implementation cost or broader device generalization.

The Cassandra record is evidence of a named edge-inference co-design direction, not a full-paper or independent reproduction. The detailed explanation above separates draft production from accepted output, representation reduction from conversion cost, token count from useful latency, and one commercial-GPU condition from general edge deployment.

PLENA: long-context inference is constrained by both how much state exists and how fast it can move

What the two memory walls mean

Long-context agentic inference retains information from earlier text, web pages, tool calls and interaction steps. The retained state can exceed the capacity of a fast local memory, forcing transfers to a larger but slower memory.

This creates a capacity wall: the state does not fit where the compute wants to use it.

The same state can also create a bandwidth (how many bytes a link can move per second) wall. Even when the data fits somewhere in the system, the links and memory interfaces may not deliver it fast enough to keep the arithmetic units busy.

Capacity asks whether the data can be stored; bandwidth asks whether it can arrive at the required rate. A design can solve one and still be limited by the other.

What PLENA changes in the hardware/software path

The record describes asymmetric-quantization compute/memory units, a flattened systolic array capable of FlashAttention-style execution, a custom instruction set, compiler, cycle-emulated simulator and automated design-space exploration. These components form one co-design contract.

Asymmetric quantization means different operands or data roles use different numerical formats or precisions. This can reduce storage and movement for values that tolerate lower precision while preserving more precision where error matters.

It requires the hardware to consume the formats directly and the compiler to schedule conversions, accumulation and memory placement correctly. The captured abstract does not specify the exact precision assignment or quality conditions.

Flattening a systolic array changes how attention-related operations are laid out across processing elements and how data moves through them. FlashAttention-style execution reduces the need to materialize large attention matrices by processing blocks and retaining required intermediates locally.

It does not make the long-context state disappear: keys, values, tool history and other state still require a capacity and movement policy.

The custom ISA (instruction set: the list of commands a processor understands) exposes operations the compiler must schedule. A simulator can estimate cycles for that instruction stream, but the result depends on the modeled memory hierarchy, link contention, buffer sizes, clock, precision, instruction semantics and control overhead.

The compiler and design-space search are therefore part of the measured system, not optional implementation details.

What the reported comparisons establish

The captured record reports up to 8.5× higher utilization than existing accelerators, 2.24× throughput over an A100 and 3.85× throughput over a TPU v6e under matched multiplier and memory settings. The evaluation is simulated.

The exact models, context lengths, memory hierarchy, area, energy, simulator validation and artifact status are not recorded in the captured abstract.

“Matched settings” means selected resources were made comparable; it does not mean the systems are identical or that every cost is measured equally. Utilization is not throughput, and throughput is not response-time tail, energy, cost or answer quality.

Agentic workloads also change the state through tools and web interaction, so context length alone does not describe memory traffic.

What a complete evaluation must report

Give context lengths, tool-call traces, batch and arrival conditions, output-quality checks, quantization formats, KV/state placement, buffer sizes, memory bandwidth, NoC (network on chip: the wires and switches that carry messages between blocks)/link contention and compiler/runtime overhead. Report prefill and decode separately, because their arithmetic and state movement differ.

Measure throughput, time to first token, time per token, tail latency, peak memory, bytes moved, utilization, energy and quality.

Compare against A100 and TPU v6e using matched models, precision, memory capacity, bandwidth assumptions, software effort and output conditions. Validate the cycle-emulated simulator against a lower-level model or prototype and state whether the reported result is a projected accelerator result rather than measured silicon.

What the record establishes and where it stops

The primary preprint abstract establishes a hardware/software design for long-context agentic LLM inference that addresses capacity and bandwidth through quantized compute/memory, flattened attention-capable execution, a custom ISA/compiler and simulated design exploration. It reports bounded simulated utilization and throughput comparisons.

It does not establish fabricated hardware, simulator accuracy, complete energy/area accounting, broad model coverage, production agentic latency or quality preservation. The PLENA record is therefore evidence of a co-design direction, not an independently validated accelerator result.

MTIA 300: training throughput depends on the communication path as well as the matrix engines

Why recommendation training becomes communication-bound

Large recommendation models contain embedding tables that map identifiers to learned vectors. A training step may access different rows on different accelerators, so the system must exchange embeddings, gradients or updates.

Hybrid parallelism also creates collective operations: AllReduce combines values across devices, AllGather distributes values, and AllToAll redistributes different pieces to different devices.

These transfers compete with computation when the same GPU (a chip with thousands of small arithmetic units, first built for graphics) resources, memory interfaces or software launch path handle both. A faster matrix multiplication does not solve a link or synchronization bottleneck.

The relevant training time is the sequence of compute, communication, dependency waiting and overlap, not the isolated bandwidth of one interface.

What MTIA 300 changes

The paper co-designs compute, network chiplets, 12 800-Gbps RDMA NICs, 16 message engines, near-memory collective reduction and the HCCL communication library. The message engines can execute communication operations without expressing every collective as a normal compute-grid kernel.

Near-memory reduction combines data close to where it is stored, reducing some movement before the result crosses the wider system.

Collectives are compiled into autonomous dependency graphs. The graph records which communication and compute actions can start, which data they depend on and when a result is ready.

This can reduce launch and synchronization overhead, but it does not remove the dependency or link capacity limits. Small messages, uneven traffic, unsupported datatypes, eager setup and poor overlap can still make a specialized path less effective.

What the paper actually compares

The manuscript evaluates an approximately 150B-parameter DLRM using TorchRec/TorchInductor and distributed Shampoo. The communication comparison uses 40 MTIA 300 accelerators versus 40 H100 accelerators at local batch 6144.

The overlap microbenchmark uses 1,000 TF32 4K×4K×4K GEMMs with collectives across 16 accelerators. These are distinct experiments with distinct denominators.

The extracted evaluation reports 3.9× communication performance relative to H100 for the 40-accelerator DLRM case. Table IV reports normalized Perf/TCO of 1.39 for 40 MTIA 300 at local batch 6144 versus 1.00 for 40 H100, and 1.42 for 24 MTIA 300 at local batch 10240 against the same H100 reference with global batch held constant.

Communication performance is not end-to-end training throughput, and normalized Perf/TCO is not a direct speedup unless its cost and performance definitions are supplied.

What the hardware numbers do and do not say

The extracted Table I gives 1.9 GHz, 216 GB HBM3E, 912 W TDP and 667 W typical power, plus chiplet (a small die that is combined with others in one package) dimensions. TDP and typical platform power are not the same as measured energy per training step.

Chiplet area is not total system area or total cost. A normalized TCO result also requires acquisition, networking, power, cooling, utilization and amortization assumptions.

Evaluate communication-only, overlap, complete training-step time, convergence and cost separately. Report collective size distributions, message counts, link utilization, overlap, idle time, numerical parity, unsupported datatypes and the performance/quality effect of changing batch size.

Reproduce the same TorchRec/TorchInductor workload on both platforms and state whether the Perf/TCO denominator includes the same system components and lifetime.

What the record establishes and where it stops

The primary paper supports a hardware/software co-design in which integrated networking, message engines, near-memory collectives and a communication library target recommendation-training communication. It reports bounded author-evaluated communication and normalized Perf/TCO comparisons with page and table locations.

It does not establish independent replication, universal end-to-end training speedup, measured workload energy, or transferable cost for other model sizes and collectives. The MTIA 300 record is evidence of a concrete training-system design, not a general accelerator ranking.

Dynamic In-Switch Computing for MoE: routing traffic can be reduced only if the switch sees enough token structure to combine useful work

Why MoE routing creates directional traffic

In a mixture-of-experts layer, a router selects several experts for each token. Tokens assigned to the same expert must reach the device that stores or computes that expert.

The dispatch is therefore an all-to-all movement: each source may send tokens to many destinations, and each destination may receive tokens from many sources. The combine phase sends expert outputs back or redistributes them to the tokens' original locations.

The traffic is irregular because token assignments change with the input. Top-k routing also duplicates a token for multiple experts.

A network can have enough total bandwidth and still be limited by directional imbalance, small transfers, routing metadata, synchronization or a destination whose queue fills first.

What in-switch computing is changing

Conventional switches forward packets or collective data. In-switch computing places a permitted operation in the communication path so data can be combined before it travels farther.

The operation must be defined for the data layout, packet order, numerical type and dependency state; otherwise moving the computation into the switch only moves the bottleneck or changes the result.

The record names DySHARP dynamic multimem addressing and token-centric dispatch/computation/combine fusion. Dynamic addressing is intended to follow changing token-to-expert destinations.

Token-centric fusion treats routing, expert computation and output combination as a connected path rather than independent collective calls. The captured evidence does not establish the exact switch operation, buffer behavior, numerical reduction, hardware implementation or how the address is updated.

Why layer and training results must remain separate

A layer-level dispatch result measures movement or execution for one MoE layer under a specified top-k and token distribution. Full training includes many layers, optimizer work, pipeline stages, synchronization, activation/gradient traffic, load imbalance and convergence.

A local reduction can be hidden by another stage or can change the timing of the next dependency.

The card describes DeepSeek-V3-like small, medium and large configurations with top-k 8/16/32. Larger top-k settings are exploratory, and the main evaluation uses a customized Accel-Sim and BookSim2 simulation of a 32-GPU GH200-NVL32-like node with nine switches.

End-to-end training uses 16-way pipeline parallelism across 16 nodes. These conditions define a modeled system, not deployed multi-GPU hardware.

What a complete evaluation must establish

Report token-to-expert distributions, top-k, duplicate-token rate, message sizes, directional link utilization, queue occupancy, switch buffers, address-update cost, combine precision, synchronization and all layer/full-training boundaries. Compare DeepEP, NVLS, FasterMoE, Tutel, CCFuser, COMET and DualPipe under the same models, top-k, batch, pipeline, network and simulator assumptions.

Calibrate the simulator against measured network and GPU behavior. Validate that in-switch operations preserve numerical results and routing semantics. Plot performance against token skew and burstiness, not only an average workload. Report full-training time, throughput, convergence, energy and failure behavior separately from operator-level movement.

What the record establishes and where it stops

The primary preprint supports a proposed dynamic in-switch MoE path combining address adaptation with token-centric dispatch, computation and combine. The captured card deliberately withholds numerical headline results pending figure and condition reconciliation. It records simulation and source conditions, not deployed hardware validation or independent reproduction.

The Dynamic In-Switch Computing record is therefore evidence of a network/compute co-design direction. The detailed explanation above separates routing imbalance from total bandwidth, switch computation from forwarding, layer results from training results, and simulation from hardware.

Patterns Behind Chaos: expert placement is a data-movement decision before it is a compute decision

Why expert routing moves so much data

An MoE inference request produces tokens that a router assigns to experts. When experts are distributed across GPUs or wafer-scale regions, each assigned token or activation must travel to the location of its expert and the result must return to the next model stage.

The movement depends on which experts are selected, how many tokens select them, the order in which requests arrive, and the topology connecting the devices.

The router may look random from the perspective of a fixed placement, but it can still have temporal and spatial structure. Temporal structure means that expert choices or traffic patterns persist or change in related ways across successive intervals.

Spatial structure means that the selected experts and their data movement interact with nearby links, memory regions or communication groups. Finding such structure can support placement and prefetch decisions, but a pattern in one trace is not a guarantee for every request.

What the method is profiling and changing

The record describes data-movement-centric temporal and spatial profiling, distilled placement insights, lightweight wafer-scale architectural modifications and a prefill-aware expert-placement algorithm. Profiling measures the routing and movement trace rather than only counting multiply-accumulate operations.

Distilling insights means converting that trace into placement rules or features that a serving system can use.

Placement assigns expert storage or execution locations. A good placement reduces the distance, congestion or repeated transfer cost for likely traffic while preserving capacity and avoiding a new hotspot.

Prefill and decode have different traffic: prefill processes many input tokens and can create a broad batch, while decode produces a smaller number of tokens repeatedly and is more sensitive to per-step movement and synchronization. A placement optimized for one phase can be poor for the other.

What forecasting can and cannot establish

The title frames the work as forecasting data movement, but the captured card does not specify the forecasting model, prediction horizon, error metric or how a wrong forecast is handled. A forecast is useful only if its prediction arrives before the placement or prefetch decision, improves the expected movement cost, and does not consume more time or bandwidth than it saves.

A forecast can also become stale when request mix, model, batch size, expert popularity, topology or system load changes. The serving system needs a refresh period, fallback placement, capacity constraint and a measurement of prediction error.

A lower average transfer count can still increase tail latency if the remaining traffic concentrates on one link or expert.

The preprint evaluates four 200B–1000B MoE models released in 2025, more than 24,000 requests across diverse workloads, wafer-scale GPU architectures and existing GPU systems. It reports 6.6× average speedup on wafer-scale GPUs and up to 1.25× speedup on existing GPU MoE computation.

UniNL: fragmented nonlinear work needs an executable representation and a schedule

Why nonlinear operators can leave a matrix accelerator underused

Large language-model inference contains matrix operations and nonlinear operations. Matrix operations multiply and accumulate many values with regular shapes, so an accelerator can organize them across a processing-element array.

A nonlinear operator applies a function or transformation that may have different arithmetic, memory and control requirements. If the array is built mainly for matrix work, the nonlinear part can leave processing elements idle or require a separate execution path.

This is a hardware/software boundary problem. The hardware must expose a way to perform the nonlinear work, while software must express the model's operator sequence in a form that uses that hardware.

If the two descriptions do not match, the accelerator may spend time moving intermediate values, starting small kernels or waiting between matrix and nonlinear stages.

What UniNL's mechanism is intended to do

The captured record describes four connected choices: decomposing nonlinear operators into primitives, approximating some functions with polynomials, adding lightweight microarchitectural support, and fusing primitives with matrix execution. A primitive is a smaller operation with a defined input/output contract.

Decomposition can expose common pieces to hardware; polynomial approximation can replace an expensive function with additions and multiplications; support can provide the needed operations; fusion can reduce intermediate storage and scheduling boundaries.

Each choice adds a condition. Approximation changes numerical results and needs an error bound or task-quality evaluation.

Decomposition can increase the number of intermediate values. Fusion is useful only when dependencies, memory lifetime and resource availability permit overlap.

Lightweight hardware still consumes area, control state and verification effort. A faster nonlinear kernel is not automatically a faster LLM if matrix work, data movement or unsupported operators dominate.

What utilization and energy claims must include

Processing-element utilization is the fraction of available compute capacity doing useful work under a stated workload and time boundary. Raising it can improve throughput, but utilization alone does not define output quality, latency or energy.

A fused schedule may keep arithmetic units busy while increasing buffering or causing contention with matrix operations.

The record reports 6.89× speedup and 7.26× energy-efficiency improvement over Jetson AGX Orin, plus 1.46× and 1.35× performance over state-of-the-art nonlinear-operator accelerator designs. These ratios therefore remain source-reported comparisons, not transferable end-to-end LLM results.

Moderately unstructured sparse GPU inference: fewer stored weights still require a usable execution path

What sparsity changes

An LLM weight matrix contains numeric values used in matrix multiplication. Sparsity sets some values to zero or removes them from storage.

If the zeros are known and skipped, the system can reduce stored data and arithmetic. Unstructured sparsity does not place the remaining values in a simple fixed pattern, so the hardware also needs metadata describing where each value belongs.

At roughly half sparsity, a dense GPU can still be faster if the sparse representation requires irregular address calculation, metadata reads, decoding, synchronization or poorly filled execution units. The relevant comparison is not only the number of nonzero values.

It is the cost of finding them, moving them, multiplying them and assembling the output.

What the three-layer format and hybrid kernel are doing

The record describes a three-layer sparse storage format and a hybrid SpMM kernel using sparse tensor cores and CUDA cores, with compressed on-chip decoding and residual correction. The storage format determines how nonzeros and their locations are represented.

Decoding reconstructs the operands needed by the compute units. Tensor cores and CUDA cores provide different execution paths, so the kernel must decide which work is assigned to each and how their partial results are combined.

Residual correction indicates that the main sparse path does not necessarily represent or execute every contribution in the same way. The correction path must preserve numerical behavior within the required model-quality tolerance.

Its storage, arithmetic and synchronization cost belongs in the result; it cannot be treated as free because the main matrix is sparse.

Kernel speedup and inference speedup answer different questions

Kernel-level speedup measures one matrix operation under a specified shape, sparsity pattern, precision and launch condition. End-to-end inference includes weight loading, other model layers, activation movement, kernel launches, synchronization, sampling or decoding, and any host/runtime work.

A 1.64× kernel improvement and a 1.41× end-to-end improvement are not contradictory; they have different denominators and boundaries.

The captured description reports up to 1.64× kernel-level speedup over SpInfer and up to 1.41× end-to-end speedup over FlashLLM. “Up to” identifies a best reported condition, not an average across all models or inputs.

The source does not specify GPU models, sparsity distribution, accuracy, batch or sequence settings, memory traffic or baseline tuning, so the values cannot be generalized to all moderately sparse LLM inference.

PiMM-NoC: mapping an AI model means assigning computation, storage and communication together

What process-in-memristor memory changes

In a conventional accelerator, weights are stored in memory and moved to compute units. Process-in-memristor-memory places computation near or inside a memristor-based storage structure, often using the physical behavior of the array to perform weighted operations.

The result still needs peripheral circuits to drive inputs, sense outputs, convert signals and communicate with other units.

The location of the multiplication does not remove the rest of the computation. Precision, device variation, analog-to-digital and digital-to-analog conversion, accumulation, buffering, programming, calibration and data movement can determine the actual latency, area and energy.

A mapping that looks efficient at the array level can be poor after peripheral and network costs are included.

What the PiMM-NoC architecture is organizing

The record describes heterogeneous tiles containing weight-stationary and general processing units connected by a network-on-chip. A weight-stationary unit keeps model weights near the computation; a general unit can handle work that does not fit the specialized array.

The NoC carries activations, partial results, control or other data between tiles.

Mapping assigns model operations and tensors to those tiles and decides when values move. A good mapping must respect capacity, operation compatibility, data dependencies, link bandwidth, buffer occupancy and timing.

It is not only a placement problem: an assignment that reduces compute can create a communication bottleneck, and an assignment that reduces movement can exceed a tile's storage or force expensive conversion.

What RL and MCTS are searching

The captured record couples reinforcement learning and Monte Carlo tree search with cycle-accurate architecture simulation. The search proposes mapping decisions, receives an objective from simulated execution, and explores alternatives.

The objective might combine latency, throughput, energy or another cost, but the source does not specify the reward, constraints, search budget or whether the simulator includes device nonidealities and peripherals.

Simulation-guided search can find a good mapping for the modeled hardware and workload. It does not prove that the mapping is good on a fabricated device or on a model whose shapes, precision and communication pattern differ from the search set.

Search results are also sensitive to the candidate space, starting policy, reward weighting and stopping rule. A large improvement against a weak or differently normalized baseline is not a general hardware claim.

Squat: make sub-8-bit quantization executable on ordinary edge SIMD

The deployment problem is a joint numerical and instruction-format problem

Quantization replaces a value represented with more bits by a value represented with fewer bits. This can reduce storage and the amount of data moved, but it also changes the numerical values used by matrix multiplication.

Quantization-aware training (QAT) inserts that reduced-precision behavior into training so the model can adjust to its own error.

Squat addresses a specific deployment boundary. Many fine-grained methods assign separate scales to channels or tokens.

That can preserve accuracy, but a commodity mobile SIMD kernel may not have an instruction path that consumes those many scales efficiently. A method can therefore produce a compact numerical representation that is awkward for the target processor.

Squat combines three choices: QAT losses aimed at attention distortion, token-adaptive 4/8-bit activation precision, and a SIMD multi-kernel mixed-precision multiplier (MKMP).

The contribution is not “4-bit is always better.” It is a co-design claim: the precision policy, the information used to choose precision, and the arithmetic kernel must describe the same executable format. The reported latency is meaningful only together with the model, bit arrangement, sequence length, processor, number of iterations and output-quality result.

Why query and key quantization matter

Self-attention forms query and key vectors and uses their products to determine how strongly one token attends to another. If their distributions change, the attention scores can change even when the rest of the model is unchanged.

Squat's analysis quantizes different portions of LLaMA-58M separately and reports that quantizing query and key accounts for most of the drop observed when the full attention module is quantized.

The paper links this loss to two observable differences. First, the quantized query and key distributions can have different variance from the FP16 versions.

Second, the attention map's distinctive first-token column can weaken or disappear. The authors treat the first token as an importance reference because autoregressive attention exposes it to later tokens and its attention column is a measurable signal associated with the information carried by each token.

This gives the method a concrete optimization target. It is not enough to minimize an average weight error if the error changes the attention structure that the model uses. The evaluation must therefore include task quality, attention-related ablations and the target inference cost.

The training losses preserve two different properties

The FP16 model supplies the reference behavior. The quantized student is trained with soft distillation: cross-entropy with the task labels is combined with a KL-divergence term comparing the student's soft outputs with the teacher's outputs.

Squat adds an entropy loss to the query and key representations and a distribution loss comparing quantized and FP16 attention maps by cosine similarity.

The entropy term is based on the paper's Gaussian approximation. For a Gaussian variable, entropy increases with the logarithm of variance.

Squat uses this relationship to encourage quantized query and key representations to retain distributional spread. This is a training regularizer, not a direct guarantee that every attention probability is preserved.

The distribution term compares the direction of the quantized attention map with the FP16 map. Two maps can have high cosine similarity while differing in magnitude, and a high similarity on an average can hide a few important heads or positions.

The paper sets the entropy-loss ratio to 0.5 and distribution-loss ratio to 1 in its reported experiments. The losses address different failure modes: one targets representation distribution, the other targets the attention pattern.

Token-adaptive precision makes the average bit count conditional

Squat assigns 8 bits to tokens ranked important and 4 bits to the remainder. Importance is computed from each token's average attention to the initial token across heads. If rho is the selected important-token ratio, the top rho × N tokens receive 8-bit treatment and the rest receive 4-bit treatment. This is a runtime policy based on the current attention map, not a fixed per-layer precision.

The distinction matters when reading “W4A4” and mixed configurations. W4A4 means a uniform 4-bit weight/activation setting in the table; mixed 4:8 columns mean 4-bit and 8-bit activation groups at stated ratios.

The arithmetic workload and memory format are not the same. A mixed policy can preserve more information for selected tokens while reducing average work, but the selector, sorting, grouping and later reconstruction have costs.

The implementation uses a token-control module, concatenates tokens by precision, and uses heapsort for top-k selection. The paper calls those overheads marginal for its setup; a complete transfer claim would need to measure them across sequence lengths and processors.

Token importance also depends on the current attention computation, so the policy must be evaluated in the actual autoregressive execution path rather than only on a static calibration sample.

The MKMP kernel closes the representation-to-instruction gap

Standard mobile SIMD paths commonly operate at byte granularity. If 4-bit operands are merely zero-extended into 8-bit lanes, the model stores fewer bits but may not perform fewer useful operations.

Squat's MKMP path packs two 4-bit operands into a 16-bit unit, performs the multiplication using the available SIMD structure, and separates the intermediate results for accumulation. The paper states that its INT4 multiplier can use about half the hardware resources of the INT8 multiplier in its design and that the theoretical 4-bit computation can reduce multiplication and addition work by half relative to byte-expanded execution.

The hardware claim has a precise boundary. It concerns the kernel's operation and resource structure; it does not automatically imply half the end-to-end latency.

Bit shifts, result recovery, memory reads, token sorting, thread scheduling and unsupported operations can consume the saved arithmetic capacity. The paper reports compiler-level overlap of memory reads and computation as part of the deployment path, so the measured result includes more than the multiplier alone.

Read quality and latency as separate axes

The paper evaluates LLaMA-58M and GPT2-97M. For zero-shot BLiMP, its LLaMA-58M average is 74.0 for FP16, 74.0 for W4A8 and 67.8 for W4A4; the corresponding W4A8 and W4A4 values for the baselines differ.

For GPT2-97M W4A4 on BLiMP Main, the paper reports average 69.2 for Squat, versus 69.9 FP16, 49.4 NIPQ, 59.7 PACT and 69.1 LLM-QAT. On LLaMA-58M W4A4 across the listed (Super)GLUE tasks, the averages are 68.6 for Squat and 71.0 for FP16.

These averages do not mean every subtask improves; the tables contain both gains and regressions.

For latency at sequence length 128, the table reports LLaMA-58M FP16 at 4.54 ms/token on the OnePlus 11 and 15.63 ms/token on Raspberry Pi 5; its uniform W4A4 values are 2.02 and 6.78 ms/token. GPT2-97M reports 6.22 and 23.04 ms/token for FP16, and 2.75 and 9.74 ms/token for uniform W4A4.

The mixed columns are distinct configurations: on GPT2 mobile, the 4:8 ratios 1:3 and 1:1 show 3.06 and 3.02 ms/token; on Raspberry Pi they show 11.24 and 10.98 ms/token.

The paper's displayed speedup labels contain an evidence issue. For GPT2 mobile, dividing the displayed FP16 latency 6.22 by 3.06 gives 2.03, while the table labels that cell 2.06; dividing 6.22 by 3.02 gives 2.06, while the label is 2.03.

The saved assessment classifies these two cells as incompatible under the stated rounding assumption and preserves the published values rather than silently swapping them. A third strict mismatch can be compatible with unshown rounding.

The arithmetic check is a correction lead, not an independent latency reproduction.

What the paper establishes and what it does not

The manuscript supports a bounded claim: on the selected small models, tasks, QAT baselines, processors and 1,000-iteration latency procedure, Squat combines attention-aware training, token-adaptive 4/8-bit activation precision and a compatible mixed-precision SIMD kernel to improve the reported accuracy/latency tradeoff. It does not establish the same tradeoff for larger models, other processors, different sequence lengths, other token-importance distributions or a production runtime.

The experiments use a OnePlus 11 with Snapdragon 8 Gen 2 and a Raspberry Pi 5 with BCM2712 quad-core Arm Cortex-A76, using all available cores. The paper reports 1,000 iterations, but warmup, thermal controls and the exact prefill/decode boundary remain conditions to verify.

The training-feasibility motivation does not establish that training was performed on-device. The code is publicly linked, but no execution or independent reproduction was performed here.

The long-term research question is whether quantization methods should be judged by numerical accuracy alone or by a complete executable contract: scale granularity, token-selection overhead, supported SIMD instruction format, memory traffic, model quality and measured latency under a controlled runtime protocol. Squat makes that contract explicit for one edge setting; its headline speedup must not be separated from the quality tables and the unresolved table arithmetic.
