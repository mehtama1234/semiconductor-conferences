The bigger theme this belongs to

A model needs a process that manages its execution

A trained language model specifies a computation, but a running system must load its parameters, allocate memory, schedule operations, and manage requests or training steps. Runtime software performs decisions during execution rather than fixing every choice in advance.

Training, fine-tuning, and inference create different requirements. Training updates model parameters. Fine-tuning adapts an existing model using further training. Inference executes a trained model to produce outputs. A result for one phase does not automatically establish an improvement in another.

Look at complete work and its dependencies

Execution consists of operations that read and produce values. Some operations can run together; others must wait for earlier outputs. Hardware can be idle because inputs are unavailable, memory is full, or another activity owns a shared resource.

A runtime changes when work happens and where its state resides. It can reduce idle time or memory use while adding scheduling, transfer, or bookkeeping costs. The evaluation must include the work moved elsewhere rather than measuring only the accelerated portion.

Single-GPU fine-tuning can still use other resources

The heterogeneous fine-tuning record proposes coordinated algorithm and hardware choices around one GPU. “Single GPU” specifies the number of those accelerators; it does not establish the total CPU, memory, storage, or communication resources used. Recorded evidence

Moving state or computation away from the GPU can make a larger task possible but also add transfers. The meaningful comparison includes time to achieve the required model quality, all resource consumption, and the conditions of the comparison method.

The captured description leaves those quantities unresolved.

Fine-tuning changes model parameters using examples. A training step usually reads parameters, computes activations, stores or recomputes intermediate values, computes gradients, and updates parameters.

Depending on the optimizer, the system may also keep optimizer states such as momentum or second-moment estimates. These objects can consume more memory than the model weights alone.

A “single-GPU” method may therefore place some state in CPU memory, another device, storage, or a custom processing path while retaining one GPU for the main computation.

The first design question is which state moves across which boundary. In a single GPU system, moving a layer’s weights before every use has a different cost from moving optimizer states once per update or checkpointing activations for later recomputation.

The evaluation should identify the bytes transferred, transfer direction, frequency, link bandwidth, overlap with computation, synchronization points, pinned-memory or storage requirements, and whether page faults or allocation overhead are included. A method can fit the model in nominal capacity while failing to meet useful throughput because transfers serialize the critical path.

Algorithm and hardware co-design can also change the amount of work, not merely where it runs. Parameter-efficient fine-tuning may update adapters or low-rank components instead of all weights.

Quantization, activation recomputation, optimizer changes, layer scheduling, microbatching and offload policy can each alter memory and computation. A comparison must state which of these changes are part of the proposed method and whether the baseline reaches the same final quality with the same trainable parameter set.

Memory capacity is not the same as trainable-task feasibility. The method must preserve the optimizer state, gradient precision, numerical stability, checkpoint/restart state, data pipeline and validation behavior required by the training objective.

If some tensors are compressed or recomputed, report the numerical effect and the extra computation. If state is evicted to host memory, report CPU contention and memory pressure.

If storage is used, report I/O bandwidth, endurance assumptions and failure behavior.

The correct performance denominator is time-to-quality, not only tokens per second or one kernel’s latency. Define the target loss, evaluation metric, dataset, number of epochs or update steps, convergence rule, random seeds and acceptable quality variance.

A method that processes tokens faster but converges more slowly, or reaches a lower final quality, has not shown a training improvement. Report preparation, loading, transfers, validation, checkpointing, failures and recovery when they are required for a fair run.

The baselines should include standard single-GPU fine-tuning using the same model and quality target, a named multi-GPU configuration, and relevant offload or parameter-efficient methods. “Multi-GPU” is not automatically a fair lower-bound comparison: it may use a different parallelism strategy, memory capacity, interconnect, batch size or quality target.

Report GPU memory, host memory, storage, CPU utilization, interconnect traffic, total energy, wall-clock time, throughput, time-to-quality and cost per completed run.

The captured description supports a heterogeneous algorithm-hardware direction for making large-model fine-tuning possible around one GPU. It does not specify models, datasets, parameter-efficient versus full fine-tuning, quality criteria, GPU/interconnect, time-to-quality, memory, throughput, energy or accuracy.

The evidence supports a capacity-and-runtime co-design direction, not demonstrated single-GPU training efficiency across model families.

Hero: mobile RAG orchestration must preserve retrieval and answer quality while respecting device limits

Retrieval-augmented generation (RAG) combines two stages. In a retrieval-augmented generation pipeline, a retriever selects documents or passages from an index using a query.

A generator uses the query and retrieved context to produce an answer. The system can improve factual grounding, but retrieval errors and generation errors are different.

A runtime that reduces latency by retrieving fewer or less relevant passages may lower answer quality even if the language model runs faster.

Hero is described as adaptive orchestration across a heterogeneous mobile system-on-chip (SoC). A mobile SoC may contain CPU, GPU and NPU resources with different throughput, memory access, power, thermal and software characteristics.

The orchestration policy may decide where retrieval, embedding, reranking, prompt construction and generation run, how data moves between memories, and when to use local or cloud resources. Each decision changes both performance and the evidence available for judging the answer.

The first requirement is to define the query path. Record query encoding, index access, candidate count, reranking, context length, prompt assembly, generation model, output length, cache state, and any network round trip.

Report retrieval recall or precision, context relevance, answer correctness, citation or grounding quality, refusal behavior, and hallucination or unsupported-answer rate separately from latency. End-to-end answer quality cannot be inferred from retrieval speed or token throughput alone.

Adaptive placement needs an observable state and a decision cost. The policy may use query length, expected retrieval difficulty, model confidence, battery level, temperature, queue state, memory pressure, network quality or historical workload.

It must state how these signals are measured, how often the policy changes placement, and how much computation and data movement the decision adds. A policy trained or tuned on one query distribution may choose poorly for a different language, topic, index size, user mix or connectivity condition.

Heterogeneous execution has multiple boundaries. Moving an embedding or retrieved context between CPU, GPU, NPU and shared memory consumes bandwidth and may require format conversion or synchronization.

Sending a query or context to the cloud adds network latency, energy, privacy exposure and availability dependence. A local-versus-cloud comparison must use the same quality target, privacy policy, network condition, model version and output length; cloud latency alone is not a complete baseline.

Mobile constraints are dynamic. Battery state, thermal throttling, background applications, memory pressure and user-visible latency can change during one session.

Report cold and warm cache behavior, sustained execution, thermal steady state, battery energy, peak and average power, memory footprint, throttling, queueing, first-token latency, total response latency and tail percentiles. An average speedup under a short benchmark does not establish sustained mobile efficiency.

The comparison should include static local placement, a fixed heterogeneous placement, cloud RAG, and the adaptive policy. Hold the index, retriever, generator, prompt, output quality, context limit, quantization and query set constant.

Use workload splits that hold out queries, topics, index updates, devices and network states. Report policy errors: cases where the chosen placement misses a quality target, exceeds a latency service-level objective, or consumes more energy than the available budget.

The captured description identifies adaptive RAG orchestration on a heterogeneous mobile SoC, but reports no answer quality, retrieval quality, latency, energy, memory, thermal or workload-diverse results. Adaptive choices may depend on query distribution.

The evidence supports a mobile RAG runtime direction, not demonstrated quality-preserving orchestration across devices and workloads.

Sandwich: hot-switching can adapt CPU serving only if switch cost and tail behavior remain inside the service objective

CPU LLM serving is a sequence of requests competing for cores, memory bandwidth, caches, power and thermal headroom. A serving configuration may include thread count, core affinity, vectorization, batch size, quantization, kernel choice, frequency policy, context handling, KV-cache policy and request admission.

A configuration that is best for one request mix can be poor for another because long prompts, short prompts, concurrent requests and output lengths stress different resources.

Sandwich is described as joint configuration search and runtime hot-switching. Configuration search chooses candidate settings and measures or predicts their behavior.

Hot-switching changes the active setting while the service is running. These are separate mechanisms.

Offline search can find a good configuration under its training workload; runtime switching must decide when the workload has changed enough to justify a switch and must pay the cost of changing state.

The switching path must be defined. A change may drain requests, alter thread placement, rebuild kernels, resize a batch, invalidate or reduce cache locality, change KV-cache layout, adjust frequency, or wait for an in-flight operation.

Measure switch duration, requests stalled, tokens lost, cache warm-up, queue growth, temporary memory, frequency transition and the configuration’s first-request behavior. A lower steady-state latency does not compensate for repeated switch penalties unless the workload intervals are long enough.

Serving quality is usually expressed through service-level objectives (SLOs), not only average throughput. Define time to first token, inter-token latency, total response latency, deadline violation, throughput, admission behavior and tail percentiles such as p95 or p99.

A configuration that improves average tokens per second while creating deadline misses or long pauses during switching may be worse for the service. Report quality or output-equivalence changes from quantization, batching, truncation and other configuration choices separately from runtime metrics.

Joint search also has an exploration cost. Testing configurations consumes requests, warm-up time, CPU cycles and possibly user-visible capacity.

The search should state whether it uses an offline trace, a simulator, a model, safe canary traffic or live exploration. If it learns from observed workload, separate search requests from production requests and report how quickly it adapts, how often it selects a poor configuration, and what prevents oscillation between configurations.

The workload must include changing conditions: request arrival rate, prompt length, generated length, concurrency, model, quantization, cache state, background CPU activity, thermal state and power limit. Configuration quality can be workload-specific.

A policy trained on a stable trace may fail under a burst or a mixture of long and short requests. Evaluate held-out traces and workload transitions, not only stationary averages.

The baselines should include a static configuration selected offline, the best fixed configuration for each known workload, and offline tuning without runtime switching. Compare equal model quality, request distribution, CPU platform, thread/core budget, memory limit, frequency policy, warm-up, cache state and measurement boundary.

Report switch frequency, switch cost, SLO attainment, tail latency, throughput, energy, CPU utilization, memory, configuration-search time and quality.

The captured record identifies joint configuration search and runtime hot-switching for CPU LLM serving, but reports no latency, throughput, quality, switch time, energy or workload results. Switching may disrupt cache state and tail latency.

The evidence supports an adaptive CPU-serving direction, not demonstrated SLO-safe hot-switching across models and workload changes.

PREBA: multi-instance GPU serving must control interference, memory pressure and tail latency across tenants

Multi-instance GPU inference means that more than one inference workload uses one physical GPU at the same time. The instances may receive separate partitions, streams, memory regions, scheduling shares or combinations of these.

The physical GPU still has shared resources: execution units, on-chip caches, memory bandwidth, memory capacity, copy engines, power, thermal headroom, driver state and sometimes scheduling queues. A tenant can therefore affect another tenant even when the software presents the instances as separate services.

PREBA is described as hardware/software co-design for multi-instance GPU-based AI inference servers. “Co-design” should identify the hardware mechanism, the software policy, the control loop between them, and the resource that each mechanism changes.

A hardware partition, a memory controller, a request scheduler, a model-placement policy and a batching policy solve different problems. Combining them in one system does not by itself show that their interaction is necessary or that the combined design is better than well-tuned software on the same GPU.

The first system question is the isolation boundary. State whether an instance receives a fixed slice of compute, memory, cache, bandwidth, power or time; whether it can borrow unused capacity; and what happens when it exceeds its allocation.

A logical partition is not the same as performance isolation. If two instances share memory bandwidth or cache, measure how one tenant's request rate, model, sequence length or batch size changes the other's latency.

If the design claims security or fault isolation, define the information or failure channel and test it separately from performance interference.

Inference serving has more than one resource demand. A request may need model weights, activations, key-value cache, temporary workspace, input processing, output sampling and host-device transfers.

Large or long-context requests can consume memory for a long time. Admission control must say whether a request is rejected, queued, preempted, migrated or allowed to cause eviction when the memory budget is full.

A throughput result without memory occupancy and request-level behavior can hide failures caused by cache growth or allocation stalls.

The serving objective must be stated per tenant and for the system as a whole. Measure time to first token, inter-token latency, complete response latency, throughput, queueing delay, deadline or service-level-objective violations, and p95/p99 or worse tail percentiles.

Report each tenant's result, not only the aggregate. A policy that raises total throughput by starving a small tenant, or that improves the mean while producing long pauses for one model, is not a fair multi-instance result.

Define fairness explicitly, such as minimum guaranteed throughput, weighted service share, slowdown relative to isolation, or a bounded latency increase.

Scheduling decisions also have costs. The policy may choose instance size, core share, memory placement, batch formation, request order, preemption, model migration, precision, clock state or power allocation.

Each decision can require synchronization, context changes, kernel completion, cache effects, data movement or model reload. Measure decision frequency, reconfiguration time, work lost, queue growth, memory fragmentation, warm-up and the effect on in-flight requests.

A hardware/software policy that is effective only after long stable intervals may not handle bursty tenants; a policy that changes too often may spend its gain on control overhead.

The workload must represent the sharing problem. Include multiple models, model sizes, input and output lengths, batch sizes, arrival rates, concurrency, burst patterns, memory footprints, accelerator kernels and tenant priorities.

Evaluate balanced tenants, a heavy tenant beside light tenants, synchronized bursts, long-context requests, changing mixes and failures or restarts. A single model at a fixed rate tests GPU execution, not multi-tenant interference.

If the method targets a particular GPU-generation feature, state the supported partition sizes, driver/runtime versions and portability boundary.

Energy and cost need the same boundary as performance. Report total server energy, energy per request or token, power limit, clock state, cooling or thermal condition, host CPU and memory use, and the cost of reserved versus borrowed capacity.

A design can improve GPU utilization while increasing host work, memory traffic, cooling demand or failed requests. Compare the same model quality, precision, output length, request mix, admission policy and end-to-end measurement boundary.

The baselines should include one instance per GPU, conventional multi-instance GPU partitioning, and default multi-instance scheduling. Add an oracle or offline allocation when possible to show the gap between the policy and a workload-specific upper bound.

Hold the physical GPU, driver, model versions, quantization, request traces, tenant priorities, memory limit, power limit, warm-up, cache state and quality target constant. Report an ablation for hardware changes and for software policy so the source of each gain is visible.

The captured record identifies hardware/software co-design for multi-instance GPU inference and qualitatively claims server efficiency. It reports no GPU generation, partition mechanism, tenant mix, tail latency, throughput, fairness, energy, isolation, memory behavior or workload-diverse result.

The evidence supports a multi-tenant GPU serving direction, not demonstrated QoS-safe, fair or portable inference-server efficiency.

Deinfer: decomposed-model parallelism is useful only when dependency and communication costs stay below the saved inference time

A decomposed language model is a model whose computation or parameters have been split into parts that can be placed or executed separately. Decomposition can expose parallel work, allow a model larger than one device, or map different components to different resources.

It also creates boundaries. Values must cross those boundaries, workers must synchronize, and the system must preserve the order and numerical meaning required by the model.

Deinfer is described as an inference system for parallel inference of decomposed large language models, with multiple optimizations intended to improve performance and remain compatible with other inference optimizations. The description does not identify the decomposition.

It could separate layers, tensor dimensions, experts, attention and feed-forward parts, pipeline stages, or another model representation. Those choices have different dependency graphs, communication volumes, memory needs and failure behavior, so the system must state the exact graph and placement before its speed claim can be interpreted.

The first principle is to expose the critical path. For each generated token or batch, identify which operations can run concurrently, which values they read, which values they produce, and which operations must wait.

Measure compute time, communication time, synchronization time, queueing, scheduling overhead, memory movement, kernel launch or runtime overhead, and idle time at every device. Parallelism helps only when useful work overlaps and the saved computation is greater than the cost of moving data and coordinating workers.

Autoregressive generation makes this especially important. A new token often depends on the state produced for the previous token.

Some work can be batched across requests or split across model components, but a fine-grained cross-device boundary may add a synchronization to every token. Report prefill and decode separately, because long prompt processing and one-token-at-a-time generation stress the system differently.

Include time to first token, inter-token latency, complete response latency, throughput, batch/concurrency and tail percentiles.

Communication must be described in bytes and timing, not only as an implementation detail. State what crosses each boundary: activations, weights, key-value cache, logits, metadata or control messages.

Report message size, frequency, direction, link, bandwidth, latency, serialization, overlap with compute, synchronization points and copies through host memory. A topology that works for a large batch may fail for small requests if fixed message latency dominates.

A method that fits model weights across devices may still be limited by activation or KV-cache traffic during decoding.

Compatibility with existing optimizations is a claim that needs a defined composition. Quantization changes bytes and numerical error.

Batching changes available parallel work and queueing. Kernel fusion changes boundaries.

Speculative decoding changes the number of tokens proposed and verified. Caching changes reuse and memory occupancy.

The evaluation should show whether each optimization is applied before or after decomposition, whether it changes the dependency graph, and whether the proposed scheduler still preserves output quality and acceptance behavior.

Model quality must remain comparable. Parallel execution should produce the same result within a stated numerical tolerance, or the paper must report the quality change from quantization, approximation, partitioning, or reordered operations.

Compare perplexity or task accuracy for the same model and decoding rule, and report output differences if floating-point order changes. A faster system that silently changes the model or stopping rule is not an isolated systems improvement.

The baselines should include monolithic inference on the largest feasible device, sequential execution of the same decomposition, and a standard distributed or tensor/pipeline-parallel implementation when applicable. Hold model weights, decomposition, precision, prompt/output lengths, decoding parameters, batch, concurrency, warm-up, cache state, device count, interconnect and end-to-end timing boundary constant.

Include a scaling study as devices increase and an ablation of communication overlap, scheduling, memory placement and other claimed optimizations.

Small requests and low concurrency are a critical boundary condition. Their compute is short, so fixed coordination and transfer costs can dominate.

Large batches may hide those costs while increasing queueing and latency. Evaluate short and long prompts, short and long generations, low and high concurrency, balanced and imbalanced partitions, cold and warm state, and changing request mixes.

Report scaling efficiency, device utilization, communication fraction, memory use, energy per token or response and cost per completed request.

The captured record says that DeInfer targets parallel inference of decomposed LLMs and claims extensive experiments, but the captured evidence reports no model decomposition, device topology, quality, latency, throughput, communication, energy or scaling result. Decomposition overhead may dominate small requests.

The evidence supports a distributed LLM inference-system direction, not demonstrated efficient and quality-preserving parallel inference across model sizes, request regimes and hardware topologies.

SmoothSpec: speculative decoding gains throughput only when draft quality, verification work and asymmetric resource allocation are measured together

Autoregressive language-model decoding normally generates one next token, appends it to the sequence, and repeats. Speculative decoding adds a draft model or draft procedure.

The draft proposes several tokens; a target model verifies them in parallel; accepted tokens advance the sequence and rejected tokens require a correction. The method can reduce the number of expensive target-model steps, but its benefit depends on how many proposed tokens are accepted and how much draft and verification work is added.

The paper record describes SmoothSpec as an intra-device parallel speculative-decoding system. It uses the same parallelism configurations for draft and target models, allocates compute asymmetrically at runtime, and adjusts draft parameters and the resource-allocation ratio using draft-token generation quality.

These are separate mechanisms: the draft parameter policy changes proposal quality and cost; the resource policy changes contention between draft and target work; the scheduler decides when and how those choices change. A fair reading must measure each mechanism and their interaction.

The basic accounting is accepted useful tokens per unit of end-to-end time. Let the draft produce a proposal, let the target verify it, and count accepted tokens plus the corrected token that advances generation under the exact algorithm.

Report proposal length, acceptance rate by position, rejected-token frequency, target evaluations, draft evaluations, generated tokens, and time for draft, verification, synchronization, scheduling and output handling. A higher acceptance rate is not sufficient if the draft becomes expensive or if target verification occupies the device while the draft is being prepared.

Intra-device parallelism means the draft and target share one accelerator's compute units, memory system, caches, queues, power and thermal limit. Asymmetric allocation can improve overlap, but changing the ratio can also create starvation, preemption, cache disruption or memory pressure.

Define the allocation unit, whether resources are partitioned or time-shared, how in-flight kernels are handled, and the cost and frequency of changing the ratio. Measure achieved utilization for each model, contention, memory traffic, queueing, clock state and reconfiguration overhead rather than inferring utilization from an allocation percentage.

The control signal needs a precise definition. “Generation quality of draft tokens” could mean acceptance probability, accepted-prefix length, target-model score, confidence, entropy, a learned predictor or a recent moving average.

State the observation window, warm-up, decision interval, parameters changed, exploration rule, hysteresis and protection against oscillation. A controller trained on one model or request mix may react too slowly to bursts or overreact to noise.

Evaluate transitions between low and high acceptance, changing prompt domains, concurrency and request lengths.

Quality and speed are coupled. Draft parameters may change sampling temperature, number of draft steps, vocabulary filtering, quantization, layer usage or another approximation.

The target verification algorithm must preserve the intended output distribution if exact speculative decoding is claimed. If the system changes the distribution, compare perplexity, task quality, output agreement, acceptance behavior and stopping semantics under the same decoding settings.

Do not treat accepted-token count as model quality.

Serving evaluation must separate prefill from decode and report time to first token, inter-token latency, total response latency, throughput in useful output tokens per second, p50/p95/p99 tails, batch size, concurrency, queueing and deadline violations. Include cold and warm starts, model loading, memory allocation, KV-cache behavior, output streaming and scheduler overhead.

Throughput improvements at high batch size can coexist with worse interactive latency; both are relevant for a serving claim.

The baselines should include ordinary autoregressive decoding, standard speculative decoding with a fixed draft and fixed resource split, and an oracle or offline resource split when feasible. Hold target model, draft model or draft quality, precision, decoding rule, prompt/output distributions, batch, concurrency, device, clock/power state, warm-up and measurement boundary constant.

Ablate dynamic draft-parameter selection and dynamic resource allocation independently. Report memory, energy per generated token, device generation, software stack and scaling across models or model pairs.

The captured description identifies a single-node system that dynamically adjusts draft parameters and the resource allocation ratio, but the stored evidence reports no acceptance rate, latency, throughput, memory, energy or model result. Parallelism may be device-generation specific.

The evidence supports adaptive intra-device speculative decoding, not demonstrated quality-preserving throughput or tail-latency improvement across model pairs and serving workloads.

Amoeba: changing tensor parallelism at runtime requires state migration and SLO-safe reconfiguration

Tensor parallelism splits a model operation across multiple devices. Each device holds or computes part of a tensor, and the devices exchange partial results so that the next operation sees the complete value.

The degree of tensor parallelism is the number of participating devices or partitions. A larger degree can provide more aggregate memory and compute for a large request, but it also adds communication and may reduce the number of independent instances that can run concurrently.

Amoeba is described as a runtime transformation that changes tensor parallelism for running LLM inference instances as incoming request context lengths change. The underlying tension is concrete: long-context requests need memory for a growing key-value (KV) cache and may benefit from more parallel resources; short-context requests may use fewer resources and allow more concurrent instances.

Changing the layout while a service is running is not the same as selecting a layout at startup. The system must preserve model state, request state and numerical correctness while moving from one execution arrangement to another.

The transformation protocol is the central artifact. State whether the system drains requests, pauses them, migrates them at a safe boundary, or transforms an active instance in place.

Identify what moves: model weights, activations, KV-cache blocks, scheduler metadata, sequence position, requests, communication groups and allocator state. Report bytes moved, links used, synchronization, temporary capacity, memory fragmentation, kernel rebuilding, cache warm-up, failed or retried requests, and the time during which the instance cannot make progress.

A higher-throughput steady state does not justify a policy if repeated transformations create queueing or deadline violations.

KV-cache behavior needs separate accounting. During autoregressive generation, the cache stores key and value tensors for prior tokens so the model does not recompute the complete prefix.

Its size grows with context length, layers, heads, precision and batch or sequence count. A change in tensor-parallel degree may require repartitioning those tensors, changing their layout, copying them between devices, or temporarily keeping both old and new representations.

Measure cache bytes, partitioning cost, reuse after migration, fragmentation, eviction, recomputation and the effect on time to first token and inter-token latency.

The policy needs an observable state and a decision rule. It may use incoming context length, expected output length, queue length, current KV-cache occupancy, arrival rate, device availability, model size or predicted service-level-objective risk.

Define how far ahead the system predicts, what threshold triggers a change, how it avoids oscillation, and how it behaves when a long request arrives during migration. A request’s context length is not the whole workload: generated length, concurrency, prompt reuse, cache state and other tenants affect the required capacity.

Serving quality must be measured end to end. Report time to first token, inter-token latency, total response latency, throughput, queueing delay and p50/p95/p99 tail latency, with SLO or deadline violations during and after transformation.

Separate prefill from decode and include short-context and long-context requests. Report per-request and aggregate results because a throughput average can hide long pauses for the request being migrated.

Include cold and warm cache behavior, model loading, admission, cancellation, failures and recovery.

The comparison should include static tensor parallelism at each relevant degree, data-parallel serving, and a policy that routes new requests without transforming running instances. The static configurations should be measured on the same model, precision, devices, interconnect, request traces, context/output lengths, concurrency, power state and quality target.

Add an oracle or offline assignment where possible. Report the claimed throughput range only with the exact workloads, baseline, timing boundary and confidence or variation; the captured description states a 1.75×–6.57× throughput improvement over state-of-the-art solutions but does not expose the conditions needed to reproduce or interpret that range.

Resource accounting must include the devices used by idle and active instances, communication traffic, host CPU, memory, storage, energy and cooling or power limits. More tensor-parallel resources per long request can increase single-request capacity while reducing system-wide concurrency.

The objective must say whether it optimizes aggregate throughput, latency, tail SLO attainment, cost, energy, or a constrained combination. Model quality and output behavior must remain constant across transformations.

The captured description supports runtime tensor-parallel transformation for context-varying LLM inference and reports a claimed 1.75×–6.57× throughput range on real-world traces. It does not report migration time, latency, KV-cache movement, quality, energy, SLO behavior or model/device-diverse validation.

The evidence supports adaptive parallelism as a serving direction, not demonstrated SLO-safe reconfiguration or general throughput improvement.

Faster-MoA: reducing agent connections changes both the computation graph and the answer evidence

Mixture-of-Agents (MoA) serving runs several language-model agents and combines their outputs. The agents may propose answers, critique one another, specialize by task, or feed results into later agents.

An all-to-all design allows many agent-to-agent connections, but those connections create communication, scheduling and inference work. A tree structure, early exit and overlapping prefill with decode can reduce work, but each change also changes which agents contribute and when.

Faster-MoA is described as a unified algorithm-system co-design with three parts: a hierarchical tree instead of all-to-all connectivity, runtime early exit based on output semantic similarity and answer confidence, and agent-dependency-aware incremental prefilling that overlaps prefill and decode. These are not interchangeable optimizations.

The tree changes the dependency graph; early exit removes computation and evidence; overlap changes scheduling without necessarily removing model work. The evaluation must isolate them and explain how the resulting system still implements the intended MoA behavior.

The tree needs a precise execution graph. Define the agents, edges, parent/child dependencies, message contents, ordering, fan-in/fan-out, synchronization and failure behavior.

An all-to-all graph may produce multiple independent views before aggregation; a tree can make early decisions influence later agents and can amplify one weak intermediate answer. Report messages, bytes, communication time, agent idle time, and the critical path for each stage.

A lower edge count is not automatically lower latency if the tree creates serial depth or load imbalance.

Early exit is a quality-changing decision. Semantic similarity can indicate that two outputs are close without showing that either is correct.

Confidence can be poorly calibrated, task-dependent or correlated with agreement rather than truth. Define the similarity representation, confidence estimator, threshold, calibration data, exit point, minimum agent coverage and fallback behavior.

Measure exit rate by task and input difficulty, agents skipped, answer changes, uncertainty, correctness, factuality, groundedness, refusal/safety behavior and disagreement cases. Compare to running all agents under the same prompt and decoding settings.

Prefill and decode have different dependencies. Prefill processes the prompt and creates attention state; decode generates tokens sequentially while reading the key-value (KV) cache.

Overlap is valid only when the consumer does not read a value before its producer has completed and when KV-cache updates are consistent. Specify which agent phases overlap, what data is ready at each boundary, how partial outputs are represented, and how cancellation or a late parent result is handled.

Measure overlap achieved, synchronization stalls, KV-cache memory, queueing, speculative or discarded work, and output equivalence.

“Similar accuracy” must identify the task metric and denominator. The captured description claims up to 90% lower end-to-end serving latency with similar accuracy, described as only ±1% variation, or sometimes higher task accuracy, relative to all-to-all MoA baselines.

That claim does not establish equal answer quality across tasks, seeds, prompts, agent models, output lengths or exit rates. Report per-task results, confidence intervals or repeated trials, answer correctness, calibration, latency percentiles, throughput and the full distribution of quality changes.

End-to-end latency must include all agent inference, prompt construction, communication, scheduling, synchronization, prefill, decode, early-exit decisions, output aggregation, model loading and queuing. Report time to first token, total response latency, p50/p95/p99, throughput, concurrency, token counts and resource use.

If the user sees a final answer only after all agents complete, streaming or internal overlap must be measured to the final answer boundary rather than only to an intermediate token.

The baselines should include all-to-all MoA, the same MoA with tree connectivity only, tree plus early exit only, tree plus overlap only, sequential agent execution, and a strong single-model or standard serving baseline where the quality target permits. Hold agent models, prompts, task set, output budget, decoding, hardware, interconnect, batch/concurrency, warm-up and measurement boundary constant.

Ablations are necessary because a claimed co-design gain may come mainly from skipping agents, changing the answer procedure, or changing the hardware allocation.

The captured description supports a tree-structured, early-exit and overlap-aware MoA serving runtime and reports a claimed up-to-90% latency reduction with approximately ±1% accuracy variation in the described comparison. It does not report task-level quality, exit behavior, communication, throughput, energy, tail latency, agent models or hardware conditions.

Early exit may alter agent consensus and answer evidence. The evidence supports a conditional low-latency MoA direction, not demonstrated quality-preserving serving across tasks, models and workloads.

Checkpointing trades ordinary execution cost against recovery

A checkpoint preserves enough state to resume work after a failure. Producing it consumes transfer and storage resources. An incomplete or inconsistent saved state can fail to reproduce the intended continuation, even if writing the checkpoint was fast.

Expcheck's captured method adapts checkpointing to expert activity in mixture-of-experts models. Experts are model components selected for particular inputs. The design question is which state must be saved to preserve a valid recovery point when activity differs among components. Recorded evidence

The record does not establish saved-state volume, normal-execution overhead, failure timing, or recovery behavior. A smaller checkpoint is useful only after the required recovery semantics are established. Tests should interrupt execution at relevant points and compare the resumed state with the intended behavior.

In mixture-of-experts (MoE) training, a router selects a subset of expert networks for each token. Expert activity is therefore uneven across batches and time.

A checkpoint must preserve enough state to resume the same training computation, not merely the experts that were active in the most recent batch. That may include shared parameters, expert parameters, optimizer states, gradients or accumulation state, router state, random-number state, data position, scheduler state, loss-scaling state, expert placement, communication state, and metadata that determines which values are valid.

An activity-aware checkpoint can reduce storage or transfer by exploiting the fact that some experts did not change or were not used in a given interval. The safety question is whether an omitted value is guaranteed to be reconstructible or unchanged when it is needed after restart.

“Inactive” is not the same as “irrelevant”: a previously inactive expert may be selected by the next batch, and an optimizer state can matter even when a parameter received no current gradient. The method must define its dependency rule and the point at which a state becomes safe to omit.

Checkpoint consistency is a distributed-systems problem as well as a storage problem. All workers need a compatible view of shared parameters, expert parameters, optimizer updates, router decisions, data ordering and communication progress.

A checkpoint taken while some workers have advanced and others have not can produce a state that cannot be resumed deterministically. The design should specify barriers, version numbers, write ordering, metadata, partial-write handling, replicas, checksums, and how a failed checkpoint is detected and discarded.

The recovery point is the exact training state represented by the checkpoint. Test failures during forward computation, backward computation, optimizer update, expert communication, checkpoint writing, storage transfer and data loading.

If nondeterminism is allowed, report an acceptable divergence in loss, parameters, router decisions and final quality rather than treating any completed run as recovery success.

Arithmetic intensity can help identify a limiting resource

Arithmetic intensity is the amount of computation performed per quantity of data moved across a specified boundary. Low intensity can indicate that transfers limit progress; higher intensity can shift the limit toward arithmetic capacity.

The value depends on the operation, input, representation, and memory boundary being measured.

The diffusion-language-model record uses this idea to organize execution stages. Diffusion-style generation has its own sequence of iterative computation, so a scheduling improvement must be evaluated on the actual model procedure.

Arithmetic intensity is a ratio: the number of arithmetic operations performed divided by the bytes moved across a named memory boundary. The boundary matters.

Operations per byte moved from high-bandwidth memory to a compute unit is not the same quantity as operations per byte moved from host memory to an accelerator or from storage into host memory. A runtime can improve one ratio while leaving the actual bottleneck unchanged.

Diffusion language models generate a result through repeated refinement steps. Each step may read a current token or latent representation, apply model layers, update an intermediate state, and decide how much uncertainty remains.

The cost and data reuse can change across early and late steps, sequence lengths, batch sizes, denoising iterations, and model configurations. A framework that chooses different execution or scheduling policies by arithmetic intensity must define the stage, its operation count, its byte count, the memory boundary, and the policy transition condition.

Operation counts also require a definition. A multiply-add may count as one operation or two.

Sparse operations, attention, routing, normalization, sampling, communication and control work may be included or excluded. Byte counts must state whether a value is counted once per transfer, once per request, or once per cache level, and whether reads, writes, metadata, intermediate materialization and recomputation are included.

Without those conventions, arithmetic intensity cannot be compared across stages or systems.

The ratio is a diagnostic, not a performance result. Low intensity may indicate that data movement limits progress, but latency can also be limited by synchronization, kernel launch, network communication, memory contention, insufficient parallelism, serial decoding or an irregular access pattern.

High intensity does not guarantee that a processor reaches its peak arithmetic rate. Measure achieved operations per second, bandwidth, utilization, queueing, synchronization, memory traffic, latency and energy in addition to the modeled ratio.

Stage orchestration can introduce transition costs. Moving a stage between devices may require copying weights or activations, changing precision, rebuilding a kernel plan, synchronizing workers or waiting for a queue.

If the policy changes frequently, the decision and movement overhead can exceed the saved compute time. Report steady-state and transition costs separately, and test workloads whose stage characteristics change during one request rather than only using a fixed average.

The baseline must preserve the generation task. Compare against standard diffusion decoding using the same model, number of refinement steps, input/output lengths, numerical representation, batch/concurrency, sampling procedure and quality target.

The autoregressive comparison needs its own model, token budget, stopping rule and quality criterion; a difference in generation procedure is not a pure runtime improvement. Report time to first useful output, total response latency, tokens or sequences per second, quality, memory, energy and variance.

Generalization requires multiple models and sequences. Arithmetic intensity changes with hidden size, sequence length, attention pattern, vocabulary, batch size, number of refinement steps and hardware.

A stage boundary tuned for one model or sequence distribution may be wrong for another. Evaluate short and long sequences, low and high concurrency, changing batch sizes, cache states, memory pressure and device configurations.
