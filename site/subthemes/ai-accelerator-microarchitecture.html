The bigger theme this belongs to

  • Architecture and accelerators

Faster inference requires more than faster multiplication

An accelerator (a chip or block built to do one kind of work fast)'s microarchitecture is its internal arrangement of arithmetic units, storage, connections, and control. A language model can keep these units busy only if the required data arrive in time and the next operation is ready to execute.

Faster arithmetic cannot remove a wait for memory or a dependency on an unfinished operation.

Four papers here change different constraints. AMBER changes how bits are stored and processed.

MBA changes how much data can remain close to computation. AHASD changes when two cooperating models execute.

OASIS changes how low-precision numbers are represented and multiplied. These distinctions explain the mechanisms; the reported improvement factors do not form a common ranking.

Weights are learned model parameters. Activations are intermediate values produced while processing an input.

The key/value cache stores attention information from earlier tokens so that generation need not recompute it each time. A token is one unit of the model's text representation, which can be a word fragment rather than a complete word.

AMBER: preserve the numbers while changing their encoding

Lossless compression preserves every encoded value after decompression. Quantization instead replaces values with a smaller set of representable choices and can introduce numerical error. A lossless compressor applied to an already quantized model preserves that model's values; it does not reverse the earlier quantization (storing numbers with fewer bits) error.

AMBER combines bit-transposed compression with a reconfigurable, pipelined bit-serial processing element. The official description covers integer, floating-point, and microscaling formats and reports evaluation on eight models and ten formats.

It gives 1.17× memory-efficiency and 3.16× compute improvements, naming Olive and Tender, without exposing the exact definitions or per-baseline comparisons. Process, clock, area, format-specific costs, and model-quality conditions remain missing. Official AMBER description.

AMBER: lossless bit storage and bit-serial arithmetic address different costs

What lossless bit compression preserves

An LLM (large language model: an AI model that reads and writes text) value is represented by bits. Integer values use a signed or unsigned encoding; floating-point values separate sign, exponent and significand fields; microscaling formats add a shared scale or group-level representation.

These formats place useful information in different bit positions. A compressor must preserve the exact encoded value if decompression is called lossless.

It does not restore accuracy already lost when a higher-precision value was quantized into a smaller format.

Bit-transposed encoding changes how bits are grouped before compression. Instead of storing each complete number as one sequence, the representation can group corresponding bit positions or fields across values.

If a group of values has statistical concentration in particular bit positions, a bit-level compressor can encode that concentration more efficiently. The operation is a representation change: after decoding, the original integer, floating-point or microscaling bits must be recovered exactly.

The potential benefit applies to weights and key/value (KV (key-value: the stored notes a language model keeps about earlier words)) cache data, but the two objects have different lifetimes. Weights are reused across many requests and can justify offline encoding.

KV data is produced and consumed during serving, so encode/decode latency (the wait for one result), memory bandwidth (how many bytes a link can move per second) and access granularity affect the result more directly. A compressed byte count alone does not establish lower serving latency unless the accelerator can decode the needed values at the rate computation consumes them.

What the bit-serial processing element changes

A bit-serial processing element performs arithmetic over successive bit portions rather than requiring a separate full-width datapath for every precision. A precision-agnostic design can reuse the same bit-level hardware for INT, floating-point and microscaling formats while changing the sequence of operations and control.

A stage-pipelined structure overlaps different inputs or bit stages, which can raise steady-state throughput (how much work is finished per second).

The trade-off is that bit-serial work takes multiple steps for one arithmetic result. Accumulation, field decoding, sign and exponent handling, scale management, control, and movement of compressed data still consume cycles and energy.

A pipeline's output rate after it is full is not the same as the latency of one request. The useful comparison must therefore include format-dependent bit counts, pipeline fill and drain, decode overhead, memory traffic and accumulation behavior.

What the reported evaluation establishes

The official description reports evaluation on eight LLMs and ten formats, with 1.17× memory-efficiency improvement and 3.16× compute improvement, and says AMBER surpasses Olive and Tender in throughput and energy. The description does not define memory efficiency or compute improvement, identify each baseline (the existing method a new result is compared against) configuration, report compression ratio by format, or state model-quality constraints.

It also supplies no area, clock, bandwidth, power or format-specific latency.

The evidence supports a unified multi-precision representation and compute direction. It does not show that every format gets the same gain, that lossless storage preserves end-to-end model quality under the surrounding quantization choices, or that compute improvement becomes the same inference-throughput improvement.

Cloud and edge suitability additionally require different memory, thermal and area constraints.

MBA: retain data close to the arithmetic

Storage capacity and transfer bandwidth answer different questions. Capacity determines how much can stay resident; bandwidth determines how quickly data can move.

Increasing capacity helps when it prevents repeated transfers of useful data. It helps less when the working data still exceed capacity or when another part of execution dominates.

MBA proposes gigabyte-scale embedded dynamic memory with priority for the key/value cache, double buffering, and iteration-aware eviction. Double buffering separates data being consumed from data being prepared for later use. Eviction chooses what to remove when space is needed.

The official description reports 5.99× speedup and 8.86× energy efficiency against a GPU (a chip with thousands of small arithmetic units, first built for graphics) baseline, versus 3.63× and 4.93× against an accelerator baseline. It does not identify the compared configurations or establish a fabricated gigabyte-buffer chip.

Technology retention, refresh costs, area, sequence lengths, and complete energy accounting require the manuscript. Official MBA description.

MBA: a large local buffer helps only when mapping, overlap and eviction preserve useful data

Why capacity and bandwidth are different limits

LLM inference (running a trained AI model to get answers) repeatedly reads model weights and, during autoregressive decoding, the key/value cache built from earlier tokens. High-bandwidth memory (HBM (high-bandwidth memory: memory dies stacked beside the processor)) can supply data quickly, but transferring data between HBM and the compute die still consumes time and energy.

A larger local buffer can reduce those transfers if the working set fits or if the most repeatedly used data remain resident.

Capacity answers how much data can stay close to computation. Bandwidth answers how quickly data can cross a connection.

A gigabyte-scale buffer improves neither automatically: if the active weights and KV state exceed its capacity, the system still transfers data; if arithmetic or another network link dominates, reducing HBM traffic may not change end-to-end latency.

What MBA changes in the memory and execution path

MBA uses embedded DRAM (eDRAM) as a large on-chip buffer. Its KV-cache-prioritized mapping (KVP) gives the cache priority when deciding which information should occupy the local buffer.

The mapping policy is important because KV entries have different reuse and lifetime depending on sequence length, layer, token position and batching. Prioritizing KV data can reduce repeated HBM reads, but it can also displace weights or other state that the next operation needs.

The architecture co-designs three mechanisms. Double buffering keeps one region available to the compute pipeline while another region is being filled or prepared.

This can overlap data movement with arithmetic, but only when transfer time, compute time, buffer capacity and synchronization are balanced. If the next data are not ready, the compute units still wait; if production outruns consumption, a buffer fills and backpressure is required.

Iteration-aware eviction chooses what to remove based on expected future use across iterations. An eviction policy is a prediction about reuse.

Removing data that will be needed soon creates another HBM transfer; retaining data with little future use consumes capacity that could protect a high-reuse KV or weight block. The policy therefore affects traffic, cache residency, overlap and energy together rather than being an independent memory feature.

What the reported comparisons establish

The official description reports 5.99× and 3.63× end-to-end speedup and 8.86× and 4.93× energy-efficiency improvement against GPU and LLM-accelerator baselines, respectively. The two baseline pairs must remain separate.

Speedup is a latency or throughput ratio; energy efficiency is useful work per energy under a defined task. Neither number establishes the other, and neither identifies how much came from eDRAM capacity, KVP mapping, double buffering or eviction.

The description does not identify the LLMs, sequence lengths, batch sizes, memory capacity, HBM traffic, eDRAM refresh or retention behavior, area, power boundary, accuracy effects or exact baseline configurations. It describes 1T1C IGZO eDRAM integration, but an architectural description is not proof of a fabricated gigabyte-scale buffer.

Density, retention, endurance, access time, refresh energy, process integration and area must all be evaluated together.

AHASD: overlap useful work without accumulating rejected work

Speculative decoding uses a smaller model to propose tokens and a target model to check them. Only accepted progress should count toward useful output.

Doing more drafting can waste work when proposals are rejected. Doing less can leave the verifier waiting.

The acceptance rule also matters to whether the generated-output distribution is preserved.

AHASD separates drafting on processing-in-memory hardware from verification on a neural processing unit. Its official description uses confidence-history and available-time controls to manage drafting and pre-verification, plus attention and task-scheduling hardware within LPDDR5-PIM.

It reports up to 4.2× throughput and 5.6× energy efficiency against GPU-only execution, and 1.5× and 1.24× against a GPU-plus-PIM baseline. Reported added hardware occupies under 3% of DRAM area, not necessarily under 3% of total system area or power.

Model pairs, acceptance distributions, absolute latency, correctness conditions, and implementation methodology remain unspecified in this source. Official AHASD description.

AHASD: speculative decoding needs a policy for deciding which draft work is worth doing

What speculative decoding computes

Speculative decoding uses a small draft language model (DLM) to propose several next tokens, then asks a larger target language model (TLM) to verify them in a batch. Accepted draft tokens can reduce the number of expensive TLM steps.

Rejected tokens are not useful output, although their generation and verification still consumed compute and energy. The useful quantity is accepted progress per unit time and energy, not the raw number of draft tokens produced.

Adaptive drafting changes the number of proposed tokens as confidence or workload conditions change. A synchronous implementation can leave the NPU (neural processing unit: a chip built to run AI models) idle while the PIM (processing in memory: logic placed inside the memory chip) side drafts, or leave the PIM side idle while verification completes.

A fully asynchronous implementation can instead produce drafts faster than verification can consume them, causing invalid or unnecessary drafts to accumulate. The control problem is to overlap useful DLM and TLM work without turning uncertainty into wasted work.

What AHASD changes

AHASD decouples DLM drafting on processing-in-memory hardware from TLM verification on a single NPU at task level. This lets drafting and verification proceed in parallel rather than forcing every operator to wait for the other side.

The task boundary matters: the system can schedule a complete drafting or verification unit, but it must still synchronize the token state and acceptance result between them.

Entropy-history-aware drafting control uses recent model uncertainty as a signal for how aggressively to draft. Lower confidence can make longer drafts less useful because more tokens may be rejected.

Time-aware pre-verification control considers available time before starting verification, with the stated goal of suppressing invalid drafting. These controls are policies, not guarantees: their value depends on the entropy distribution, acceptance rule, model pair, request length and thermal state.

The architecture adds attention algorithm units and gated task scheduling units inside LPDDR5-PIM. Localized attention keeps relevant attention computation near the PIM data, while gated scheduling controls when task execution is allowed to proceed.

The reported sub-microsecond task switching concerns switching overhead; it does not establish total draft/verify latency, accepted-token rate or end-to-end serving performance by itself.

What the reported numbers establish

The official description reports up to 4.2× throughput and 5.6× energy-efficiency improvement over GPU-only execution, and 1.5× throughput and 1.24× energy-efficiency improvement over the GPU+PIM baseline. The “up to” values are best cases.

Throughput must be tied to accepted output tokens and request conditions; energy efficiency must state whether energy includes both DLM and TLM, rejected work, memory traffic, control and idle periods.

The source reports hardware overhead below 3% of DRAM area. That denominator is not total system area, total power, thermal density, or mobile-device cost.

It also does not establish LPDDR5-PIM fabrication or the area/energy of the NPU-side additions. The description omits model sizes, acceptance rates, adaptive-draft distributions, absolute latency, correctness conditions, thermal methodology and cross-device generalization.

OASIS: compute using a small set of representative values

Non-uniform quantization assigns short codes to representative values that need not be equally spaced. Multiplying the codes as integers would generally give the wrong result: code numbers identify values rather than express their magnitudes.

One alternative is to precompute the possible products and retrieve the appropriate product using the two codes.

OASIS: lookup multiplication must preserve quantization meaning and control outlier error

Why non-uniform quantization does not fit ordinary integer MACs

Quantization replaces a continuous numerical value with a code that refers to a representative value. Uniform quantization spaces representatives at regular intervals.

Non-uniform quantization places them where the model's weights or activations are concentrated, which can represent a skewed or heavy-tailed distribution more efficiently. The code is an index, not necessarily the numerical magnitude.

This creates a hardware problem. If a weight code and activation code are multiplied as ordinary integers, the result is generally not the product of their represented values.

Dequantizing before multiplication restores the numerical meaning but adds conversion, storage and data-movement work. OASIS instead precomputes products for pairs of representative values and uses the two codes to select the corresponding product from a lookup table (LUT (look-up table: a small memory that stores a function's answers)).

What the Cartesian-product LUT changes

If there are (N_w) weight representatives and (N_a) activation representatives, a direct product table has (N_wN_a) possible pairs. The table can replace a general multiplier with code decoding and a lookup.

OASIS uses Cartesian-product LUT organization to reduce LUT size relative to earlier LUT-based GEMM (general matrix multiplication: multiplying two grids of numbers) methods and reports 64× lower LUT size and 1024× higher computational parallelism than those methods.

The table count does not equal total GEMM cost. The accelerator must read codes, select products, accumulate products across the reduction dimension, move partial sums and handle values that are not represented well by the common codebook.

Lookup parallelism can also increase table bandwidth, read ports, routing and accumulation demand. The reported ratio is therefore a microarchitecture comparison whose usefulness depends on the complete memory and accumulation path.

How outlier handling changes the numerical path

Aggressive activation quantization can represent common values compactly while poorly representing rare large values. Those outliers can contribute disproportionately to a dot product.

OASIS identifies activation outliers with the Orizuru top-k detection engine, computes the regular values through LUT-based GEMM, and applies concurrent error compensation for the outlier contribution.

The top-k engine must decide which values are exceptional under a threshold or ranking rule, then route their correction without stalling the common path. The correction is useful only if the outlier representation, location, sign, scale and accumulation order are preserved.

Detecting an outlier is not itself a proof that the compensated product matches FP16; the remaining quantization error and the hardware cost of detection and correction must be measured.

What the reported results establish

The recovered version-4 evaluation models hardware with cycle simulation, 28-nm logic synthesis and memory models. Figure 11 reports 3.00× speed and 1.44× energy efficiency against FIGLUT for four-bit weights and activations in single-batch decoding; FIGLUT uses sixteen-bit activations.

This is not a measurement of fabricated accelerator silicon, and the precision mismatch is part of the comparison condition.

The accuracy claim also has source-version and metric differences: the arXiv abstract reports 1.98%, the version-4 PDF abstract reports 1.94%, and Section V-B reports 2.05%. Table IV's LLaMA-2-7B values of 70.49 for FP16 and 68.55 for four-bit OASIS imply a 1.94-percentage-point difference for that model, not a universal relative loss.

These values should not be collapsed into one unqualified accuracy number.

What the group suggests—and does not establish

The shared technical direction is to reduce wasted representation, transfer, or execution work while accounting for the cost introduced by doing so. This is a synthesis of mechanisms, not evidence of a measured long-term adoption trend across conferences.

Combining these methods would require compatibility checks. A compressed representation needs a compatible arithmetic path. A larger buffer changes the value of compression. Speculative execution changes the pattern of data reuse and useful output. Their individual gains cannot simply be multiplied.

An end-to-end comparison should hold output-quality requirements, model, input/output lengths, and batch size explicit, then report completed useful work, latency, energy, memory traffic, and area under a stated implementation method. The three DAC manuscripts remain missing.

OASIS's recovered conditions supersede omissions in its historical card below, but source discrepancies and independent reproduction remain open.

Compare the results carefully

How to compare these papers’ results fairly

First identify the inputs and required output quality. Then identify the limited resource: time, memory, communication, energy, circuit area, or correctness coverage.

Ask which part of the method reduces that cost and which new cost it adds. Compare numbers only when the experiments hold these conditions sufficiently similar.

Correction register

Problem:

Adaptive speculative decoding on a mobile single-NPU-PIM system can leave resources idle under synchronous execution or waste draft computation under asynchronous execution when draft lengths fluctuate.

Mechanism / artifact:

Task-level asynchronous heterogeneous architecture decoupling DLM drafting on PIM from TLM verification on an NPU, with entropy-history-aware drafting control, time-aware pre-verification, localized attention units and gated task scheduling in LPDDR5-PIM.

Workload — the work tested:

Multiple LLMs and adaptive speculative-decoding algorithms on a mobile LPDDR5-PIM/NPU system; model sizes, DLM/TLM pairs, acceptance rates, draft distributions, request lengths, batch and arrival conditions are unspecified.

Hardware and manufacturing assumptions:

Single-NPU mobile system with LPDDR5-PIM, attention units and sub-microsecond task switching; DRAM-area overhead is reported, while NPU additions, process, thermal, power and complete-system area are unspecified.

Baseline — the comparison method:

GPU-only baseline

State-of-the-art GPU+PIM baseline

Synchronous/asynchronous policy constraints, model quality rule, hardware and energy boundary are unspecified

Reported measurements:

The official description reports up to 4.2x throughput and 5.6x energy-efficiency improvement versus GPU-only, 1.5x throughput and 1.24x energy-efficiency improvement versus GPU+PIM, and under 3% DRAM-area overhead; accepted-token definition, aggregation, energy scope and area denominator are unspecified.

Limits on the conclusion:

Draft tokens are not automatically useful output; rejection consumes DLM, TLM, memory and synchronization work, so throughput must be measured per accepted token and output-quality rule.

Entropy-history and time-aware controls guide adaptive drafting but do not guarantee acceptance or avoid wasted work under changed model pairs, request lengths or thermal states.

Sub-microsecond task switching is one overhead component, not end-to-end latency; queueing, synchronization, memory traffic, verification and idle time must be included.

The official description supplies no model sizes, acceptance distributions, absolute latency, correctness conditions, thermal method, complete area/power or cross-device test; no universal mobile speculative-decoding claim follows.

Correction register

Problem:

LLM inference needs lower memory and compute cost, but weight-only quantization adds dequantization overhead, integer weight/activation quantization can reduce quality, and non-uniform codes do not map directly to ordinary low-precision multipliers.

Mechanism / artifact:

Dual-side non-uniform weight/activation quantization with Cartesian-product lookup-table GEMM without dequantization, outlier-aware activation handling, concurrent LUT-based error compensation and the Orizuru top-k outlier-detection engine.

Workload — the work tested:

LLM inference including LLaMA-2-7B and the version-4 model suite; four-bit weights/activations, single-batch decoding for the FIGLUT comparison; full model list, sequence lengths, batch conditions and accuracy metric definitions are incomplete in the captured record.

Hardware and manufacturing assumptions:

Dedicated LUT-based low-precision accelerator; version-4 hardware evaluation uses cycle simulation, 28-nm logic synthesis and memory models, with area, memory, frequency, power, process and fabricated status otherwise unspecified.

Baseline — the comparison method:

FP16 baseline

Atom quantization/accelerator baseline

FIGLUT accelerator

Precision, model, batch, memory and quality parity are condition-specific and must remain attached to each result

Reported measurements:

The recovered abstract reports 64x LUT-size reduction and 1024x higher computational parallelism over existing LUT-based GEMM methods, an average accuracy drop of 1.98% versus FP16, 3.00x speedup and 1.44x energy-efficiency improvement versus FIGLUT; version-4 PDF abstract reports 1.94% and Section V-B 2.05%, while LLaMA-2-7B Table IV implies 1.94 percentage points. Definitions and aggregation remain source-specific.

Limits on the conclusion:

Non-uniform codes identify representative values and cannot generally be multiplied as integer magnitudes; LUT lookup avoids dequantization but still requires code access, product selection, accumulation, memory bandwidth and outlier handling.

Outlier detection and compensation can reduce error for selected activation values without eliminating residual quantization error or proving quality on every model, token distribution or layer.

The 64x LUT and 1024x parallelism ratios are not automatically end-to-end speed or energy gains; table bandwidth, read ports, routing, accumulation and control costs must be included.

The accuracy headline differs across abstract/source versions and the hardware result is simulation/synthesis/modeling rather than measured silicon; full model suite, area/energy accounting, sequence conditions and independent reproduction remain open.
