The bigger theme this belongs to

Start by identifying what must remain protected

A security requirement identifies information or behavior that another party must not obtain or control. A hardware evaluation then needs to specify that party's capabilities.

Can they run ordinary software, share a processor, observe physical signals, change inputs, or access the device directly? A protection can be effective under one set of capabilities and ineffective under another.

A side channel exposes information through an observation outside the intended data interface. Execution time, shared-resource behavior, and physical signals can depend on internal computation. Preventing direct access to a protected value therefore does not automatically prevent information about it from being inferred.

Distinguish the observation from the conclusion

Showing that a signal changes with internal activity establishes a measurable relationship. Establishing a practical information leak additionally requires showing what an observer can infer under the allowed access conditions.

The inference may depend on repeated measurements, prior knowledge, control of inputs, or alignment of events.

A protection evaluation must retain those conditions. Reducing one signal or defeating one tested inference procedure does not establish that all observations carry no useful information. Conversely, a laboratory observation with physical access does not by itself establish a remote attack.

The category also contains other security questions

Memory safety concerns whether a program can access memory outside its permitted objects or regions. Cryptographic correctness concerns whether a primitive computes its specified result.

Key protection concerns whether secrets remain protected during that computation. These questions can interact, but a result about one does not prove the others.

The broad taxonomy groups them for navigation. The individual records must be read using their actual protection requirement, not merely the presence of the word “secure” in a title.

Address translation and memory safety

The semi-virtual-addressing record proposes a lightweight translation module together with allocation and randomization choices for microcontrollers. A microcontroller typically combines a processor and peripheral control in a resource-constrained device. The mechanism changes how a program's addresses identify physical memory. Recorded evidence

The useful questions are which invalid accesses are prevented, how legitimate software remains compatible, and what hardware and execution overhead is added. The description leaves those conditions unresolved. An expanded address space alone does not establish the isolation behavior of a complete memory-management system.

Semi-virtual addressing: enlarging the address space is not the same as proving memory isolation

The underlying memory-safety problem

A program uses addresses to read and write memory. A pointer value may be valid for one object but invalid for another object, even when both objects are stored in the same physical memory.

An out-of-bounds access can overwrite a nearby object, read secret data, corrupt a return address or change control data used later by the program. A microcontroller often has no full virtual-memory system to translate and check these accesses.

It may instead expose physical memory directly, leaving protection to software conventions, compiler instrumentation or a small set of hardware regions.

This creates two separate requirements. The system needs enough address space and mapping state to represent where objects or regions are located, and it needs access enforcement: a rule that rejects an access when the address is not allowed for the current object or region.

The first requirement is about naming and mapping memory. The second is about enforcing authority.

A larger address range can help randomize or separate objects, but it does not by itself stop a program from using an invalid address.

What a lightweight translation module changes

The record proposes a page-table-free Lightweight Address Translation Module for a RISC-V CORE-V-MCU setting. A conventional MMU usually translates virtual addresses through page tables and can check permissions at page granularity.

A page-table-free design may use simpler hardware and a restricted mapping representation to reduce area, energy or timing variability. The exact translation rule, metadata format, permission checks, fault behavior and granularity are not exposed in the captured description.

The proposed result is described as semi-virtual addressing: a 575 KB physical address space is represented through a 2 GB address space. This number describes the range of names the software can use, not 2 GB of installed memory.

The system still has to decide how a generated address maps to a physical location and what happens when the address is outside the object's permitted region. If multiple virtual addresses map to one physical object, the security benefit depends on whether stale, guessed or aliased addresses are rejected and whether the metadata can be changed safely.

The relevant path is therefore:

  1. software produces an address;
  2. the translation hardware derives or looks up the corresponding physical location;
  3. the hardware checks the access against the permitted region and operation;
  4. an invalid access is blocked and produces a defined fault;
  5. the fault cannot be bypassed through another instruction, alias, DMA path, interrupt path or privileged mode.

The captured source establishes the proposed translation artifact, but it does not specify enough of this path to conclude that the module provides complete isolation.

How randomization and type-safe allocation fit into the chain

Heap randomization changes where dynamically allocated objects are placed or which address is used to refer to them. This can make a guessed target less reliable.

Randomization is probabilistic resistance: it raises uncertainty for an attacker, but it does not reject an access that has already obtained a valid reference or discovered the location.

Type-safe allocation uses information about which kind of object a region is intended to contain. If the hardware or runtime retains that information and checks it on every relevant access, the mechanism may prevent some forms of type confusion or cross-object use.

If type safety only influences allocation and does not participate in the access check, it is not itself a complete enforcement boundary. The description does not state the type metadata, its lifetime, the operations checked, or how reuse of freed memory is handled.

The three mechanisms should therefore be evaluated separately and together. Translation can provide an address mapping, randomization can make locations harder to predict, and type-aware allocation can constrain object placement or use.

None of these labels alone identifies which memory-safety violations are blocked. A complete claim must name the violation classes: spatial out-of-bounds reads and writes, temporal use-after-free, double free, type confusion, return-address corruption, data-only corruption and unauthorized DMA or peripheral access.

The attacker model determines what “memory safety” means

The evaluation must state whether the attacker can supply input, run untrusted code, observe addresses, read fault responses, control a peripheral, trigger interrupts, exploit a memory leak or execute with a privileged role. It must also state whether the protected program includes a runtime, operating system, allocator, compiler instrumentation and trusted libraries.

A mechanism may protect ordinary load and store instructions while leaving DMA, debug access, speculative behavior or privileged code outside its boundary.

An attacker who can learn a valid pointer may not need to guess a randomized address. An attacker who can corrupt allocator metadata may defeat a protection rule that assumes the metadata is trusted.

An attacker who can reuse a freed object may exploit a temporal error even when spatial bounds are checked. These are different paths and need separate tests.

The captured description does not supply an attack model or a coverage matrix, so the security boundary remains unspecified.

What the comparisons must establish

The software-only baseline should show which protections are normally available without the proposed hardware and what their runtime, memory and code-size costs are. The full-MMU baseline should use a named MMU configuration and operating environment, because an MMU is not one fixed design.

Its page size, translation caches, permission model, fault path and operating-system support affect both cost and protection.

For each baseline and the proposed module, report which invalid accesses are detected, when they are detected, and whether the fault occurs before the protected data is changed or disclosed. Include valid-access latency, translation-cache behavior if any, worst-case interrupt latency, code-size changes, memory consumed by metadata, hardware area, energy and frequency.

A claim of deterministic translation must report a worst-case bound, not only an average cycle count.

The security experiment should use vulnerable programs or generated tests with known ground truth. It should count blocked and missed violations by class, include false positives on valid programs, and test allocator reuse, aliasing, privilege changes, interrupts, DMA and fault recovery where those paths are in scope.

Formal reasoning or proofs can strengthen the result, but the proof assumptions must match the implementation and the attacker model.

Software compatibility is another requirement. Existing pointer representations, linker layouts, interrupt handlers, device drivers, boot code and debugging tools may assume physical addresses or a particular memory map.

A mechanism can be technically protective but difficult to deploy if it requires pervasive source changes or breaks peripheral addressing. The record does not provide compatibility results, application benchmarks or implementation measurements.

The captured official description supports a lightweight semi-virtual address-translation direction for a microcontroller and reports a 575 KB physical space represented in a 2 GB semi-virtual space. It does not report translation area or latency, protection coverage, attack success, software compatibility, metadata cost, DMA behavior, fault semantics or measurements against either baseline.

The evidence supports address-space expansion with integrated randomization and type-safe allocation, not demonstrated equivalence to a full MMU or complete memory-safety enforcement. Recorded evidence

S2CIM: protecting compute-in-memory requires a defined secret, an attacker, and an end-to-end inference check

What compute-in-memory is trying to do

Compute-in-memory, or CIM, places data storage and part of the arithmetic in the same memory array. In a conventional accelerator, weights move from memory to separate arithmetic units.

In a CIM macro, stored values and input values interact inside or close to the memory cells, often through analog or mixed-signal accumulation followed by conversion. This can reduce data movement, but it also places model weights and intermediate values in a structure that may be physically accessible to an attacker.

The security problem has several possible assets. The stored weights may reveal a proprietary model.

The input may contain private user data. Intermediate or accumulated values may reveal both.

A key or transformation parameter may protect one of these assets, but the protection claim depends on where the key exists, when it is used, and what an attacker can measure or control. “Secure inference” is therefore not one outcome.

It can mean that weights cannot be read, inputs remain hidden, the computation remains correct, or the circuit resists a specified side channel. These claims need separate tests.

What the recorded S2CIM design contains

The captured record describes a FeFET-based secure CIM macro, Affine-Transform Splitting for offline/online obfuscation, and Drain-Input Gate-Scan signed multi-bit MAC circuitry. FeFET refers to a ferroelectric field-effect transistor used for nonvolatile storage.

The stored state can persist without power, which helps edge inference but also means that a physical attacker may target the memory array, readout path, peripheral circuits or retained metadata.

An affine transform changes a value using a linear operation and an offset. Splitting such a transform into an offline part and an online part can move some work away from the deployed device or make a stored representation different from the model's direct weights.

That may reduce the usefulness of a memory readout. It does not automatically provide cryptographic confidentiality: the transformation may be reversible if the parameters are exposed, inferable from known inputs and outputs, or implemented in a way that leaks its state.

The signed multi-bit MAC circuitry changes how multiply-accumulate operations are represented or combined. The captured description names it as part of the secure architecture, but does not expose the exact encoding, sign handling, conversion path, key dependency or leakage argument.

A circuit-level name is not enough to determine whether it prevents weight extraction, input inference, fault injection, or only supports the intended arithmetic.

The threat model must define the protection boundary

At least four attacker positions should be distinguished:

  • A remote user who can submit inputs and observe inference outputs.
  • A software attacker who can execute code on the edge device and read ordinary memory or peripheral registers.
  • A local physical attacker who can probe pins, observe power or electromagnetic emissions, disturb voltages, or image or remove the package.
  • An attacker who can modify stored FeFET states, inject faults, replay a prior state or observe the device during provisioning.

These attackers have different capabilities and require different evidence. Chosen-input output observations test a black-box inference boundary.

A power-trace experiment tests a side-channel boundary. Direct array readout tests storage confidentiality.

Fault injection tests integrity. A 50% attack-success figure has no stable meaning until the attack target, number of alternatives, input access, measurements, repetitions and random-guess baseline are stated.

Key handling is central. The evaluation should identify whether a secret key exists, where it is generated, where it is stored, how it reaches the macro, whether it is present in plaintext on the device, and what happens after reset or power loss.

If the offline/online split leaves a reusable secret in a peripheral register or predictable memory region, storage obfuscation may not protect the model. If the design avoids a key and relies on a secret transform, the transform and its secrecy assumptions still need to be stated.

Correctness and security are different measurements

Encrypted or obfuscated inference must first produce the intended model result. The reported 97.4% encrypted Vision Transformer inference accuracy needs a reference definition: accuracy relative to the original unprotected model, accuracy on which dataset, with which model and preprocessing, and after what ADC/DAC quantization and noise.

A high task accuracy does not prove that weights or inputs are confidential. Conversely, a security transform that hides data but materially changes model decisions has not demonstrated a usable inference system.

The comparison should report clean-model accuracy, protected-model accuracy, degradation by class or task, calibration if relevant, and the numerical error introduced at each stage: storage, transformation, multiply-accumulate, accumulation, conversion and decoding. It should also test robustness across input distributions and operating conditions.

FeFET variation, retention, endurance, temperature, voltage, device-to-device variation and ADC/DAC behavior can affect both correctness and leakage.

Area and energy claims need a complete boundary

The record reports up to 16.8x area-efficiency improvement and up to 6.7x lower energy per MAC. “Area efficiency” can mean operations per unit area, not necessarily a smaller complete accelerator.

The denominator must state whether it includes the FeFET array, word-line and bit-line drivers, sense amplifiers, ADCs, DACs, accumulators, controllers, key or transform storage, error handling and interface memory. An encryption or obfuscation scheme that reduces array movement but adds large peripheral circuits may change the conclusion at system level.

Energy per MAC must use the same operation definition and include data movement, conversion, transformation, key handling, initialization and failed or repeated operations. A macro-only number cannot be compared directly with a system-level baseline.

Report throughput, latency, batch size, active area, total power, energy per inference, standby or retention energy and the process technology under the same workload and precision.

What a complete security evaluation needs

Compare against an ordinary nonvolatile CIM design and against recent in-memory-encryption CIM schemes using the same model, dataset, precision, process assumptions and measurement boundary. Report attack success against a random-guess baseline and against a meaningful unprotected baseline.

State whether attacks receive unlimited traces, chosen inputs, known plaintexts, model outputs, physical access or array readout. Include ablations that remove the affine split, the signed MAC circuitry, the key or each proposed protection so that the contribution of each part is identifiable.

Test direct weight recovery, input recovery, model-extraction quality, side-channel distinguishability and fault-induced output changes separately. If the claim is resistance rather than impossibility, report the measurement cost and attack budget.

Test fresh devices, process variation, temperature and voltage changes, and include the peripheral circuits that connect the macro to the rest of the inference system. A secure macro whose surrounding controller exposes the transform or key has not established end-to-end protection.

The captured official description supports a FeFET secure-CIM direction with affine-transform splitting and signed multi-bit MAC circuitry. It reports up to 16.8x area-efficiency improvement, up to 6.7x lower energy per MAC, 97.4% encrypted ViT accuracy and 50% attack success under stated threat models, but does not expose the process, complete area boundary, peripherals, key management, model, dataset, attack procedure or random-guess reference.

The evidence supports a circuit-and-algorithm co-design direction, not a complete end-to-end confidentiality claim, complete integrity claim, or directly comparable end-to-end energy or security result. Recorded evidence

Protecting computation inside memory

S2CIM combines circuit and algorithm choices for computation and storage in memory. Its captured description names transformations intended to obscure information, but does not establish the complete attacker model, key handling, model accuracy, or surrounding-circuit cost. Recorded evidence

An attack-success percentage must be read against the task. A result of 50% can have different meanings depending on what is being guessed, how many alternatives exist, and what an uninformed guess achieves. The percentage by itself cannot establish protection.

Cryptographic acceleration needs two evaluations

Safe-IoT's record concerns an accelerator for the ML-DSA digital-signature scheme. Faster execution or lower memory use concerns implementation efficiency. Correct signatures under the selected parameters and resistance to unintended information leakage require their own checks. Recorded evidence

Safe-IoT: an ML-DSA accelerator must be measured for both signature work and implementation security

What ML-DSA acceleration is doing

ML-DSA is a post-quantum digital-signature scheme. A signer uses a secret key to produce a signature for a message.

A verifier uses a public key to check that the signature corresponds to that message and key. The security goal is not simply to perform arithmetic quickly.

The implementation must produce correct signatures, reject invalid signatures, protect secret intermediate values and avoid leaking enough information for an attacker to recover the signing key or forge signatures.

The arithmetic is dominated by polynomial operations over a finite ring. A polynomial is a list of coefficients, and multiplication can be accelerated by transforming the coefficients into a representation where multiplication is cheaper.

The number-theoretic transform, or NTT, is the relevant transform used by many lattice-cryptography implementations. It requires modular additions, subtractions and multiplications, plus a controlled sequence of data movements and twiddle-factor operations.

A hardware NTT block can improve throughput, but it also creates a concrete timing, power, memory and leakage surface.

What the Safe-IoT artifact claims to change

The captured record names a memory-efficient hardware/software co-design with an MI-NTT circuit and lookup-table modular multiplication. The hardware/software boundary matters.

Some operations may be placed in hardware for speed while key setup, message handling, control and less frequent routines remain in software. The result depends on the cost of moving polynomials between the processor and accelerator, waiting for the accelerator, storing intermediate vectors and coordinating the two sides.

Lookup-table multiplication can replace some general modular arithmetic with precomputed values. That may reduce logic or cycles, but a table can also create address-dependent memory activity.

If a secret-dependent index selects a table entry, cache, bus, power or timing observations may reveal information. The security conclusion therefore depends on the table layout, access pattern, masking or constant-time behavior, and whether the table itself is public or secret-dependent.

The captured description does not expose those details.

The parameter set is part of the result

ML-DSA has parameter sets with different security targets and different polynomial dimensions, modulus-related operations and signature/key sizes. A throughput result without the parameter set cannot be compared fairly.

Message size, number of signatures, key-generation versus signing versus verification, batching, randomness generation and rejection sampling also affect the work.

The reported “up to 3.0x throughput improvement over CPU” needs a defined operation: signatures per second, verifications per second or total protocol transactions. It needs the CPU identity, frequency, compiler, software implementation, vector instructions, operating system, thread count and whether key generation or random-number generation is included.

A hardware accelerator can appear faster if the baseline is a scalar implementation or if data transfer and setup are excluded. The same accelerator may have a smaller advantage over an optimized vectorized implementation.

Memory efficiency is a boundary question

The record reports 2.6–8.3x lower on-chip RAM and a 4.28–176.53x area-time-product improvement. These ranges may correspond to different parameter sets or comparison points. They cannot be understood without a memory accounting rule.

State what is counted: coefficient buffers, NTT working memory, twiddle factors, lookup tables, secret keys, public keys, signatures, message buffers, random sampling state, DMA descriptors, control storage and any CPU-side memory. Explain whether memory is peak live storage or total storage capacity, whether off-chip memory is allowed, and whether the accelerator reuses buffers by overwriting intermediate results.

Lower on-chip RAM may increase latency, external traffic or energy. An area-time product also needs the area boundary, clock frequency, active time, process technology and whether software execution is included.

Correctness is more than one known-answer test

The implementation must produce signatures that pass an independent verifier for the selected parameter set and must reject modified messages, modified signatures and wrong public keys. It should be checked against official test vectors and a reference implementation across key generation, signing, verification, rejection paths and random seeds.

Modular arithmetic must handle negative values, reduction boundaries, coefficient ranges and NTT ordering correctly.

Hardware/software integration adds more failure modes: truncated transfers, stale buffers, interrupted operations, malformed commands, reset during signing and inconsistent endianness or packing. A high throughput number is not useful if a rare integration error creates an invalid signature or exposes secret state after a fault.

The captured source does not provide correctness coverage, test-vector results or fault behavior.

Cryptographic security and side-channel security are separate

ML-DSA can be mathematically sound while a particular implementation leaks its secret key through timing, power, electromagnetic radiation, memory access or fault behavior. Constant-time control flow is useful but does not prove constant power or electromagnetic behavior.

Lookup tables, modular multipliers, rejection sampling, conditional reductions and NTT data movement all need leakage analysis.

The threat model should state whether the attacker can measure a device physically, run software on the same processor, observe shared memory or buses, submit chosen messages, repeat signatures, reset the device, inject faults or observe only remote timing. Tests should report trace count, measurement quality, alignment, preprocessing, statistical distinguishers, key-recovery success, forgery success and comparison with an unprotected implementation.

If the accelerator relies on masking or blinding, report randomness generation, mask refresh, failure handling and the cost of those protections.

What a fair system comparison reports

Compare the same ML-DSA parameter set and operation against a named optimized CPU implementation and, where relevant, a comparable hardware/software accelerator. Use the same clock and process assumptions where possible.

Report latency distribution, steady-state throughput, energy per operation, total area, on-chip and off-chip memory, setup cost, random-number cost, CPU occupation and end-to-end time. Separate signing, verification and key generation.

The final result should connect efficiency to the device boundary. A 3× accelerator speedup with a large CPU wait or external-memory cost is different from a 3× end-to-end protocol improvement.

A RAM reduction that moves state to slower memory is different from a reduction in total memory traffic. A wide ATP range should be explained by parameter set and comparison boundary rather than presented as one general gain.

The captured official description supports a memory-efficient ML-DSA accelerator with MI-NTT, lookup-table modular multiplication and hardware/software co-design. It reports up to 3.0x throughput improvement over CPU, 2.6–8.3x lower on-chip RAM and 4.28–176.53x area-time-product improvement, but does not specify the parameter set, CPU, process, frequency, memory boundary, operation, power, correctness tests or leakage model.

The evidence supports an implementation-efficiency direction, not a comparable end-to-end result or demonstrated cryptographic and side-channel security. Recorded evidence

Remote ML-KEM side channels: a cryptographic scheme can be secure while an implementation leaks its secret key

What ML-KEM is protecting

ML-KEM is a post-quantum key-encapsulation mechanism. One party publishes a public key.

Another party uses that public key to create a ciphertext and a shared secret. The recipient uses a secret key to decapsulate the ciphertext and derive the same shared secret.

A secure implementation should not reveal the secret key through its outputs, timing, memory behavior, power behavior or fault responses.

The mathematical security claim and the implementation-security claim are different. The scheme can be designed so that recovering the secret key from public data is computationally difficult, while a processor running a correct implementation still leaks information through microarchitectural state or power-management behavior.

A remote attack does not break the underlying hardness assumption directly if it instead collects an observable signal correlated with secret-dependent execution and uses many observations to infer the key.

What a plaintext-checking behavior can provide

Decapsulation must process a ciphertext and determine whether the result is acceptable. Implementations may perform checks, recomputation, comparison or conditional selection before returning a shared secret or failure result.

Any observable difference in this path can become a signal. The captured description calls the behavior a plaintext-checking oracle, but does not expose the exact input format, returned response, timing difference, error behavior or number of queries.

An oracle is useful only when the attacker can connect an input choice to a measurable output. The experiment must therefore state whether the attacker submits chosen ciphertexts, receives a success/failure response, observes timing, or relies only on a power signal during a remote request.

If the same behavior is available through a network API, the server's retry policy, batching, rate limits and error normalization affect the attack. If the behavior is an artifact of a local test harness, the remote claim is narrower.

What “remote power” means in this setting

The processor is not assumed to expose a laboratory power pin to the attacker. A remote measurement may arise from a software-visible power or performance interface, a shared-resource timing signal, a power-management transition or another signal correlated with processor activity.

The exact sensor, sampling rate, resolution, access permission, network path and aggregation method determine whether the signal is available in a real deployment.

In this setting, network noise can be larger than the secret-dependent effect. The attack may need many traces, repeated chosen requests, stable processor placement or a quiet co-tenant environment.

Network distance, request concurrency, scheduling, frequency scaling, sleep states, thermal conditions and other workloads can change both the signal and the number of observations required. The captured record says that speculative execution and dynamic power management affect the attack, but it does not provide the processor SKU, trace protocol or noise model.

What secret-key recovery means

The reported result is up to 99.5% secret-key recovery success. That phrase needs a precise denominator.

It should state how many independent keys were tested, how many key coefficients or bits were recovered, whether the result means exact full-key recovery or a partial candidate set, how many traces and queries were used, the time per key, and whether the attacker receives verification feedback. “Up to” identifies a best condition, not the expected result across parameter sets, machines or deployments.

The attack should be evaluated against an unprotected implementation and any available defenses. A random or brute-force reference is not always the right baseline for key recovery, because the attack may already use public ML-KEM structure.

Report the recovery rate, false-recovery rate, confidence or candidate-list size, traces per recovered key, network requests, wall-clock time, and performance as noise or distance increases. A result that works in one quiet configuration after millions of requests has a different operational risk from one that works in minutes against a busy multi-tenant service.

Why implementation details matter

Secret-dependent branches, rejection paths, conditional reductions, memory addresses, cache state, speculative execution and frequency changes can all create observables. Constant-time source code can still produce power or microarchitectural differences.

Conversely, a noisy signal may become exploitable when an oracle lets the attacker choose inputs that amplify the difference. The implementation, compiler, processor, operating system, power-management configuration and remote interface are therefore part of the security boundary.

The evaluation should identify the ML-KEM parameter set and implementation version, compiler flags, CPU model and microcode, operating system, frequency governor, core affinity, virtualization state and remote collection path. It should separate traces by key and by machine, avoid training and testing on adjacent traces from the same execution, and test held-out keys, processor states and workloads.

If the attacker model assumes access to a power counter or performance counter, the study should state whether that interface is normally available to an unprivileged remote user and what provider configuration enables it.

Mitigations must be tested as part of the claim

Possible mitigations include constant-time decapsulation, removing or coarsening power interfaces, reducing response differences, blinding or masking, scheduling isolation, disabling relevant performance observations, adding noise and limiting repeated queries. Each mitigation trades security against latency, availability, energy, observability for administrators and compatibility.

A mitigation is not established by suggesting it; the experiment must show how recovery rate, trace requirement and attack time change while valid decapsulation continues to work.

The captured official description supports a remote power side-channel study of ML-KEM on Intel x86 using plaintext-checking behavior as an oracle and reports up to 99.5% secret-key recovery success. It does not specify network distance, sensor or trace interface, number of traces, attack time, CPU SKU, key/parameter set, implementation version, mitigations or transfer to other ML-KEM implementations.

The evidence supports remote exploitability under the tested conditions, not a universal ML-KEM break and not a general recovery rate across x86 systems and deployments. Recorded evidence

Janus: control-flow protection can reduce transient attack paths without proving that all transient leaks are gone

What transient execution makes possible

Modern processors may execute instructions before the processor knows that an earlier branch or indirect target was correct. A branch predictor guesses which instructions are likely to be needed.

The processor executes along that guess to save time. If the guess is later found to be wrong, the architectural register and memory state can be rolled back.

The temporary work can still change microarchitectural state such as caches, predictors or buffers. An attacker can measure that state and infer a value that the program was not allowed to return architecturally.

This creates two different security questions. The first is architectural control flow: which instruction should execute according to the program and its permissions?

The second is speculative observability: what information can transient instructions influence before the processor discards their architectural result? A defense that prevents an invalid indirect branch target may reduce the set of transient gadgets, but it does not automatically prevent every leak through valid targets, direct branches, data dependencies, caches or other microarchitectural structures.

What the ARM primitives contribute

Pointer authentication adds a cryptographic tag to a pointer or related control value. Before using the value, the processor can authenticate it using a key and context modifier.

If an attacker corrupts a return address or indirect target without knowing the signing key, authentication can fail. This protects particular pointer-integrity transitions; it does not make all memory unreadable, does not prevent an already valid pointer from reaching sensitive data, and does not by itself specify what the processor does during speculation before authentication resolves.

Branch Target Identification, or BTI, constrains where certain indirect branches may land. A target must carry an appropriate landing marker for the branch type.

This can make it harder to redirect execution into an unintended instruction sequence. BTI is a control-flow target rule, not a general confidentiality proof.

A valid landing point may still contain a useful transient sequence, and attacks that do not rely on an indirect branch may lie outside its coverage.

The effectiveness of PAC and BTI depends on the ABI, compiler, linker, operating system, exception paths, signal handling, dynamic loader, shared libraries and hardware generation. A protected application can still call an unprotected library, store an unauthenticated pointer in a place later consumed by protected code, or use a control-flow path that the compiler did not instrument.

The exact instruction forms and key-management rules therefore belong in the threat model.

What compiler-based protection changes

Janus is described as a compiler-based defense using PAC and BTI, modifier fusion and carrier-register reuse. A compiler sees the program's control-flow graph and can insert or combine instructions at function boundaries, returns and indirect calls.

Modifier fusion may reduce repeated authentication work by sharing a modifier or combining operations. Carrier-register reuse may carry an authenticated value or related state through existing registers rather than allocating additional registers or memory.

These transformations are performance and code-generation choices, not security guarantees by name. Reusing a modifier can reduce instruction count, but the modifier must remain bound to the right call site, stack frame or object.

Reusing a register can reduce register pressure, but spills, interrupts, exceptions and inline assembly must preserve the security invariant. A correct compiler pass needs a stated invariant: for every protected return or indirect transfer, what value is authenticated, what context binds it, when verification occurs, and what happens after failure.

The compiler also needs whole-program coverage rules. It should identify protected and unprotected boundaries, address-taking operations, tail calls, function pointers, virtual dispatch, callbacks, setjmp/longjmp, exceptions, signal handlers, hand-written assembly, shared-library calls and dynamic loading.

A benchmark with low overhead can still leave an exploitable uninstrumented path. Conversely, a formally strong policy can be impractical if it requires every library and runtime component to be rebuilt.

What attack coverage must show

The evaluation should name each transient-execution and control-flow attack class tested. Examples include mispredicted conditional branches that access secret data, poisoned indirect branches, return-address manipulation, speculative return paths, cross-domain calls, cross-process observation and attacks that use caches or other shared structures as the channel.

It should state the attacker privilege, code-execution ability, memory-corruption primitive, training or poisoning ability, victim boundary and observation channel.

For each attack, report whether the attack is prevented, merely made harder, or remains possible. Include proof or measurement that the sensitive value cannot influence an observable channel under the stated assumptions.

A reduction in gadget count is not the same as a zero-leakage result. Tests should include known vulnerable examples, compiler-generated applications, unprotected and existing-CFI baselines, different optimization levels, shared libraries and failure paths.

If PAC failure causes an exception, measure whether the exception path itself leaks or can be turned into a denial of service.

How to read the performance numbers

The captured record reports 3.85% average SPEC CPU2017 overhead and 2.97–7.80% overhead on real-world ARM64 applications. An average is useful only with the baseline compiler, hardware, input sets, run count, confidence interval and definition of overhead.

Hardware-interrupt security: an interrupt becomes an attack surface when an untrusted actor can trigger or observe its protected work

What an interrupt changes in execution

An interrupt is a hardware event that causes the processor to pause or redirect ordinary execution to a handler. The event may come from a timer, device, peripheral, memory system, inter-processor signal or another hardware source.

The handler runs with defined privilege and usually reads or updates state before returning to the interrupted program.

The interrupt mechanism is intended to make device events reliable. Security problems arise when the event, its timing, its handler state or its side effects cross a privilege boundary without the required checks.

An unprivileged program may be able to request a device action, cause an interrupt indirectly, observe when a handler runs, or influence data that the privileged handler consumes. Even if the program cannot read the handler's memory directly, it may infer secrets from timing, cache changes, output state, fault behavior or resource contention.

This is different from saying that interrupts are inherently unsafe. The security question is the complete path: who can cause the event, which controller accepts it, which privilege level handles it, what data enters the handler, what state the handler changes, and what the original program can observe afterward.

What the automated testing framework is looking for

The record describes an automated interrupt-feature and trigger-condition testing framework. At a conceptual level, such a framework can enumerate interrupt sources or controller features, vary software and hardware preconditions, observe whether an event is delivered, and compare the resulting state against an expected privilege boundary.

It can search combinations that are difficult to test manually, such as device state, interrupt enable bits, priority, masking, pending state, privilege transitions, timing and concurrent activity.

Discovery is not the same as exploitation. A framework may report a suspicious event because an interrupt was delivered under an unusual but intended configuration, because a test oracle is too broad, or because the observed effect is a denial of service rather than secret leakage.

Each finding needs a minimal reproducer, a clear protected asset, a trigger available to the stated attacker, a measurable leakage or integrity effect, and a check that the result is not caused by a test harness artifact.

How an interrupt can leak information

The handler may process secret-dependent state or touch memory whose location depends on a secret. Interrupt timing can change the number of cycles available to the interrupted program.

Handler instructions can modify caches, translation state, branch predictors, buffers, registers or device queues. An attacker may then measure execution time, memory access latency, output behavior, contention, or the presence or absence of another event.

The leak may also be indirect. A handler that copies data, validates a request, clears a fault or updates a status register can create a binary response.

Repeated triggering can turn that response into an oracle. If an interrupt arrives during a sensitive sequence, preemption may expose partial state or create a race.

If a low-privilege source can raise a high-priority interrupt repeatedly, the immediate impact may be availability loss, while the same scheduling disturbance can also amplify a side channel through microarchitectural state.

The threat model must state whether the attacker can execute code locally, access a device or peripheral, control input timing, observe interrupts, share a core, read performance counters, cause faults, or configure interrupt-controller registers. It must also state which parts of the handler and device driver are trusted.

“Unprivileged software” is not enough if the attacker must first control a device, obtain a physical signal, or rely on a particular kernel configuration.

Cloud-TEE availability: proving that an enclave exists is not the same as proving that it will receive CPU time

What a TEE normally promises

A trusted execution environment, or TEE, runs selected code and data inside a protected boundary. The hardware and trusted software aim to prevent an untrusted operating system, hypervisor or neighboring workload from reading or modifying the enclave's state.

Remote attestation lets a remote party check a measurement of the code and configuration before trusting an enclave.

Those protections are usually discussed as confidentiality and integrity. Availability is a different property.

An enclave may have correct isolated state and still be paused, starved of CPU cycles, repeatedly preempted, or prevented from starting. If a remote service relies on the enclave to meet a deadline, denial of CPU time can violate the service even when no secret is disclosed and no instruction result is corrupted.

Why an untrusted scheduler creates the gap

The scheduler decides which runnable context gets a processor and for how long. In a cloud setting, that decision may be made by software outside the enclave's trusted computing base.

A malicious or overloaded scheduler can give the enclave too few slices, delay its interrupts, evict its state, or schedule competing work on the same resource. The enclave can observe that it is slow, but it may not be able to prove whether the loss is ordinary contention or an intentional denial-of-service attack.

Remote attestation normally says what code is running and perhaps what hardware configuration it runs under. It does not automatically prove how many cycles the enclave will receive after attestation.

A resource commitment must therefore bind an availability promise to an observable quantity: CPU share, maximum scheduling delay, minimum progress over an interval, reserved cores, or another precisely defined contract. The promise must include the time interval and the behavior when the provider fails to meet it.

What availability-verifiable attestation adds

The record describes availability-verifiable remote attestation with resource commitments, trusted runtime monitoring and preemptive scheduling. Conceptually, attestation can report both the enclave identity and the configuration that is supposed to enforce a resource allocation.

A trusted monitor can measure runtime progress, detect starvation or contention, and provide evidence to a remote verifier. A preemptive scheduler can enforce a policy by interrupting competing work or allocating bounded execution windows.

These pieces solve different problems. Attestation communicates a statement about code and configuration.

Monitoring observes whether the statement continues to hold. Scheduling changes the execution decision that causes the availability result.

A signed report from the monitor does not create CPU capacity if the hardware, memory system or external host cannot provide it. The evaluation must show what is measured, who trusts the monitor, how monitor state is protected, and how a remote verifier distinguishes an attack from legitimate load.

What a CPU denial-of-service claim must define

The attacker model should state whether the adversary controls a co-tenant, the host scheduler, a hypervisor component, a device, an enclave workload or only ordinary guest software. It should state whether the attacker may create many competing tasks, generate interrupts, consume memory bandwidth, force cache contention, trigger page faults, cause migrations or prevent enclave startup.

A CPU-only attack can have a different boundary from a memory-bandwidth or I/O attack.

The service objective must also be explicit. Possible objectives include a minimum CPU fraction, a maximum response time, a bounded pause, a deadline for a trusted computation, or fair share among enclaves.

PMU-Faker: a performance counter can become a timer when its event count changes predictably with secret-dependent work

What a performance-monitoring unit normally does

A performance-monitoring unit, or PMU, counts hardware events such as retired instructions, cache misses, branch activity, cycles, stalls or other microarchitectural conditions. Developers and system operators use these counts to find bottlenecks.

The processor usually provides a configuration interface to choose an event, start and stop counting, and read a counter.

The security question is not whether a counter is called a performance metric. It is whether an attacker can observe a value that changes with a victim's secret-dependent behavior.

If an event count distinguishes two executions, it can serve as a clock or classifier even when the normal high-resolution timer is removed. The event does not need to count time directly.

It only needs a sufficiently stable relationship between the victim's work and an observable counter delta.

How a timer-free timing signal arises

Worked example

Suppose a victim performs one of two operations depending on a secret. One path executes a different number of instructions, causes different cache activity, or interacts differently with speculative execution.

A permitted PMU event may count that difference. An attacker can start a counter, let the victim run, stop the counter, and use the count to distinguish the paths.

Repeating the experiment can reduce noise and recover a secret bit, classify an input, or build a higher-level attack.

Removing an explicit time source therefore changes the attack surface without necessarily removing measurement. A PMU event can have lower resolution, more noise or a more complicated calibration requirement than a cycle counter.

The attacker may still combine it with repetition, event selection, instruction-triggered variation or a known workload to construct a usable signal.

What automated PMU fuzzing is trying to discover

PMU-event fuzzing varies event selections, privilege settings, instruction sequences, victim operations and execution contexts, then looks for counts that respond to a controlled difference. A valid discovery should show that the event is accessible to the stated attacker, that the count changes for a known cause, that the change is repeatable, and that the signal is not an artifact of multiplexing, counter overflow, scheduler migration or a misinterpreted event definition.

The captured record describes 118 discovered PMU events and a PMU-Faker timing mechanism intended to balance precision and adaptability across instruction-triggered cycle variation. The number 118 is a discovery count under the tested search space.

It is not automatically the number of vulnerable events on every processor, because event encodings, counter width, privilege controls and implementation behavior differ by microarchitecture and operating system.

Why instruction-triggered variation matters

Some attacks need a timer that can resolve small differences between instruction sequences. If a PMU event responds to instruction-triggered cycle variation, an attacker may construct a timing signal from the count of a carefully selected workload.

Adaptability may mean changing event choice or calibration when the processor or victim behavior changes. Precision may mean separating nearby execution costs.

This mechanism creates a calibration problem. An event that is useful on one CPU generation may count a different condition on another.

Operating-system virtualization may scale, multiplex or hide counters. Hypervisors may expose virtual counts that have different noise and reset behavior.

The evaluation must identify the exact event encoding, counter configuration, access privilege, counter width, sampling or read interval, core affinity, virtualization and overflow behavior.

If the result is a timer replacement rather than direct key recovery, report the downstream attack separately.

Security controls and their tradeoffs

Possible defenses include restricting PMU access, filtering events, reducing precision, virtualizing or randomizing counts, disabling events in enclaves, flushing or partitioning counters, and changing the victim's execution pattern. Each can reduce observability while harming profiling, debugging, capacity planning, or legitimate enclave monitoring.

A defense that blocks one event may leave another correlated event available.

The evaluation should test event families and combinations after mitigation, not only the event used by the original attack. It should measure whether the attacker can select an alternative event, average multiple noisy counters, or use instruction-triggered calibration.

In-vehicle attack-chain traceback: linking alerts across network domains is not the same as proving the attacker’s path

What traceback is trying to reconstruct

An in-vehicle attack can cross several communication domains. Host software may send or receive data through an Ethernet gateway, which may then exchange messages with a controller area network, or CAN, bus.

Each domain has different identifiers, timing, protocol rules and trust assumptions. An intrusion-detection system, or IDS, may raise alerts in more than one domain, but the alerts are usually partial observations rather than a complete attack narrative.

Traceback tries to infer which alert or event caused another event and to order the stages into an attack chain. The output may identify an entry point, a gateway transition, a target ECU, or a set of plausible paths.

This is a reconstruction problem under incomplete and noisy evidence. It is not automatically proof of attacker identity, exact packet causation or successful compromise.

What the temporal graph represents

A graph has nodes and edges. A node can represent an IDS alert, a message, a host process, a gateway action or an ECU state.

An edge can represent temporal order, protocol reachability, cross-domain forwarding, or a causal relation proposed by the method. A temporal graph adds time constraints: an event cannot cause an earlier event, and a path must respect the delays and ordering possible in the vehicle network.

The graph is useful only when its node and edge meanings are defined. If an edge means “could have preceded,” it is weaker than “caused.” If multiple alerts can map to one packet or one packet can create several alerts, the graph can contain duplicate or missing paths.

The method must state how clock differences, buffering, retransmission, aggregation, dropped alerts and simultaneous events are handled. A plausible path can still be wrong when the IDS missed the real intermediate event.

What the four plausibility checks contribute

The record describes four plausibility checks but does not expose their exact rules. Such checks might constrain timing, protocol direction, gateway reachability, message format, ECU capability or consistency across domains.

They can remove graph paths that are impossible under known vehicle behavior. They do not prove that the remaining path is the path used by an attacker unless the checks cover the relevant causal assumptions and the alert inputs are reliable.

This distinction matters because traceback quality depends on both the graph algorithm and the upstream alerts. If the IDS produces a false alert, the graph may construct a convincing chain from nonexistent evidence.

If the IDS misses a stage, the method may bridge two events that were not directly connected. Report alert precision and alert recall separately from traceback precision and traceback recall.

Otherwise a high chain score can hide a system that performs well only when supplied with unusually clean alerts.

Compatibility is not the same as certification approval. A certification-related claim must identify which requirement or boundary is preserved, what evidence is produced, which software and hardware are in scope, and whether the vehicle manufacturer or assessor accepted the argument.

A method can avoid packet marking while still adding code, memory, logging, timing or diagnostic behavior that requires review.

Masked ML-DSA modular reduction: reducing the cost of side-channel protection without changing the protected interface

Why modular reduction is on the critical path

ML-DSA performs arithmetic on polynomial coefficients modulo a fixed modulus. Additions and multiplications can produce values outside the desired range, so the implementation must reduce them back into a valid representative range.

Modular reduction is repeated inside transforms, polynomial multiplication, sampling and signing. Its latency, area, memory traffic and switching behavior can affect the whole accelerator.

A reduction unit is not only an arithmetic block. In a masked implementation, its inputs are represented by multiple shares.

Each share hides part of the sensitive value, and the shares are combined only in a way intended to preserve security. A reduction circuit that is fast for ordinary values may be unsafe when it combines shares through secret-dependent carries, table addresses, comparisons or glitches.

What first-order masking means

In a simple two-share first-order representation, a sensitive value x is split into shares x0 and x1 such that their combination reconstructs x, while either share alone should not reveal it under the masking assumptions. Operations must transform the shares without exposing a statistical relation between one observed leakage sample and the secret.

This protection is about an attack model. First-order security generally addresses an attacker who observes one leakage point or one leakage sample at a time and uses a first-order statistical test.

It does not automatically protect against higher-order combinations of multiple shares or multiple time samples. Hardware glitches, unequal delays, register reuse, randomness failure, routing coupling and unmasked intermediate values can also violate the assumptions.

What a drop-in modular-reduction design is trying to preserve

The record describes a drop-in masked modular-reduction architecture optimized for Caliptra ML-DSA signing. “Drop-in” implies that the unit can replace an existing reduction block with limited changes to the surrounding design.

The useful engineering question is whether the replacement keeps the same functional interface, masking format, clocking and protocol while reducing cost.

An interface-compatible replacement is not automatically security-compatible. The surrounding pipeline may expect a particular share ordering, fresh randomness, latency, reset state or valid/ready behavior.

A change in timing can expose a share longer than before. A reduction unit that is secure in isolation may leak when its outputs feed an unmasked transform or when the controller reuses a register across shares.

The paper-level evaluation must therefore include the complete signing path and state which components are inside the leakage boundary.

What the arithmetic implementation must control

Reduction can use conditional subtraction, quotient estimation, Barrett-like methods, Montgomery-style methods, lookup structures or combinations of these. Each choice has different area, delay, multiplication and comparison behavior.

In a masked circuit, a conditional operation cannot simply reveal a secret-dependent decision through a control signal or a different sequence of gates.

The evaluation should describe how carries, comparisons, conditional subtraction, shares, randomness and intermediate products are represented. It should state whether the design is purely combinational, registered, pipelined or time-multiplexed, and whether the same hardware processes both shares.

It should report clock frequency, latency per reduction, initiation interval, coefficient width, modulus, throughput, random bits consumed and behavior on boundary values.

Test Vector Leakage Assessment, or TVLA, applies statistical tests to traces collected under controlled inputs. “No first-order leakage in TVLA over more than 1,000,000 traces” means that the reported test did not cross its chosen leakage threshold under its trace setup, test vectors, clock, device and analysis order.

It is useful evidence, but it is not a proof that no attacker can recover the key.

The result needs the target platform, probe, acquisition bandwidth, sampling rate, alignment, trace classes, threshold, confidence rule, number of devices, random seeds, masking order and analyzed time windows. It should include fixed-vs-random and other relevant tests, verify that the test has enough sensitivity, and test higher-order combinations when the threat model requires them.

BREW-RC: write latency can reveal hidden error-correction structure in ReRAM

What the hidden ECC is doing

Resistive RAM, or ReRAM, stores information in the electrical resistance of memory cells. A memory controller may add an error-correcting code, or ECC, before writing data.

The ECC computes additional parity information from the data. During a read, the controller uses the stored data and parity to detect or correct errors.

The parity bits are usually an implementation detail. A user may send data and receive data without seeing the codeword or the parity-check matrix.

The matrix defines which data and parity bits participate in each check. If it is recovered, an observer can understand the device's correction structure, model its reliability behavior more accurately, or use that knowledge in a later attack.

Recovery of the matrix is not the same as recovering all stored user data, but it removes a layer of hidden implementation information.

How write timing becomes an observation

A write operation may take different time depending on the codeword, the cells being programmed, verify-and-retry behavior, controller scheduling, or an ECC-related path. If a chosen data pattern produces a codeword with a particular parity structure and the elapsed write time changes predictably, the timing becomes a side channel.

The attacker does not need to read the parity bits directly. They submit or induce write patterns, measure completion time, and infer constraints on which hidden parity relationships could have produced the observed differences.

Timing is useful only if the signal is repeatable compared with device variation, controller queueing, temperature, wear, interface jitter and measurement noise.

“Non-invasive” describes the measurement method, not the attacker’s required deployment access. The evaluation must state whether the attacker needs physical access to the memory pins, a local controller API, a storage device interface, a privileged driver, a co-tenant channel or only ordinary application writes.

A laboratory measurement at the device interface may not be available to a remote storage user.

What bit-exact ECC recovery means

The target is a parity matrix, not just the ECC family name. A bit-exact recovery reproduces the specific relationships used by the product, including bit ordering, grouping, parity placement and possibly controller transformations.

This can be more useful than identifying a broad code family because timing models and reliability predictions depend on the exact mapping.

SAT-based recovery expresses the unknown matrix entries as Boolean variables and adds constraints derived from measured timing observations and known write patterns. A satisfiable assignment is a candidate matrix.

The solver can find one matrix consistent with the observations, but the result is only unique if the data constrains the unknowns sufficiently. The study should report whether the recovered matrix is uniquely identified, how many candidate matrices remain, how many observations are required, and whether an independent write/read test validates every recovered relation.

Timing constraints can be wrong if the observed delay has several causes. ECC parity effects may be mixed with cell programming time, wear-leveling, queue depth, error retries, temperature, voltage, background maintenance or controller scheduling.

The recovery pipeline must isolate or model those factors and report confidence in each constraint. Otherwise the SAT solver may fit a stable but unrelated timing pattern.

What “complete recovery on two products” establishes

The captured record reports complete ECC recovery on two commercial ReRAM products and multiple device samples. This is strong evidence that the method worked under those products' conditions.

It does not establish that the same timing signal exists in every ReRAM controller, that products from other vendors use recoverable matrices, or that the attack works after firmware changes, timing quantization, randomized scheduling or added noise.

Product diversity matters because ECC may be implemented in the memory array, controller, firmware or a separate reliability layer. The code can differ by capacity, operating mode, vendor, wear state and controller revision.

Test held-out devices, independent samples, product generations, capacity modes, temperatures, voltages and wear levels. Separate training or inference data by device so that repeated measurements of one sample do not make generalization look stronger.

What the measurement must report

Report timing resolution, timer location, number of writes, data-pattern design, sample count, measurement noise, queue state, environmental conditions, recovery time, solver time and success criterion. Include the amount of physical or software access, whether writes are destructive, and whether an attacker can repeat operations without triggering wear limits or service alarms.

Compare against an opaque-ECC baseline that does not use a recovered matrix and against timing models that omit parity effects. Measure the practical consequence: improved error-rate prediction, better reliability characterization, a lower-cost fault attack, or another defined outcome.

Matrix recovery alone is a capability result; it does not show that the recovered information changes an attack or reliability decision.

Countermeasures and deployment boundary

Possible defenses include constant-latency writes, batching, timing quantization, randomized scheduling, queue hiding, controller noise, rate limits, access control and changing the ECC mapping. These defenses can reduce reliability observability or increase write latency and energy.

They should be tested against an adaptive recovery algorithm, not only the original fixed timing model.

What a counting thread is measuring

A counting thread is an attacker-controlled or attacker-influenced thread that runs at the same time as a victim and observes a shared processor resource. What the signal represents

It is not a direct instruction log. The waveform also contains effects from voltage regulation, clocking, memory traffic, other cores, interrupts, thermal state, measurement equipment and unrelated software.

Instruction-level side-channel disassembly tries to infer a sequence of executed instructions from this aggregate signal. The target may be exact instruction identities, instruction classes, basic blocks or a useful partial sequence.

These targets have different difficulty and security meaning. Recovering a rough class sequence is not the same as recovering a cryptographic key or full program state, but it may reveal control flow, secret-dependent operations or code structure that supports a later attack.

Why modern CPUs make the inverse problem difficult

The out-of-order execution model allows instructions to execute when their inputs and functional units are ready rather than strictly in source order. The speculation mechanism executes paths before branches resolve.

Multiple instructions can overlap, share execution units and retire in a different timing pattern from the source sequence. Deep pipelines, caches, branch predictors, simultaneous threads and frequency changes further mix the electrical effects.

The observation is therefore many-to-one: different instruction sequences can produce similar waveforms, and the same sequence can produce different waveforms under different inputs and processor states. PLONK-Hammer: zero-knowledge privacy assumes the prover’s computation and memory are not faulted

What PLONK is proving

PLONK is a zero-knowledge proof system used to prove that a computation satisfies a set of constraints. A prover takes a circuit, public inputs and private witness values, then produces a proof.

A verifier checks the proof without learning the private witness, assuming the protocol and implementation behave as required.

Input privacy is a protocol property under an implementation model. The proof is intended to convince the verifier about a statement without exposing the private input.

Soundness is a different property: a faulty or malicious prover should not convince the verifier of a false statement. A fault-injection attack can affect either boundary.

It may alter the witness, intermediate values, proof data, or memory used to compute the proof. A successful attack might leak information, create a false proof, or cause a denial of service; these outcomes must be separated.

What Rowhammer changes

Rowhammer is a DRAM fault mechanism in which repeated activity around memory rows can disturb stored bits under susceptible hardware and conditions. The attack does not directly read a protected value.

It aims to induce memory errors in locations that influence a victim computation. Whether this is possible depends on DRAM technology, row layout, refresh policy, memory controller behavior, physical placement, access permissions and the victim's memory allocation.

The relevant attack chain is therefore longer than “Rowhammer breaks zero knowledge”:

  1. the attacker obtains a way to create the required memory activity;
  2. the induced disturbance flips a bit or changes a value in the prover's memory;
  3. the changed value affects a proof-relevant computation;
  4. the resulting faulty proof or output remains observable;
  5. repeated observations let the attacker infer private information or construct a valid false result.

Breaking one link does not establish the whole chain. A bit flip in an irrelevant buffer may only crash the prover.

A faulty proof that the verifier rejects may reveal no private information. A repeated proof response can become an oracle only if the attacker can distinguish outcomes and relate them to the secret input.

Why polynomial commitments matter to the analysis

PLONK represents constraints and witness relationships through polynomial evaluations and commitments. A polynomial commitment binds the prover to a polynomial while allowing the verifier to check claims about evaluations without receiving the entire polynomial.

If a fault changes a coefficient, evaluation, opening proof, challenge-dependent value or commitment-related state, the resulting algebraic inconsistency may be detectable—or may create a structured faulty proof that leaks information through acceptance behavior.

The captured description names faulty-proof analysis and polynomial-commitment recovery, but does not specify which values are faulted, which commitments are exposed, how many faulty proofs are collected, or how the recovered information maps to the private input. A recovery claim needs an algebraic explanation and an independent validation: identify the unknowns, show the equations contributed by each observation, state whether the system has a unique solution, and test the recovered input against fresh proofs or known values.

What the gnark result does and does not establish

The card identifies gnark's PLONK implementation as the tested system and reports qualitative secret leakage. This establishes a demonstrated concern for that implementation under the tested fault model if the full experiment is reproduced.

It does not establish that the PLONK protocol is mathematically broken, that every gnark configuration leaks, or that a verifier accepts a faulty proof.

The experiment should report the proof parameters, circuit, private-input distribution, memory location, fault type, bit-flip rate, number of attempts, observation channel, recovery success and verifier behavior. It should distinguish a partial leak from exact input recovery and show how many faulty proofs and how much time are required.

If an attacker needs co-location, a vulnerable DRAM module, access to a large memory region or a privileged memory interface, those are part of the practical boundary.

Fault model and platform transfer

DRAM faults vary by vendor, density, generation, temperature, refresh settings, memory controller, placement and neighboring-row pattern. A fault model demonstrated on one platform may not transfer to another.

Memory allocation and page placement can also determine whether a disturbed row contains prover data, a commitment, a witness buffer or unrelated state.

The evaluation should name hardware, firmware, operating system, refresh settings, memory layout, privileges, co-location and mitigation configuration. It should test error-correcting memory, refresh changes, row isolation, memory allocation policies and other defenses where relevant.

It should measure false positives, crashes, rejected proofs and availability effects, not count every induced bit flip as secret recovery.

Privacy and soundness need separate checks

For privacy, demonstrate what private information is recovered, from which observations, at what success rate and against what baseline. For soundness, attempt to produce a proof of a false statement and report verifier acceptance, not merely a corrupted internal state.

For availability, measure crashes, retries, latency and resource exhaustion. A defense may stop one outcome while leaving another.

What compute-in-memory weights are

In a compute-in-memory, or CIM, accelerator, neural-network weights are stored close to or inside an array that performs part of the multiply-accumulate operation. A crossbar has rows and columns of memory cells.

Input signals may be applied along one dimension, and the resulting electrical response along the other dimension contributes to a computation.

Integrity and provenance are different claims

Integrity asks whether a value was changed without authorization. Provenance asks where the value came from and whether it is the approved version.

A signature can authenticate a digest and signer, but only if the verifier checks the correct object, the key is trusted, and the authenticated object is bound to the device, model version, address and use context.

Signing columns instead of an entire weight matrix can reduce signature storage, verification work or update granularity. A column signature lets the system verify a smaller unit before use or after a partial update.

The security boundary is the column. If a column contains multiple weights and one signature authenticates the aggregate, the verifier must still detect a change to any weight that affects the signed digest.

What graph isomorphism preserves

A graph represents objects and relationships. In a hardware graph, nodes may represent gates, registers, signals, modules or operations, while edges represent connectivity or dependency.

An isomorphism is a one-to-one relabeling or correspondence that preserves a chosen graph relationship. If two graphs are isomorphic under that definition, their connectivity structure is preserved even though node names or presentation order may change.

An isomorphic transformation can make a design harder to match using names, layout order or a simple graph comparison while preserving its logical function. It does not necessarily change graph invariants such as degree patterns, connectivity, subgraph counts, cut structure, fan-in/fan-out, sequential boundaries or repeated motifs.

An attacker can use those invariants, domain knowledge and simulation to recognize a design even when labels have changed.

Function preservation is also a separate condition. A graph transformation may preserve an abstract graph relation while changing timing, reset behavior, clock-domain assumptions, initialization, side effects, power or physical constraints.

Conversely, formal functional equivalence may prove that the transformed RTL computes the same outputs under stated inputs without proving that the transformed design hides the original architecture from a structural or physical observer.

Athena: pre-silicon leakage estimation is a model, not a measured side channel

Start with the physical question

A side channel exists when an unintended observable changes in a way that carries information about a protected computation. The observable might be execution time, power consumption, electromagnetic radiation, cache activity, or another signal available to the attacker.

The protected value might be a cryptographic key, an input, a model parameter, or an intermediate state. The security question is not merely whether two executions produce different internal activity.

It is whether an attacker with a stated observation method can use repeated observations to distinguish secrets or recover useful information.

Athena is described as an analytical timing-aware pre-silicon estimator. That places it before a fabricated chip and before ordinary post-silicon trace collection.

Its purpose is potentially valuable: a design team can identify risky blocks while changes are still possible. But the result is an estimate produced by an abstract model.

It is not, by itself, a measured side channel, a successful key-recovery attack, or proof that a physical implementation leaks at a usable rate.

What “timing-aware” has to represent

Execution time is produced by a chain of microarchitectural events. Pipeline depth, cache hits and misses, branch decisions, speculation, stalls, resource contention, memory ordering, interrupts and other events can change the number of cycles between an input and an observed completion.

If any of those events depend on a secret, timing can become an observation channel.

An analytical model must therefore state which events it represents and how they become an observable. A simple model might assign a cost to each instruction or cache event.

A more detailed model might represent microarchitecture, dependencies, pipeline occupancy, cache state, branch behavior and contention over time. The captured description does not specify the equations, abstraction level, timing source, power model, leakage metric, or the boundary between modeled behavior and unmodeled physical effects.

The word “timing-aware” alone does not show that the relevant secret-dependent events are represented.

Timing and power should also be kept conceptually separate. A timing estimate predicts when events occur.

A power estimate predicts how switching activity, capacitance, voltage and implementation details contribute to an electrical signal. Timing can influence power by changing which units switch and when, but a timing model is not automatically a physical power model.

If Athena combines these views, the evaluation must identify the mapping and its calibration data.

Estimation is different from exploitation

The estimator may rank designs or blocks by predicted leakage. That can support an early design decision. A security claim requires a further chain:

  1. a secret changes internal events;
  2. those events change a measurable attacker observation;
  3. the observation survives noise and measurement limits;
  4. an attacker can distinguish secrets or recover information within a stated trace and computation budget.

The first step can be visible in a simulation while the second fails after synthesis because routing, clocking, supply networks, placement, coupling or analog behavior change the signal. Conversely, a model can miss a physical path and produce a false negative.

A predicted ranking can therefore be useful even when it is not an attack result, but the two outcomes must not be reported as if they were equivalent.

The attacker and measurement boundary are part of the result

The evaluation needs to specify whether the attacker measures completion time remotely, reads a local cycle counter, observes power through a probe, records electromagnetic radiation, or uses another channel. It must state whether the attacker chooses inputs, repeats the same operation, knows the implementation, controls scheduling, shares a processor, or has physical access.

It must also state the measurement resolution, alignment method, noise, number of traces and allowed computation.

These details determine what “leakage” means. A cycle difference visible to a privileged local counter may be irrelevant to a remote attacker whose network jitter is larger.

A power pattern visible on a benchtop probe may not be available through the package or board interface. A model that does not define the observation cannot establish practical attack exposure, even if its internal score changes with the secret.

How to validate a pre-silicon prediction

The strongest validation uses the same designs at several boundaries: analytical model, RTL or gate-level simulation, and fabricated hardware where available. The comparison should use the same secrets, inputs, clock conditions, workload, leakage metric and baseline.

Report rank correlation between predicted and measured leakage, absolute timing error, and whether the model correctly identifies high- and low-leakage designs.

Security measurements should include a named test such as correlation or mutual information, and where appropriate TVLA or NICV. These tests answer different questions and need their assumptions stated.

Attack success and traces-to-success show whether the measured signal supports an actual inference procedure. False positives are designs predicted to leak but not confirmed under the validation condition.

False negatives are designs whose measured leakage the model failed to predict. Both matter when the tool is used to choose what receives further security work.

The validation must cover process, voltage and temperature (PVT) conditions, process variation, clock and workload changes, and the implementation stages that change physical behavior. If no fabricated chip is available, gate-level or post-layout results can test some assumptions, but they are not a substitute for all physical leakage paths.

A transfer test across implementations, process corners or devices is needed before claiming that the estimator generalizes. In the results, false positives and false negatives should be reported in lowercase, explicit categories so a reader can distinguish a bad prediction from an untested condition.

What the baselines must mean

The timing-oblivious analysis baseline should use the same design set and leakage definition while removing the timing information, so the comparison isolates the claimed contribution. The post-silicon leakage-testing baseline should report its measurement apparatus, trace budget, noise, process and attacker access.

Runtime, model-construction cost and design-iteration cost also matter because a pre-silicon tool is useful partly by making evaluation earlier or cheaper.

The captured record reports qualitative leakage estimation only. It reports no correlation, mutual information, TVLA/NICV, attack success, false-positive or false-negative rate, timing error, trace count, runtime, power result, or process-transfer result.

Analytical models may miss physical leakage paths. The evidence supports an early timing-aware leakage-estimation direction and a validation requirement; it does not establish demonstrated physical leakage prediction.

In other words, the record supports an analytical proposal, not demonstrated physical leakage prediction.

What the attack is trying to change

A spiking neural network represents information with events distributed over time. A neuron may emit a spike when its membrane state crosses a threshold, and later layers consume the resulting event sequence.

The input is therefore not only a vector of values. It includes which events occur, when they occur, how long the sequence lasts, and how the sensor or encoder maps a physical signal into spikes.

An adversarial example is an input selected to change the network's decision while remaining within a stated perturbation budget. For an SNN, the perturbation can change spike timing, add or remove events, scale an event-related quantity, or alter the temporal pattern over several steps.

Spike-PTSD is described as a bio-plausible adversarial attack based on spike scaling. The first-principles question is therefore: what quantity is scaled, at which time steps or neurons, with what sign and magnitude, and why does the resulting sequence remain within the claimed plausibility and sensor constraints?

“Bio-plausible” is not a security metric. A perturbation can look plausible in a biological description while being impossible for the sensor, encoder, communication link or neuromorphic hardware to produce.

Conversely, a hardware-realizable perturbation may not satisfy a biological criterion. The evaluation must define these as separate constraints.

The attack chain has several distinct stages

The attack should be understood as a chain rather than one score:

  1. an attacker obtains or observes an input sequence;
  2. the attacker applies the spike-scaling rule;
  3. the modified sequence passes through the sensor, encoder and SNN interface;
  4. the network produces a changed output;
  5. the change is measured against the clean output and the task label;
  6. the perturbation cost and detectability are checked against the threat model.

Failure at any stage changes the security claim. A digital spike sequence that fools a classifier may not survive event quantization, refractory-period rules, packet timing, sensor bandwidth, clock discretization or hardware noise.

A changed output can also be a natural misclassification rather than an attack success unless the clean prediction, ground-truth label and targeted or untargeted success definition are recorded.

Threat model and attack objective

The threat model must say whether the attacker knows the model and weights, can differentiate through the spike encoder, can query the deployed model, can modify sensor values before encoding, or can directly inject digital events. It must state whether the attacker seeks untargeted misclassification, a chosen target, confidence reduction, class confusion, denial of service, or a physical-world change in recognition.

White-box, score-based black-box and decision-only black-box attacks require different budgets and should not be pooled.

The budget needs a unit. It may be an amplitude change, number of added or removed spikes, number of changed time bins, total scaled event mass, temporal displacement, energy, query count or a combination.

A budget without a normalization is not comparable across samples with different lengths, firing rates or sensor ranges. The evaluation should report the distribution of perturbation cost, not only the fraction of fooled inputs.

Preserve the temporal structure explicitly

Scaling can alter more than one property at once. It may change the number of spikes, the time at which a threshold is crossed, the membrane trajectory, the relative ordering of events, and the activity seen by downstream layers.

The paper should identify which of these changes is intended and constrain the others. For example, preserving the event count does not preserve timing; preserving average firing rate does not preserve local timing; preserving a waveform envelope does not establish that the encoder emits the same event pattern.

The attack should be tested against temporal controls: shuffled spikes, uniform scaling, time shifts, random event changes and a no-attack input. These controls help identify whether the claimed mechanism depends on scaling specifically or on a more general increase in input energy or activity.

Results should also be stratified by sequence length, baseline firing rate, class, temporal sparsity and the location of the changed events.

Gradient-based SNN attacks are a useful baseline only if they use the same knowledge, input representation, objective, success definition and budget. A clean SNN inference condition measures the unmodified error rate and is required to establish a denominator, but it is not an attack baseline by itself.

Other meaningful comparisons may include random spike perturbations, event-addition or deletion attacks, temporal-shift attacks, standard image attacks applied before encoding, and a physical sensor perturbation if deployment is the claimed setting.

Every comparison needs the same train/test or model-transfer boundary. If the attack is tuned on one set of sequences and evaluated on another, the split must be stated.

If the method is evaluated on one network and transferred to another, report source and target architectures, training data, time constants, thresholds and encoder settings. Transferability is a separate result from white-box success.

What the measurements must establish

Report clean accuracy, attacked accuracy, untargeted and targeted attack success where applicable, confidence or margin change, perturbation cost, query count, runtime and failure rate. For temporal inputs, report event-count change, changed-time-bin count, timing displacement, sequence duration and any energy or bandwidth cost.

Include confidence intervals or per-sample distributions when the dataset is small or the attack fails selectively.

Hardware realizability requires a second evaluation. Specify the sensor, spike encoder, time resolution, refractory behavior, event transport, neuromorphic processor, noise, clock and operating conditions.

Replay the generated perturbations through that path and report how many remain valid and successful. If the work is only a digital SNN experiment, it should be described as such; it does not establish a physical attack on neuromorphic hardware.

Defenses also need an adaptive test. A detector trained on clean activity may flag an obvious increase in spike activity but miss a carefully constrained temporal change.

Test rate limiting, temporal smoothing, spike filtering, input validation, adversarial training and detector combinations against an attacker that knows the defense. Report clean-performance cost, because a defense that removes the attack by rejecting ordinary temporal variation may not be deployable.

Why cross-device side-channel analysis is difficult

A side-channel model learns a relationship between an observed trace and a hidden target, such as a key byte, an intermediate value or a class of operations. The trace also contains variation that is not the target: device-specific process variation, placement and routing, probe position, clock behavior, voltage, temperature, measurement gain, noise, alignment and acquisition equipment.

A model trained on one chip can therefore learn features that identify that chip rather than features that remain useful for the secret on a new chip.

PD-Net is described as device-invariant representation learning for heterogeneous cross-device side-channel analysis. The intended operation is to transform a raw power or electromagnetic trace into a representation that suppresses device identity while retaining information about the leakage target.

These are competing requirements. If the representation removes all device-dependent variation, it may also remove the physical leakage that makes the target recoverable.

“Invariant” is useful only relative to a stated nuisance variable and a preserved security-relevant target.

Define the variables before judging invariance

Let a trace depend on at least four variables: the secret or intermediate value, the public input, the device and manufacturing instance, and the acquisition condition. A representation is useful if it reduces dependence on the device and measurement condition while retaining dependence on the target.

It is not enough to show that traces from two devices look similar in a visualization or that a device classifier performs poorly. The target decoder must remain accurate under the same transformation.

The paper needs to specify whether “device” means a different chip of the same design, a different board, a different process lot, a different implementation, or a different cryptographic core. These shifts have different causes.

A model that transfers between two chips on the same board does not establish transfer across layouts or technologies. The measurement setup must also be separated from the device so that the model is not merely learning a fixed probe or acquisition signature.

The attacker model determines the useful direction of transfer

In a profiling attack, the attacker may collect labeled traces from a device they control and then attack a target device with unknown secrets. The evaluation must state which devices are profiling devices, which are targets, what labels and keys are known during training, whether target traces are available for calibration, and whether the target key is fixed or random.

A zero-shot cross-device attack, a few-shot adaptation attack and a target-device fine-tuned attack are different claims.

The observation channel matters as well. Power and electromagnetic traces have different spatial, frequency and alignment properties.

The learned representation should preserve a measurable signal for the leakage target. This can be tested through classification or regression of the intermediate value, key rank, guessing entropy, success rate and traces-to-success.

Identify the assets before evaluating the architecture

A binary neural network (BNN) stores weights and usually reduces them to binary values, which makes multiply-accumulate operations simpler. Compute-in-memory (CIM) performs part of that operation inside or close to the memory array.

The same array that improves data movement can expose model parameters to anyone who can read cells, observe peripheral behavior, inject faults, or study power and electromagnetic activity.

CPA-BNN is described as an RRAM CIM and PUF architecture with in-situ encryption or ciphertext convolution, in-memory batch normalization, intrinsic PUF key extraction, and current-tilt masking. These mechanisms address different assets.

Model confidentiality asks whether the weights can be reconstructed. Data integrity asks whether stored or processed weights can be changed without detection.

Inference correctness asks whether the protected path produces the intended BNN result. Side-channel resistance asks whether an observer can infer the key or weights from an unintended signal.

Key security asks whether the PUF-derived secret is unique, stable, unpredictable and unavailable to the attacker. A combined architecture does not prove all five properties automatically.

What in-situ encryption must preserve

Encryption changes the representation of the stored or processed weights. The accelerator must still compute the same binary operation, or a precisely defined equivalent operation, after ciphertext handling.

The evaluation should show where encryption occurs, where decryption or an equivalent key-dependent operation occurs, and whether plaintext weights ever appear in a readable array, register, bus, sense amplifier or intermediate result.

Ciphertext convolution also needs a defined algebra. A conventional BNN may use binary XNOR and population count, while encrypted processing may require a transformed operation, extra encoding, correction terms or key-dependent accumulation.

The paper should specify the data representation, ciphertext domain, key dependency, batch-normalization placement and output decoding. Accuracy on a single task is not enough if the protected arithmetic changes the decision boundary or fails for another network size, layer type or input distribution.

A PUF is a hardware primitive with several separate requirements

A physical unclonable function derives a response from manufacturing variation. A useful key-generation PUF needs uniqueness across chips, reliability across repeated evaluations and operating conditions, sufficient entropy, resistance to modeling or prediction, and a secure enrollment and helper-data process.

“Approximately 100% key reliability” is incomplete without the number of chips, repeated trials, bit-error definition, voltage and temperature range, aging, cycling and error-correction overhead.

Reliability and uniqueness are different. A PUF that returns the same response on one chip can still return correlated responses across chips.

Conversely, a highly unique response that changes with temperature cannot serve directly as a key. Report intra-device stability, inter-device Hamming distance, entropy, min-entropy or an equivalent security measure, prediction attack results, helper-data leakage and the random-guess baseline.

The key must also be protected during extraction, storage, reset, test, debug and power cycling.

Current-tilt masking presumably changes the electrical behavior of the array or its peripherals so that secret-dependent activity is less visible. A masking claim requires a leakage model and a stated order.

A first-order result does not establish resistance to higher-order analysis, glitches, transitions, memory retention or joint observations from multiple signals.

Power and EM evaluation should use controlled fixed-versus-random or fixed-versus-fixed tests, a named leakage metric, trace count, alignment method, preprocessing, acquisition bandwidth, signal location and operating conditions. TRAC: row-activation monitoring is a security detector only if its count, threshold, and timing semantics cover the real disturbance path

What RowHammer monitoring is trying to detect

DRAM stores charge in cells arranged in rows. Activating a row repeatedly can disturb nearby rows.

Under sufficiently aggressive access patterns and device conditions, a neighboring victim row may experience bit flips. The security problem is therefore a relationship between an aggressor’s activation history, the physical adjacency and vulnerability of victim rows, the DRAM refresh and timing policy, and the controller’s ability to observe and respond before the disturbance becomes exploitable.

TRAC is described as transparent row activation counting with an ACT-triggered update, in-subarray processing, and an LFSR-based counter. The core claim is not simply that a counter exists.

It is that the mechanism observes the relevant activations, associates them with the correct rows or regions, estimates the accumulated risk with sufficient accuracy, and triggers a protective action before a victim bit flips—without breaking normal DRAM timing or imposing unacceptable cost.

Define what is being counted

An ACT command opens a DRAM row. The detector must specify whether it counts every activation, activates per bank or subarray, counts a rolling time window, resets on refresh, or uses another epoch.

It must explain how row identity is represented, how counters are allocated, and what happens when many rows are active. A count that is exact over one interval but forgets activations at a boundary can miss an attack distributed across intervals.

The threshold also needs a physical interpretation. If the mechanism uses a fixed threshold, the threshold must be below the minimum disturbance limit for the target DRAM population under worst-case conditions.

If the threshold is probabilistic or uses an LFSR-based approximation, the evaluation must quantify undercount probability, overcount probability, state period, collision behavior, reset behavior and the effect of the approximation on protection coverage. A randomized counter can reduce hardware cost, but it cannot be treated as exact without a bound on missed detections.

In-subarray processing changes the accounting boundary

Putting the update logic in or near the subarray may reduce data movement and avoid a global counter structure. It also introduces questions about area, wiring, timing, power, yield and integration.

The design must state whether the update occurs before the next ACT can be accepted, whether it extends tFAW or other timing constraints, how concurrent banks behave, and how the memory controller receives a threshold event.

“Transparent” should mean that the mechanism is on the critical path only to the extent reported and does not require software or the controller to change the security protocol. It should not mean that overhead is assumed to be zero.

Measure normal and stressed workloads, queueing, refresh interaction, bank parallelism, row-buffer locality, worst-case latency and bandwidth. A circuit-level result alone does not establish transparent system behavior.

Security coverage must use physical attack conditions

The attack suite should include single-sided and double-sided hammering, many-sided or half-double patterns where relevant, varying row distances, randomized access, different bank mappings, refresh management, throttling evasion and attacks that distribute activations across counters. It should state whether the attacker can run code locally, choose addresses, share memory, use DMA, control huge pages, disable or influence refresh, or observe timing and faults.

Security coverage requires a ground truth: which activations produce a victim disturbance on each tested DRAM device and condition, and whether TRAC detects them before the first bit flip. Report missed attacks, false alarms, detection latency, threshold crossings, protected rows, recovery action and whether the action actually prevents or only reports the error.

A count that detects a high activation rate is not enough if the device’s vulnerable threshold is lower or if the physical adjacency map differs from the assumed map.

“Correctness and stability” need separate tests

Counter correctness asks whether the recorded count matches the intended ACT stream under normal and adversarial command sequences. Stability asks whether the result remains correct over voltage, temperature, process, refresh, retention, power cycling and long operation.

Security effectiveness asks whether the detector prevents disturbance. These are different measurements.

Test command races, simultaneous bank activity, counter overflow, reset and refresh boundaries, power transitions, faulty or delayed updates, and the case where the attacker causes the monitoring state itself to saturate. If the LFSR or another approximation is randomized, repeat with multiple seeds and report confidence intervals rather than one successful trace.

If the response is a mitigation such as throttling, refresh, row relocation or isolation, include its recovery time and its effect on subsequent commands.

Compare against PRAC at equal protection

Per-Row Activation Counting (PRAC) is a meaningful baseline only when both systems protect the same DRAM population against the same attacks and use the same security target. Compare exact and approximate count semantics, threshold choice, protected-row coverage, missed-detection probability, false-positive rate, area, energy, latency, bandwidth, refresh impact and controller changes.

A smaller design that misses a class of attacks is not an efficiency improvement on the same security boundary.

The captured record reports qualitative absence of timing overhead, negligible area cost, and qualitative correctness and stability. It supplies no numeric area, energy, latency, security coverage, false-positive rate or disturbance threshold, and it does not specify the RowHammer threat model, DRAM generation or process.

The evidence supports an in-subarray row-activation-monitoring direction, not demonstrated RowHammer prevention under a defined device population and adversarial command set.

Shooting Falcon with One Fault: a single-bit fault claim must connect DRAM disturbance to key recovery

The attack crosses three security boundaries

Falcon is a lattice-based digital-signature scheme. A signer uses secret material to compute a signature for a message, and a verifier checks the signature with a public key.

The security question in this paper is not whether an ordinary Falcon signature verifies. It is whether an attacker can cause a precise fault in the signer’s memory, observe the resulting faulty signature or failure behavior, and collect enough information to recover the signing secret.

The described attack has three separate boundaries:

  1. RowHammer must induce a controlled bit change in a memory location used by Falcon.
  2. The fault must survive the implementation’s computation and produce a useful faulty signature or other observable.
  3. The cryptanalytic recovery procedure must convert a stated number of useful faults into the secret key with a stated probability.

A result at one boundary does not prove the others. A bit flip in memory is not automatically a useful cryptanalytic fault.

A simulated useful fault is not automatically a practical RowHammer attack. A recovery algorithm that works on selected faulty signatures is not automatically a key-recovery attack against every Falcon implementation.

Define the fault model precisely

The record describes a single-bit flip and vulnerable-address discovery. The evaluation must identify the exact memory object, byte and bit, when it is used, whether the bit changes from zero to one or one to zero, and whether the fault is transient or persistent.

It must say whether the attacker can choose the address, map pages, observe physical addresses, allocate memory near the target, trigger signing operations, repeat the hammer pattern and detect a successful fault.

The memory placement is part of the attack. Virtual adjacency does not necessarily imply DRAM-row adjacency.

The page allocator, huge pages, physical address mapping, bank and row functions, memory deduplication, cache state, refresh policy and row remapping determine whether a vulnerable address can be found and used. Vulnerable-address discovery may require a separate calibration phase and may fail after reboot, migration, page retirement or a change in DIMM.

The platform description must include DRAM generation, module or chip population, row-buffer organization, refresh settings, timing parameters, CPU and memory controller, operating system, privileges, core placement and mitigations. Hammering time and resource cost are part of practicality.

A fault that requires privileged access or a long offline calibration is a different threat from an unprivileged remote signing attack.

A faulty signature is not just a corrupted output

The cryptanalytic step depends on where the fault enters the signing computation. A fault in a secret coefficient, an intermediate polynomial, a random sampler, a norm check or a public value can have very different consequences.

The paper should map the physical bit flip to the logical variable and show why the resulting signature leaks a constraint on the secret rather than merely failing verification or producing an unrelated invalid output.

The evaluation should report the fraction of induced faults that yield usable faulty signatures, the fraction that verify under the attack’s acceptance condition, the rejection and abort behavior of the implementation, and the number of signing queries and discarded attempts. A count of 250,000 faulty signatures is meaningful only if “faulty,” “usable,” and “collected” have precise definitions and the attacker can recognize them without already knowing the secret.

Key recovery needs a reproducible denominator

The HPP cryptanalytic recovery workflow named in the record must state its input assumptions, equations or solver behavior, preprocessing, required fault pattern, memory and runtime, and success criterion. Report the number of independent trials, recovered keys, failed recoveries, confidence interval, and whether the public key verifies the recovered secret.

If the method uses an optimized subset of faults, disclose the selection rule and the percentage discarded.

The comparison with the state of the art must hold the implementation, Falcon parameter set, fault model, signing procedure, attacker knowledge, acceptance rule and success probability constant. “800x fewer faulty signatures” can arise from a stronger fault model, a different definition of a fault, a lower success threshold, reuse of information across signatures, or a more favorable implementation.

It is not an intrinsic 800x improvement until those conditions are matched.

Check the implementation, not only the scheme name

The record names Falcon-512 reference implementation, but the security of a fault attack depends on the exact version, compiler, optimization, memory layout, arithmetic representation, random-number generation, rejection sampling, constant-time protections and fault checks. A defense that recomputes or verifies intermediate values may turn a useful fault into a detected failure.

A compiler or allocator change may move the target away from the discovered vulnerable row.

The evaluation should test multiple builds and layouts, fresh processes, ASLR states, compiler settings, operating-system versions, DRAM modules and Falcon implementations. It should report whether the attack transfers across devices and whether memory scrubbing, replication, signature verification, redundant computation, RowHammer mitigations or fault detection reduce recovery success.

If transfer is not demonstrated, the result should remain scoped to the tested platform and binary.

The captured record reports 250,000 faulty signatures for secret-key recovery, an 800x reduction relative to the stated prior work, and a single-bit flip attack. It does not state attack success probability, hammering time, privilege model, DRAM platforms or repeatability, and the 800x comparison requires matched implementation and fault-model conditions.

The evidence supports a promising RowHammer-to-Falcon fault-attack direction, not demonstrated practical key recovery across platforms or Falcon implementations.

Slcross: a cross-component cache channel needs separate evidence for communication, inference, and deployment reach

Identify the shared resource and the observation

A cache side channel exists when one component changes a shared cache state and another component observes the change through timing, contention, evictions, or another measurable effect. On a heterogeneous SoC, the components may use different instruction sets, execution units, drivers and privilege domains while still sharing a system-level cache or interconnect.

The security boundary is crossed only if the observer can distinguish the victim-dependent states with the access it actually has.

Slcross is described as reverse engineering system-level-cache mechanisms on an Apple M2 SoC, enabling GPU-to-CPU covert communication and an inference-time attack on an embedding table. These are related but different results.

A covert channel demonstrates that a sender and receiver can exchange information through a shared resource. An inference attack demonstrates that the observed signal correlates with a sensitive workload and can be decoded.

Neither result alone establishes a general remote data-extraction attack.

Reconstruct the channel in stages

The mechanism should be described as a causal sequence:

  1. a sender or victim accesses cache lines or other shared structures;
  2. those accesses change the SLC state or contention;
  3. a receiver performs a probe or timing measurement;
  4. the measurement is synchronized and classified into a symbol or secret-dependent event;
  5. repeated observations produce a communication rate or an inference result.

Each stage has failure modes. Replacement policy, set mapping, inclusivity, coherence, prefetching, GPU scheduling, memory compression, quality-of-service rules and OS activity can change the signal.

A CPU receiver may not observe the same state as a GPU sender. A reverse-engineered cache mapping is a hypothesis until access patterns, eviction behavior, associativity and timing distributions are measured across relevant addresses and workloads.

The covert-channel result has its own metrics

Report bit rate, symbol rate, raw and corrected error rate, synchronization method, channel occupancy, trial count, confidence intervals and the sender and receiver resources used. State whether the sender is a cooperative process, a victim workload or a malicious GPU kernel, and whether the receiver can run concurrently.

Include the time required to establish cache mappings and the effect of scheduling interruptions.

The receiver’s privilege and API access are central. A channel available to two processes on one user account is different from a channel available across users, sandboxes, browser contexts, virtual machines or remote clients.

The evaluation must identify whether GPU command submission, shared buffers, performance counters, high-resolution timers, shared memory, driver permissions or elevated privileges are required. A local covert channel should not be described as remote leakage without an additional network or service boundary.

The embedding-table attack is a separate inference problem

An embedding table maps tokens or indices to vectors. A cache observation may reveal which rows are accessed, how often they are accessed, or some property of the GPU execution.

To claim sensitive GPU-information leakage, the work must define the secret target: token identity, sequence content, embedding index, model architecture, intermediate value or another property. It must state whether the attacker knows the model, controls prompts, sees outputs, can schedule a concurrent workload, and has labeled training traces.

Report classification accuracy, precision/recall or rank quality as appropriate, sample complexity, observation window, target vocabulary or candidate set, false positives, false negatives and the clean workload error. An accuracy number without the candidate-space size and random baseline does not establish useful information recovery.

If the attack only distinguishes a small set of hand-selected prompts or embedding accesses, the conclusion must stay at that scope.

Noise and workload conditions determine generality

System-level cache observations are affected by other CPU and GPU activity, memory traffic, prefetching, thermal and frequency changes, OS scheduling, driver behavior, display workloads and concurrent users. Test controlled idle conditions separately from realistic noisy workloads.

Vary core allocation, GPU occupancy, kernel size, batch size, model phase, request timing, cache state and observation duration. Hold out prompts, models, kernels and time periods so that the classifier cannot memorize a fixed execution schedule.

Apple M2 is a concrete platform, not a universal cache architecture. The evaluation should identify the chip revision, OS and driver versions, memory configuration, performance-state policy and software permissions.

Transfer to another M-series generation, another OS release or another GPU/CPU system requires its own measurements. A reverse-engineered mechanism may be informative without being stable after a firmware, driver or scheduling change.

Mitigation must be tested against an adaptive observer

Possible mitigations include reducing timer resolution, partitioning or flushing shared cache state, changing GPU scheduling, limiting cross-domain resource access, adding noise, and preventing untrusted concurrent kernels. Each can reduce the signal while imposing performance or usability cost.

Evaluate the same channel after mitigation and give the attacker knowledge of the defense. Report residual bandwidth, inference accuracy, false alarms, latency, throughput and energy, not only whether one probe stops working.

The captured record qualitatively demonstrates a cross-component covert channel and sensitive GPU-information leakage through an Apple M2 SLC, but supplies no bandwidth, error rate, attack accuracy, sample complexity, privilege requirement or mitigation analysis. The generality beyond Apple M2 and the selected LLM embedding workload is unknown.

The evidence supports a platform-specific cross-component cache-channel direction, not demonstrated general or remote leakage.

DM-MARK: watermarking authorization requires robustness and provenance evidence separate from accelerator speed

State what the watermark is meant to prove

A diffusion model generates an image or another output through a sequence of denoising steps. A watermarking system changes the model, the generation process, the output, or a combination of them so that a detector can later identify an authorized source or usage condition.

That creates several distinct questions: does the watermark survive ordinary transformations, can an attacker remove or forge it, does the detector avoid false accusations, and does the detected mark establish authorization rather than merely model identity?

DM-MARK is described as a software-hardware co-designed diffusion watermarking framework with a 12 nm FinFET accelerator for watermark generation and reverse detection. “Generation” and “reverse detection” need precise definitions.

The evaluation should identify where the mark is inserted, what secret or key controls it, whether it is embedded in latent values, denoising noise, model weights, or the final image, and whether the detector has access to the model, the key, the generation trace, or only the output.

Authorization is a protocol, not only a classifier score

An authorized-usage system needs an enrollment and verification protocol. It should state who creates the key, where it is stored, how a detector obtains trusted reference information, how keys are rotated or revoked, and what evidence is retained for a dispute.

If the detector only recognizes a statistical pattern, an attacker who can train a surrogate or copy the pattern may forge the mark. If the watermark is tied to a secret key, the key-management and compromise boundaries determine the security claim.

The security properties should be separated: authenticity of the source, ownership attribution, detection of unauthorized generation, traceability of a user, and tamper evidence are not interchangeable. A watermark can be robust to compression while remaining forgeable.

A high detector accuracy can coexist with a high false-positive rate on outputs from unrelated models. The paper must define the decision, the protected asset, and the consequence of a false positive or false negative.

Robustness needs an explicit attack set

Diffusion outputs can undergo resizing, cropping, recompression, color changes, denoising, filtering, inpainting, outpainting, re-generation, latent editing, prompt changes, model fine-tuning, distillation, watermark overwriting and collusion. The evaluation should specify which transformations are in scope and their severity.

It should include an adaptive attacker that knows the detector and attempts removal or forgery, not only benign image processing.

Report detection true-positive rate, false-positive rate, false-negative rate, ROC or precision-recall behavior, confidence calibration, and performance by transformation and content type. State the clean unwatermarked distribution, watermark strength, image quality metric, sample count and decision threshold.

“11.33% higher detection accuracy” is not interpretable without the original accuracy, class balance, confidence interval, attack condition and whether the increase trades off image quality or false alarms.

Quality and security can conflict. A stronger mark may improve detection while changing generated content, reducing diversity, increasing artifacts or making the mark easier to identify and remove.

Measure fidelity, perceptual quality, semantic preservation, diversity, generation success, watermark strength and detector performance together. If the system protects a diffusion model rather than individual outputs, test whether model extraction or fine-tuning preserves or removes the mark.

The accelerator boundary must be complete

The 12 nm FinFET implementation should state whether the reported latency and memory values cover only the watermark module, reverse detector, denoising pipeline, on-chip buffers, external memory, host communication, key handling, initialization and post-processing. A GPU comparison must use the same model, resolution, precision, batch size, number of diffusion steps, detector threshold and output quality.

A baseline ASIC comparison must use the same technology assumptions, area boundary, frequency target, memory, process libraries and design constraints.

The reported 18X GPU latency speedup, 3.1X on-chip-memory savings, 4.56X EMA reduction and 212.5X speedup over a baseline ASIC are ratios whose denominators need definitions. “EMA” is not defined in the captured record; it might refer to an energy, memory, or another implementation metric, and the paper must identify the quantity and units.

Report absolute latency, throughput, area, power, energy per generated or detected output, off-chip traffic, memory capacity, frequency, utilization, yield assumptions and accuracy/quality at that operating point.

Deployment and failure handling matter

An edge device may operate with intermittent connectivity, limited secure storage and multiple users. The design should state how keys survive reset, how detector failures are handled, whether outputs remain usable when verification is unavailable, and whether an attacker can replay a valid marked output.

If the application treats a watermark as authorization, the system must define what happens when the mark is missing, ambiguous, copied, or detected with low confidence.

The captured record identifies a diffusion watermarking framework and a 12 nm accelerator and reports an 11.33% detection-accuracy increase plus several speed and memory ratios. It does not identify watermark attacks, quality metrics, exact EMA definition, device configuration, or area/yield conditions.

The evidence supports an accelerator and watermarking direction, not demonstrated robust authorization, forgery resistance, or normalized end-to-end edge efficiency.

Icarus’s Wings: an MoE slowdown claim must connect prefix construction to a reproducible offloading bottleneck

The system being attacked

Mixture-of-Experts (MoE) models contain many expert networks, but a token is routed to only some of them for each layer. This can reduce arithmetic work, yet storing every expert in fast memory may be too expensive.

An offloading system keeps some experts in GPU memory and moves others from slower memory when the router predicts that they will be needed. Prefetching is useful when the next requests have enough temporal locality for the prediction to be correct.

The security problem is an availability problem: an attacker wants to cause unnecessary expert movement, cache replacement, memory traffic, or synchronization so that legitimate decoding becomes slower. Icarus’s Wings is described as a gradient-based universal hidden-prefix attack that minimizes temporal locality, misleads expert prefetching, and uses a target-balancing scheduler.

The important causal chain is not simply “a prefix is adversarial.” It is: the prefix changes routing or request timing; the offloader makes different placement and prefetch decisions; those decisions increase replacement and transfer work; and a victim’s service quality degrades under a stated multi-user condition.

Define the attacker’s control

The attack model must state whether the attacker submits ordinary prompts, controls hidden-prefix tokens, chooses request order, shares a GPU, observes latency, knows the model and router, or can coordinate several users. A universal prefix may be reusable across inputs, models or devices, but each form of universality needs its own held-out test.

Controlling a prefix in one request is not the same as controlling the scheduler, cache state, or other tenants’ requests.

The paper should identify the computation needed to construct the prefix, its length, token restrictions, number of optimization steps, gradient access, queries, storage, and whether the prefix is visible to the victim. If the attack requires model weights or internal router outputs, it is a white-box attack.

If it can be produced from latency observations or public APIs, that is a different and stronger deployment claim.

Separate the three reported effects

An 85.4% increase in cache replacements is a mechanism-level observation. It shows more replacement events under the tested condition, but it does not by itself show that useful requests are delayed or that an attacker can sustain the condition.

A 12.5% reduction in prefetch accuracy measures prediction quality only if the prefetch target, prediction horizon, top-k rule, denominator and workload are defined. A 0.7X decoding speed is an outcome metric, but its baseline, token length, batch size, quality, throughput and whether the victim or attacker is being slowed must be stated.

The evaluation should report cache hit/miss rates, expert residency, transfer volume, PCIe or interconnect traffic, queue time, GPU utilization, memory bandwidth, first-token and per-token latency, throughput, tail latency and energy. Measure the victim’s service separately from the attacker’s cost.

Maximum-length outputs can make a slowdown look larger than it would be for short requests; report multiple sequence lengths and stop conditions.

Baselines and denominators matter

The unattacked MoE offloading condition establishes ordinary performance. A caching/prefetching baseline establishes what the system assumes about locality.

Stronger comparisons should include random prefixes, ordinary long prefixes, adversarial but non-universal prefixes, request-order attacks, cache-thrashing workloads and alternative offload policies. All conditions need the same model, device, batch, memory capacity, precision, request mix, concurrency, output length and scheduler.

The “0.7X decoding speed” statement needs a direction and denominator. If speed is normalized throughput, 0.7X means a 30% reduction; if it is latency expressed as a ratio, the interpretation differs.

Report absolute values and confidence intervals. A 12.5% prefetch-accuracy loss may have little service impact if transfers overlap with computation, or a large impact if they serialize the critical path.

The system-level result must establish which case occurs.

Test generalization and defenses

“Universal” should be tested across held-out prompts, users, sequence lengths, model checkpoints, expert counts, routing policies, devices, offloading implementations and request schedules. A prefix that transfers across prompts but not across models is input-universal, not system-universal.

The locally discovered repository for this record contains a pinned README and demonstration image, but no recovered full paper or executable attack; its README findings therefore do not replace the missing experimental conditions.

Defenses should be evaluated against an adaptive attacker. Options include admission control, per-tenant rate limits, cache partitioning, randomized prefetching, expert replication, scheduling isolation, traffic shaping, detection of abnormal routing or replacement patterns, and fallback execution.

Report clean performance, false alarms, residual slowdown, attacker cost and whether the defense shifts the bottleneck to another resource.

The captured record reports an 85.4% increase in cache replacements, a 12.5% reduction in prefetch accuracy and 0.7X decoding speed for maximum-length outputs, but does not enumerate models or devices, attack cost, attack success rate or defenses. The additional repository assessment confirms only artifact discovery: the pinned repository has a README and image, no recovered full paper, and no executed demo.

The evidence supports a plausible MoE offloading denial-of-service direction, not demonstrated universal or deployment-general attack impact.

What a useful comparison reports

State the protected asset, allowed observer actions, available measurements, and required outcome. Report successful and failed cases, false alarms where applicable, measurement cost, and protection overhead. Keep device configuration, software versions, and input conditions explicit.

Then vary the conditions on which the method relies. The scientific conclusion should identify which observation or invalid action the method prevents, under which assumptions, and at what cost. That supports informed transfer to another system while preserving the tested boundary.

Energon: infer transformer structure from GPU sensors that were not intended as a model interface

The leaked object is architecture, not a model output

A model API returns a prediction that the service intends a user to see. Energon studies a different observation: power and temperature reported by a GPU while another user's model runs.

The attacker does not need the model's weights or output API. The proposed inference target is architectural information such as the number of encoder/decoder layers, attention heads and model family.

This distinction matters because architecture is not the same as a complete model. Learning that a target resembles one T5 variant does not recover its training data, weights, tokenizer, prompt, or exact learned function.

It can nevertheless reduce the uncertainty an attacker faces when building a substitute model or choosing a transfer attack. The paper's security claim is therefore about information leakage that makes later attacks more informed, not direct extraction of all model parameters.

The threat model depends on shared physical sensors

The paper considers multiple users on a remote GPU service. The victim runs an unknown transformer in one virtualized instance. The adversary runs ordinary software in another instance and reads power or thermal data using nvidia-smi or pynvml, without root privileges. The paper argues that these readings come from physical sensors and remain visible even when compute, memory and bandwidth resources are separated by NVIDIA virtualization/MIG.

The important assumption is cross-instance observability. The attacker does not need to execute inside the victim's process, read its memory, or invoke its API, but does need a sensor view that reflects activity on the shared physical GPU.

If a provider removes or coarsens that view, changes sensor sampling, adds aggregation noise, or gives each tenant a physically separate device, the measured attack surface changes. The experiment therefore demonstrates a risk under this sensor-access model; it is not a claim that every cloud GPU configuration exposes the same signal.

Why transformers produce a useful trace

An encoder processes a fixed input sequence in parallel and produces a representation. A decoder then generates output tokens one at a time, using an expanding context.

The paper's custom-model traces show a staircase pattern: a smaller encoder-related rise followed by repeated decoder steps whose power increases as the generated sequence grows. The authors report roughly 6 W during the custom encoder phase and up to 20 W during decoder execution on the GTX 1660 Ti Mobile experiment; the exact trace is a device and sampling result, not a universal transformer signature.

The number of repeated steps and the size of each computation depend on layer count, attention-head count, embedding dimension and input/output behavior. Temperature changes more slowly than instantaneous power because the GPU and package have thermal capacity.

That makes temperature a lower-bandwidth but potentially longer-lived observation. Energon uses both traces as features for a learned classifier rather than treating either signal as a direct readable layer counter.

The measurement protocol is part of the result. The custom gradient analysis attempted higher sampling rates but settled at 7 Hz, stabilized the initial GPU temperature around 28 °C, and allowed the device to cool between traces.

For the main extraction experiments, the paper collected 100 traces per model over 120 seconds, used an 80:20 train/test split and stratified K-fold cross-validation. Cooling helps reduce carry-over between laboratory traces, but it is not necessarily available to an attacker observing a continuously running service.

Conversely, long traces and repeated measurements can make a real attack easier than a single isolated run.

The inference pipeline has several classification stages

Energon trains a convolutional classifier with three convolutional layers, batch normalization, ReLU, two max-pooling layers and fully connected output layers. For custom language transformers, it first predicts attention-head count and then predicts encoder/decoder layer count within the relevant head family.

This hierarchy reduces a large classification problem into questions whose labels correspond to visible trace structure.

Worked example

The custom language set contains nine configurations: 6/8, 12/8, 12/12, 12/16, 24/16, 32/16, 48/16, 24/32 and 32/32, where the first value is the encoder/decoder layer count and the second is attention heads. The reported attention-head classification reaches 100% on the tested 8- and 32-head groups and 96.25% on the 16-head group.

Those are held-out test results from a finite set of known configurations; they do not establish reliable interpolation to an unseen architecture outside the training families.

For eight pre-trained language models from T5, Google, MarianMT and Meta, the root-family classifier reports a maximum of 95% and a five-fold average of 89%. Within selected families, T5 attention-head identification and Meta encoder/decoder identification are reported at 100% average accuracy.

This family-conditioned result is narrower than “architecture can always be recovered”: the classifier uses prior knowledge about which families and variants are possible.

For vision transformers, the paper studies eight models from Apple, Google, Meta and Microsoft using CIFAR-10-derived inputs. The root-family classifier reports maximum/average accuracy of 91.25%/84.75% across five folds, while family-specific attention-head classifiers for Meta, Google and Microsoft report 100%.

Again, the family-specific labels and the selected model catalog define the denominator.

Noise changes the question from recognition to robustness

The paper evaluates concurrent workloads in a partitioned GPU setting. With transformer inference and matrix multiplication running in parallel, family identification averages 89.25%; Meta and T5 architecture distinctions are reported at 92% and 87%.

The authors also run three and four concurrent processes and report only a small performance reduction for several tasks. With different background categories—matrix multiplication, CNN inference and vision-transformer inference—the matrix-multiplication condition produces a reported 4% drop in root-family identification.

These experiments show that the signal is not immediately destroyed by the tested noise. They do not establish robustness to all co-tenants, arbitrary request timing, sensor quantization, workload scheduling, GPU generations, driver versions or cloud monitoring policy.

A noise experiment is meaningful only with the background process, concurrency, trace alignment and training/test separation stated.

The downstream attack is a separate experiment

Energon uses extracted architecture to build a substitute MarianMT model. When encoder/decoder count and attention heads are recovered, the substitute obtains a reported BLEU score of 44.12 and BERT score of 93.53 in one target/substitute setting.

When embedding dimension or feed-forward size remains unknown, the table reports BERT scores of 93.08 and 93.53 for the listed alternatives. These scores measure output similarity under that experiment; they do not prove weight recovery or equality of internal representations.

For vision transformers, the authors construct substitutes and generate FGSM/PGD examples. The listed Google ViT results range from 83.38% to 98.63% success, with the paper summarizing an average around 93%.

Attack success depends on the target models, data, perturbation method, substitute training and success definition. It is evidence that partial architectural leakage can aid transfer attacks, not a universal attack rate against all transformers.

What the paper establishes and what remains open

Energon establishes a concrete side-channel chain under its stated conditions: GPU sensor traces correlate with transformer structure; a CNN can classify selected model families and architectural parameters; tested background processes do not remove the signal; and recovered structure can support a substitute model or transfer attack. The paper reports responsible disclosure to NVIDIA and suggests restricting sensor access, exposing coarser metrics, warning or throttling users, and obfuscating architecture through model variants.

It does not establish that every NVIDIA GPU, MIG layout or cloud provider leaks the same information, that the classifier works without family knowledge, that traces remain separable under all sensor policies, or that an attacker can recover weights or training data. The train/test split is among collected traces from selected models, so a stronger evaluation would hold out entire architecture families, devices and software stacks, measure attack cost and sample count, and test whether mitigations reduce inference without making GPU management unusable.
