These are not eight interchangeable ways to measure whether a language model is good at chip design. They act on different objects.

A configuration search chooses within an existing tool interface; changing the tool itself can affect future designs that were never in the search. Generating a learned reward changes training incentives; repairing a routed design changes a physical artifact directly.

Their failure modes and verification costs therefore differ.

The common design question is where to place a machine-generated proposal relative to a trusted check. A proposal can narrow the next search or suggest a revision without being accepted as correct.

The check needs to assess the resulting object under the original requirements. If the requirements, testbench, reward and generated candidate all inherit the same mistaken assumption, agreement among them is weak evidence.

Three long-term hypotheses follow from this comparison, not from a measured historical increase. First, structured proposals may make failures easier to locate when their fields have explicit meanings and independent validity checks.

This would weaken if structure merely relocates errors into unchecked relationships. Second, implementation feedback may improve practical choices when the report belongs to the exact candidate and its constraints remain fixed.

This would weaken if apparent gains disappear after integration or matched evaluation. Third, learned guidance may reduce repeated search work when training cost is reused across sufficiently many unfamiliar tasks.

This would weaken if gains depend on benchmark familiarity or expensive per-task repairs.

Testing those hypotheses over time requires comparable task families, source access, tool and model versions, budgets and acceptance rules across editions. This chapter combines ICCAD 2025 fallback records with DAC 2026 records; that difference alone cannot establish a shift from one approach to another.

Unavailable manuscripts and the selected-paper sample also prevent treating these eight records as field-wide proportions.

A language model produces text or structured output from its input context. In chip design, that output might be hardware-description code, a tool command, a suggested layout change, or a set of compiler settings.

The output becomes useful only when the surrounding process can interpret it, execute it, and check the resulting design.

The design flow therefore includes more than the model. It includes the specification, the information supplied to the model, the permitted actions, the design tools, and the rule for accepting an output. Changing any of these can change the measured success rate.

Information supplied to the model affects the claim

Retrieval-augmented generation supplies selected reference material with a request. In a design application, that material could include design rules, examples, or tool documentation. Retrieval can make relevant information available, but it does not establish that the material is complete, current, or correctly applied.

An evaluation must identify which references the model could access and how they were selected. A method with task-specific examples or manually prepared rules has different preparation costs and transfer assumptions from one evaluated with only a general specification.

Drcagent proposes physical-design repairs

Drcagent's captured description combines design-rule information, a language model, and feedback from electronic-design tools to repair violations. A design-rule check evaluates whether physical geometry satisfies specified manufacturing constraints. Repairing one violation can change nearby geometry and create another. Recorded evidence

The useful outcome is a valid repaired design under the full relevant checks, with the original circuit intent preserved. The record does not establish violation coverage, closure rate, runtime, final layout quality, or transfer across processes.

A multi-turn repair loop by itself does not establish any of those outcomes.

Generated code needs several kinds of checking

The two-tier Verilog-generation record combines retrieved information, classification, prompting, simulation, review, and hardware-performance checks. Verilog describes circuit behavior and structure. A valid text representation can still implement the wrong function, and a functionally correct description can produce an unsuitable circuit after synthesis. Recorded evidence

Separate syntax acceptance, simulated correctness, synthesis completion, and implemented hardware quality. Report how many outputs fail each step. A system that accepts fewer but better designs may have a different useful result from a system optimized for generating many syntactically valid candidates.

Paretopilot chooses synthesis settings

High-level synthesis constructs hardware from a higher-level program and settings that influence parallelism, resource use, and scheduling. Paretopilot's captured method uses a language model to guide exploration of these choices. Recorded evidence

Several objectives can conflict. A candidate may be faster but larger.

A Pareto (Pareto front: the designs that no other design beats on every cost at once) set contains candidates for which no other evaluated candidate is at least as good on every objective and better on one. The quality of that set depends on the objectives, evaluated candidates, and budget.

The current description does not establish enough of those conditions to interpret its reported improvement as a generally better search.

Count the work needed to obtain an accepted design

A complete budget includes preparing references, model calls, tool execution, failed attempts, repairs, and human intervention. If training or task-specific tuning is required, state whether that cost is included and how often the resulting method is reused.

Compare the same tasks and acceptance rules. Preserve model and tool versions, prompts or interfaces, and failure records.

Test unfamiliar designs and conditions. The strongest conclusion identifies which part of the design process improved, what feedback caused the improvement, and what work still requires a separate correctness or physical check.

VERIRL: improve a generator without confusing its reward with circuit correctness

What the inspected preprint establishes

Selected method and evaluation sections of version 1 were read on 2026-09-08. No training, repository code or generated RTL was executed; conference-version and artifact reconciliation remain open. The current reading card below includes this extraction; the original captured fields remain available in its disclosure.

VERIRL trains a policy with a learned reward model. Its trace-back procedure replaces an internal candidate's score with the mean of its children's scores; sample balancing adjusts learning contributions using probability and reward. Sections III, V–VI; trace-back on PDF page 5

Evaluation uses twenty samples per task and pass@1/pass@5. Table II reports CodeQwen2.5-based VERIRL at 69.3/78.1 on VerilogEval-human and 58.2/66.0 on RTLLM v1.1. Inference selects the best results across three temperatures. Sections VII-D–F and Table II, PDF pages 7–8

These are functional benchmark results, not measured circuit power, area or timing. The independent examples below explain why training scores, repair success and final acceptance need separate meanings.

The trained object is a probability distribution over outputs

A language model generates a sequence by assigning probabilities to possible next tokens. For a hardware task, the sequence includes a proposed implementation. Training changes which implementations are likely to be generated; it does not directly change the circuit already produced on a previous attempt.

A policy is the model used to choose outputs. A reward is a score used to guide learning.

A reward model is a learned function that predicts a score from the task and candidate. Executing a testbench is a different operation: it runs selected input sequences and checks the circuit's responses.

Predicted quality and observed test outcome can disagree.

Worked example, with the numbers

from the papers
  1. Suppose a generator produces two candidates. A receives predicted reward 0.9 but fails a required reset test.

B receives 0.7 but passes all the available checks. The reward ranking prefers A; the observed test outcome favors B.

Training can improve prediction quality, but calling the score a reward does not make it an authoritative correctness decision.

Sparse feedback can hide useful distinctions

An all-or-nothing test outcome may assign zero to both a program that does not parse and one that computes nearly every tested case correctly. Their next repairs may be very different.

More detailed observations can help distinguish missing syntax, incorrect output width, wrong state transitions and output-cycle errors.

However, counting passed tests does not automatically measure how close a circuit is to correct. Consider ten tests: nine exercise ordinary addition and one checks overflow.

A circuit passing nine receives 90% test success but still violates a required case. Duplicating the ordinary tests could increase the percentage without improving the implementation.

Coverage and severity do not arise from the denominator alone.

The original specification must therefore remain visible when test results become training labels. Multiple generated testbenches can share the same omission. Agreement across tests is more useful when they exercise genuinely different requirements than when they restate one easy case in different code.

Repair potential and present correctness answer different questions

For an independent tree example, candidate A initially passes none of its tests. Two revised children pass all tests and 80% of tests respectively.

Averaging the children's scores gives 0.9. That can express usefulness as a starting point for the particular repair process; it is not A's own measured pass rate.

The distinction matters when constructing preferred and disfavored training pairs. A high score inherited from repairs may encourage outputs that lead to good repairs, rather than outputs that already pass.

Whether that helps one-shot generation depends on the data representation and the learning procedure. It cannot be settled by changing the score's name.

To evaluate this boundary, retain candidate identities, original test outcomes, repair histories and inherited scores as separate fields. Test final sampled outputs independently of the scorer used in training.

These are proposed checks, not claims that the released implementation mislabels its results or that its reported benchmark gains are invalid.

Probability and reward are not the same kind of confidence

Generation probability says how likely the current model is to emit an output under the sampling process. Reward says how desirable a scorer judges it. A common output may be consistently wrong, while an uncommon output may implement an unusual requirement correctly.

An adaptive weighting scheme changes how much particular examples influence an update. Increasing attention to promising rare cases may help the model learn beyond frequent patterns.

Reducing the influence of persistently uninformative cases may reduce noise. But unusual valid behavior can also look rare, and scorer mistakes can make invalid behavior look promising.

For a simple illustration, suppose a batch has ninety routine cases and ten unusual cases. Optimizing only the overall mean can improve ninety answers while degrading all ten unusual ones.

A weighted objective can expose that imbalance, but it still needs trustworthy labels and evaluation on the relevant task categories. A balanced numerical objective is not itself a guarantee of generalization.

Understand what multiple-attempt success measures

Pass@1 concerns one sampled solution; pass@5 concerns whether at least one of five sampled solutions succeeds. A higher multiple-attempt score can be useful when the user can afford to generate and test alternatives.

It does not say the system can identify the successful candidate without those checks.

Worked example, with the numbers

from the papers
  1. For an independent finite-sample calculation, suppose twenty generated candidates contain four passes. A uniformly chosen single candidate succeeds with probability 4/20 = 0.2. Choosing five distinct candidates from that set has success probability 1 − C(16,5)/C(20,5), approximately 0.718. Here C(n,k) counts the ways to select k objects from n without regard to order. The difference reflects additional chances, not a change in any candidate's correctness.

Do not replace that finite-sample calculation with an assumption that every attempt is independent and has identical success probability unless the measurement supports it. Models can repeat the same wrong structure. Record sampling settings, candidate count, testing cost and selection procedure when comparing methods.

Choosing the best setting using the evaluation results adds another selection step. A transferable deployment claim should distinguish a setting chosen on separate validation tasks from a best-of-settings result on the reported benchmark. Neither is inherently meaningless; they estimate different procedures and require different budgets.

Dataset filtering does not prove independence from evaluation

Removing near-identical text helps reduce one form of duplication. It does not ensure two differently worded problems require different circuits. Conversely, similar text can specify importantly different behavior, such as a different reset polarity or output cycle.

An independence check should follow problem provenance and semantic overlap as far as the evidence allows. It should also distinguish training examples, reward-training pairs, repaired descendants and evaluation tasks.

A large count of pairs can contain repeated information from a much smaller number of underlying problems.

Training and evaluation costs also serve different purposes. Preparing testbenches, exploring repair branches and training a scorer are preparation work.

Generating a new candidate and checking it are per-task work. Any claimed engineering saving needs both, with the intended number and variety of future tasks stated.

Connect training improvements to implementation requirements

VeriOpt discusses using implementation feedback to improve RTL costs. VERIRL's inspected evaluation concerns functional generation. Better functional sampling can supply more usable starting candidates to a later implementation flow, but does not establish that those candidates satisfy area, power or clock constraints.

The bounded hypothesis is that informative, correctly interpreted training feedback can increase the chance of obtaining usable RTL on unfamiliar tasks. It weakens if rewards mainly predict benchmark-specific test behavior, if repair-derived labels do not transfer to final outputs, or if gains vanish under matched sampling budgets.

Source-to-artifact consistency, broader test coverage, dataset independence, reproduced measurements and independent comprehension review remain open.

VeriOpt: improve implementation cost without changing the required behavior

What the manuscript actually supports

The version-1 preprint was inspected on 2026-09-08, including method, evaluation tables and limitations. This is manuscript reading, not execution or verification of a conference camera-ready version. The current reading card below includes the inspected conditions and preserves the original abstract-backed fields in its disclosure.

VeriOpt assigns planning, programming, reviewing and evaluating roles, then supplies optimization context and synthesis reports. Section V-C explicitly describes manual external synthesis feedback. Sections III and V-C; limitations on PDF page 8

Evaluation uses GPT-4o, Icarus Verilog, Design Compiler and RTLLM; Table II reports 25/29 testbench passes. PPA (power, performance and area: the three main costs of a chip design) baselines are the flow's functionally passing pre-optimization designs. Section IV-A and Table II, PDF pages 6–7

Table III's 73.23% is critical-path reduction for the 16-bit divider. Some leakage and slack (time to spare before a signal would arrive too late) entries worsen.

Its 90% slack improvement for the four-bit pipelined multiplier also exceeds the prose's stated 39.44% maximum. Preserve that discrepancy rather than silently harmonizing it. Table III and Section IV-C, PDF pages 7–8

The independently constructed examples below explain how to read those boundaries. They are not recreated VeriOpt circuits, simulations, or measurements.

Define behavior before optimizing its implementation

Register-transfer-level code, or RTL, describes how stored state and combinational logic determine a circuit's outputs. Combinational logic calculates from its current inputs.

Registers preserve values between specified clock events. For a sequential circuit, correctness concerns a sequence of states and outputs, not just a final arithmetic answer.

Worked example, with the numbers

from the papers
  1. Suppose a request accepted at clock edge 0 must produce its sum at edge 1. An implementation that produces the same sum at edge 2 violates that timing contract unless the interface explicitly permits the extra cycle.

A faster clock does not automatically make it interchangeable with the original circuit: connected components may still expect the result on a particular edge.

Width also matters. Adding unsigned eight-bit values 255 and 1 gives 256 mathematically.

An eight-bit output wraps to zero if that is the specified behavior; a nine-bit output can retain 256. An optimization that drops the carry is correct for one contract and incorrect for the other.

Natural-language requests and checking code must agree on which result is required.

Roles organize work; checks establish what passed

A planner can state the intended registers, operations and state transitions. A programmer can implement them.

A reviewer can compare implementation with plan. An evaluator can use tool outcomes to identify revisions.

This separation can make a proposed change easier to inspect, but it does not make the plan correct merely because another role followed it.

Worked example, with the numbers

from the papers
  1. For example, a plan might wrongly give enable priority over reset. Every later role could agree with the implementation, while the required simultaneous-reset-and-enable case remains wrong. The useful external check comes from the specification, not from agreement among generated descriptions.

Simulation applies selected input sequences and compares observed behavior with expected behavior. A passing testbench establishes agreement on those checks, not on every possible sequence.

Formal equivalence can answer a broader comparison under explicitly modeled assumptions, but should not be inferred from the existence of a reviewer or a successful simulation. A robust account must name the actual check used.

Timing slack is a margin, not a pass percentage

For a simplified setup check, slack is the required arrival time minus the actual arrival time. If data is required by 2.0ns but arrives at 2.4ns, slack is −0.4ns: the path is late.

Reducing arrival to 2.2ns improves slack to −0.2ns, yet the requirement still fails. Halving the lateness is not timing closure.

The critical path is the path that limits the relevant timing objective under the chosen constraints. Shortening it can improve achievable speed, but another path may then become limiting.

Clock definitions, input arrival assumptions, output requirements and cell-library conditions affect the result. A percentage alone cannot say whether the final design meets its deadline.

Small starting margins also make percentages unstable. Changing slack from −0.02ns to −0.03ns worsens the magnitude of lateness by 50%, but the absolute change is 0.01ns.

Neither number should be hidden: the percentage conveys relative change, while the absolute value and required margin determine acceptance. This is a teaching calculation, not a recovered optimized report.

Pipelining and sharing change different costs

Pipelining places storage between portions of a computation so less logic must finish between adjacent clock events. Consider two serial combinational blocks taking 1.1ns each.

With 0.2ns of aggregate register overhead, a single-stage timing estimate is 2.4ns. Splitting evenly can give approximately 1.3ns per stage, but now an item crosses two stages and extra registers consume area and clock activity.

These estimates omit routing and other implementation costs.

Resource sharing instead lets several operations use one hardware unit at different times. Replacing two adders with one can reduce arithmetic hardware, but adds operand selection, scheduling and possibly storage.

If both results are required simultaneously, sequential reuse cannot meet that requirement without changing some other part of the architecture.

The design objective must therefore say which quantities may move. Minimizing area subject to a fixed output schedule is different from minimizing area while allowing arbitrary extra cycles.

A comparison that changes the functional or timing contract has changed the task, not merely found a cheaper implementation.

Power, energy and activity are different measurements

Power is energy per unit time. Energy for one task depends on power during the task and the duration of execution.

A circuit averaging 8W for two seconds uses 16J; a 10W implementation finishing in one second uses 10J. Lower power can accompany higher energy when work takes longer.

Dynamic power concerns switching activity. Leakage concerns current that can persist even when useful switching stops.

Suppressing unnecessary register updates may reduce some activity while leaving clock distribution and other logic active. Clock gating controls clock activity; it is not equivalent to disconnecting a region's power supply.

Neither should be credited with a particular leakage reduction without the corresponding implementation evidence.

A power estimate also depends on how often signals change. Comparing one design under mostly idle inputs with another under active inputs is not a matched workload comparison.

The relevant evidence includes activity assumptions, operating conditions, included circuitry and how power was calculated. A synthesis report supplies estimates under a model, not a physical measurement of fabricated hardware.

Keep each candidate's results together

Worked example, with the numbers

from the papers
  1. Suppose candidate A has power 4, area 10 and delay 3, while candidate B has power 7, area 6 and delay 2, in fixed arbitrary units. Neither dominates the other: A uses less power, B is smaller and faster.

Reporting power 4, area 6 and delay 2 as one design would invent an implementation that neither candidate provides.

Every result row should therefore identify the exact RTL revision and its correctness outcome, synthesis settings and complete metric set. If separate power-, area- and timing-oriented candidates are generated, retain them separately.

The best improvement in each column does not establish one candidate achieving all of those improvements simultaneously.

Failed generation tasks also remain part of the overall outcome even if they cannot enter a PPA comparison. In an illustrative ten-task study, finding correct implementations for six tasks and improving all six does not mean ten tasks were solved.

Report generation coverage and conditional implementation improvements with their own denominators and search budgets.

What this contributes to the larger subject

The connection to two-tier Verilog generation is the separation of behavior generation from implementation quality. The connection to MappingEvolve is that a favorable optimization score still needs a valid accepted result. The edited objects differ: RTL in one case, mapping software in the other.

The bounded hypothesis is that structured proposals plus implementation feedback can improve design choices when the original contract and acceptance checks remain fixed. It would weaken if gains depended on looser output timing, unmatched activity assumptions, manual work excluded from the budget, or selecting incompatible metrics from different candidates.

Target-library and operating conditions, complete prompt/retry cost, exact post-optimization checking, per-candidate RTL/report pairing and artifact reproduction remain unresolved in this assessment. Independent review is still required; the new explanation does not establish production readiness or a historical trend.

FPGA HLS architecture optimization: make connected stages work at compatible rates

What is available, and what is still missing

It does not supply the benchmark conditions needed to interpret that average. Official description

Its pinned README and top-level source were reread for this explanation. The saved primary assessment additionally records selected script and stored synthesis-report inspection; those observations are attributed to that earlier assessment, not to a newly executed experiment.

No manuscript page citations are available.

The release contains a Fire-module example, not the full optimization framework. Its README names Vivado HLS/Vivado 2019.2, ZCU102 and a 100MHz target, while listing full-model integration and automation as future work. These conditions describe the released example, not every paper benchmark. Pinned README

Start with a computation, not a generated file

An FPGA is a device whose configurable logic, arithmetic resources, memory blocks and connections can implement a chosen digital circuit. High-level synthesis, or HLS, translates a program and implementation directives into a hardware design.

The same computation can be implemented with different amounts of parallel arithmetic, buffering and resource sharing.

A convolution computes weighted sums over selected input values. An activation such as ReLU replaces a negative result with zero and retains a nonnegative result.

These operations define values that must be produced. Their implementation additionally determines when values are available, how they are stored and how subsequent operations receive them.

For a simple independent example, four products can use one multiplier over several cycles or four multipliers concurrently. The second choice needs enough input delivery capacity and a way to add the products.

If operands arrive one pair per cycle, installing four multipliers alone cannot sustain four useful products per cycle. Architecture optimization must consider the connected computation rather than count arithmetic units in isolation.

The inspected example branches and rejoins

The top-level source unpacks 32-bit stream payloads as floating-point values, applies a squeeze convolution and ReLU, duplicates the resulting stream, processes two expand convolution/ReLU branches, concatenates their outputs and packs the result. The function requests HLS dataflow execution. Pinned pipeline_top and duplicate_stream

Dataflow execution allows connected stages to overlap when dependencies and resources permit. It does not make all operations independent.

A consumer still needs the correct input values in the expected order. Duplication means each branch receives the required values; it does not mean the branches receive alternating halves of the input.

Concatenation joins outputs along a specified dimension. It is not addition. If one branch produces channels [a,b] and the other [c,d], an intended output might be [a,b,c,d]. Returning [a+c,b+d] has different shape and meaning. Returning [a,c,b,d] preserves four values but can still violate the required channel order. A test must check layout and ordering as well as arithmetic.

Throughput depends on the slowest sustained rate

Latency is the time from starting a particular work item until its output is ready. Initiation interval is the spacing between accepted work items in a repeated schedule. The two can differ because several items can be in progress together.

Worked example, with the numbers

from the papers
  1. For an idealized example, a pipeline has latency (the wait for one result) ten cycles and accepts another item every five cycles. Four items finish by cycle 10 + 3×5 = 25, assuming the first starts at cycle zero and no stalls occur. Processing them without overlap would take forty cycles. The first item's latency remains ten; overlap improves repeated-work throughput, not necessarily individual response time.

Now consider a producer able to supply one value per cycle and a consumer able to process one every two cycles. A finite queue temporarily absorbs the difference.

Its occupancy grows until it is full, after which the producer must slow down. More buffer space delays this event but cannot remove a permanent rate mismatch.

A duplicated stream has two consumers. If both must receive every input value, the slower branch can limit the source's sustained rate even while the faster branch is idle.

Replicating work at a branch point can therefore create a capacity requirement rather than a free speedup. The relevant optimization may involve balancing branches, changing their parallelism, or reconsidering how intermediate values are stored.

A complete stream protocol is part of correctness

Backpressure means a receiving stage temporarily prevents its sender from delivering another value, usually because storage is full. This is ordinary flow control, not automatically a deadlock. Deadlock requires a set of waits from which the system cannot advance under the allowed actions.

For an independent construction, suppose two tasks each insist on reading an empty input queue before writing the value the other task needs. Neither can begin.

A different schedule or an initial value could change the outcome. This does not show that the released Fire module deadlocks; it shows why testing arithmetic functions separately is insufficient to establish progress of a connected streaming system.

A useful functional check also needs the expected number of inputs and outputs, tensor dimensions, channel order, end-of-output signaling and numerical tolerance. Floating-point sums can change slightly when their addition order changes.

A tolerance should express an allowed numerical difference, not silently excuse an incorrect channel permutation or missing output.

Read the saved synthesis estimates without turning them into board measurements

The saved assessment records top-level latency of 335,494 cycles and interval of 229,703 cycles at a requested 10ns period. Multiplication gives approximately 3.355ms latency and 2.297ms interval.

The same assessment records an estimated 8.419ns clock period. These are stored HLS estimates, not a fresh synthesis run, achieved post-route frequency, or measured full-model performance. Selected text/XML report assessment

At a fixed clock, fewer cycles reduce the corresponding scheduled time. But a design with more parallel logic can become harder to connect physically and fail the requested clock after placement and routing.

One cannot replace the requested clock with a favorable estimate and call the product an observed speedup.

Resource fit is another separate question. FPGA lookup-table logic, registers, dedicated arithmetic blocks and memory blocks have distinct capacities.

Spare registers cannot necessarily replace exhausted memory or arithmetic resources without changing the implementation. Integrating the kernel with data transfer and control logic can consume capacity not represented by an isolated kernel estimate.

The saved script inspection found synthesis and export enabled, with C simulation and co-simulation commented out. That limits what that script demonstrates; it does not establish that the authors never ran correctness tests elsewhere.

Generating hardware files is not itself evidence of functional equivalence, timing closure, or successful execution on a board.

A faster module does not establish the headline system gain

Worked example, with the numbers

from the papers
  1. Suppose a complete workload spends forty time units in an optimized module and sixty elsewhere. Making the module ten times faster changes total time from one hundred to sixty-four, for a speedup of 100/64 = 1.5625, not ten. Transfers, other layers and control work can dominate after the improvement. This is an illustrative calculation, not a decomposition of the reported 11.78× result.

An average speedup also needs its aggregation rule and per-model results. The ratio of summed runtimes, the arithmetic mean of individual speedups and their geometric mean answer different questions.

A paper-level claim needs matched baselines, resource constraints, accepted numerical quality and complete costs before those numbers can be compared across methods.

Compared with ParetoPilot, which selects synthesis configurations, this record concerns generation and optimization of a connected hardware architecture. The available example helps explain the resulting data path but does not reveal the complete language-model search process.

Prompts, retries, model versions, rejected designs and the mechanism connecting feedback to architectural edits remain unresolved.

The bounded insight is that useful automation must jointly preserve values, stream order, progress and feasible rates. Evidence would strengthen with complete model-level comparisons and reproducible optimization histories; it would weaken if local gains disappear after integration or depend on unequal resource budgets.

The inspected sources do not yet establish that broader result.

The evidence therefore supports LLM-assisted modular HLS architecture generation and a partial artifact-backed dataflow example, not demonstrated production-ready FPGA acceleration or a reproducible end-to-end 11.78× gain. Prompts/search cost, benchmark aggregation, matched baselines, correctness, post-route/board evidence and resource/quality constraints remain unresolved.

ModuPlace: turn placement preferences into relationships that a placer can evaluate

What the recovered manuscript establishes

An author-hosted seven-page manuscript was recovered on 2026-09-08; its title, authors and DOI 10.1145/3770743.3803892 identify this paper. Text was inspected, including method and evaluation sections; no model, placer or router was executed. The current reading card below includes this recovery and preserves the original description-only fields in its disclosure.

The method partitions components hierarchically, generates weighted relative-position/rotation graphs, and places modules then components. Training combines expert examples and preference optimization. Sections 3.2–3.4, PDF pages 2–5

The evaluation uses Qwen-2.5 7B, 426 training graphs, four 80GB A100s, eleven boards, routing with PcbRouter/Freerouting, and ADS electromagnetic simulation. Table 2 reports mean wirelength 1266.5 versus SA-PCB's 1528.5, and vias 48.6 versus 81.7.

P8 instead has wirelength 816.2 versus 688.6 and vias 23 versus 12. Section 4.1 and Tables 1–2, PDF pages 5–6

Thus the reported average advantage is not improvement on every board. The explanation below develops independent examples; none is a reconstructed benchmark. Manuscript recovery does not establish reproducibility or independent acceptance.

Start with what placement must produce

A printed circuit board, or PCB, supports electronic components and conductive connections between their terminals. A schematic states which terminals must connect electrically.

Placement decides where components sit and how they are oriented. Routing then chooses actual conductive paths, subject to available layers, clearances and obstacles.

A net is a set of terminals that must be electrically connected. A via connects conductive layers through the board.

Moving a component can shorten one net while making another harder to route. A geometrically compact placement can therefore require longer routes or more layer changes than a less compact one.

Worked example, with the numbers

from the papers
  1. Consider two terminals at (0,0) and (10,0), in arbitrary length units. Their direct horizontal separation is ten. If a blocked region requires a route to rise to y=3, cross, and descend, that route has length sixteen. Both placements can have the same terminal separation while differing in the available paths. This is why an estimate made before routing is not a measurement of completed wiring.

Half-perimeter wirelength, abbreviated HPWL, sums the horizontal and vertical spans of a net's terminals. For terminals at (0,0), (10,0) and (0,4), it is fourteen. It summarizes spatial spread; it does not construct legal copper paths, determine layer changes, or certify electrical behavior. The relevant question is whether optimizing the estimate improves the completed board under the same router and rules.

Represent a relationship before choosing every coordinate

An intermediate representation is an explicit description passed between stages of a design process. Here the important conceptual distinction is between asking for final coordinates and describing relationships that constrain their choice.

A graph has objects as nodes and relationships as edges. Its usefulness depends on what each relationship means, not on the fact that it is called a graph.

For an independent example, suppose A should be left of B with a preferred horizontal displacement of four, while C should be above B by three. A coordinate optimizer can compare candidate positions with those requests.

Translating all three components together preserves the relative displacements. The board boundary and any fixed connector still determine whether the translated arrangement is legal.

What technology mapping chooses

A Boolean network specifies logical relationships independently of a particular cell library. A cell library supplies circuit implementations of functions with characterized costs and behavior. Mapping chooses how to cover the network with compatible cells. The mapped netlist records chosen cells and their connections.

Begin with one computation and several implementations

High-level synthesis, or HLS, constructs hardware from a higher-level program and implementation settings. A directive instructs the tool about choices such as loop scheduling or array organization.

Different settings can produce circuits with different resource use and execution schedules while aiming to preserve the program's specified result.

Worked example, with the numbers

from the papers
